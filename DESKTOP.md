# Настольное приложение на Tauri v2

Рабочий документ разработки. Сверено с кодом 0.4.4 (задача el-zsj)
26.09.2026; первая редакция — 21.09.2026 на базе 0.2.15. Спецификация, а
не описание готового. Реализовано: платформенно-нейтральная библиотека
выбора каталога данных (el-2be, см. «Контракт для оболочки»), управляемый
запуск `pc-api` (el-39i) и окно Tauri v2 поверх общего интерфейса (el-2a4,
см. «Окно и безопасность»), нативные папки и смена хранилища (el-646).
Жизненный цикл реализован в el-zsj; ограничения проверки ОС указаны ниже.
В публичную часть репозитория не предназначен.

## Зачем

Сейчас на Windows продукт раздаётся как zip с exe и батником
(`packaging/windows`): батник поднимает `serve --open` с базой и
миниатюрами рядом с exe, дальше интерфейс живёт вкладкой браузера. На
macOS — голый CLI-бинарь arm64. Для инструмента, которым архив разбирают
неделями, это неудобно.

Нужно окно приложения: запуск двойным кликом на **Windows x64** и
**macOS arm64**, свой значок, понятное «запущено» и «выключено», без
терминала и без вкладки браузера.

## Что это не меняет

- Сервер, база, миниатюры, вся логика — как есть. Десктоп — окно поверх
  того же `pc-api` и того же встроенного `dist`, а не вторая реализация и
  не свои экраны.
- CLI (`serve`, `--open`, Ctrl+C), Docker-образ `FROM scratch` и
  статические Linux-бинари остаются; на NAS нужен сервер, а не окно.
- Нативный код не выполняет бизнес-операций. Всё, что трогает архив, идёт
  через HTTP API с его защитами: preview token плана, подтверждение
  `purge`, writer lock (`pc_core::lock`), один исполнитель задач.
- **Никаких автоматических сетевых запросов.** Проверка обновлений, updater
  и телеметрия в MVP не входят (см. «Следующий этап»).

## Сборка и изоляция в workspace

### Что было неверно

Прежняя редакция предлагала исключить крейт из `default-members`, чтобы
«`cargo test --workspace` на ubuntu его не трогал». Это не так. По
[документации Cargo](https://doc.rust-lang.org/cargo/reference/workspaces.html#package-selection)
`default-members` действует только тогда, когда команда запущена в корне
workspace **без** `-p`/`--workspace`; `--workspace` выбирает всех членов.
А корневой `Cargo.toml` задаёт `members = ["crates/*"]` — новый каталог
`crates/pc-desktop` станет членом сам.

Хуже того, `default-members` развёл бы проверки: CI вызывает
`cargo clippy --all-targets` без `--workspace` (в виртуальном workspace
без `default-members` это все члены), а `cargo test --workspace` — всех.
С `default-members` clippy перестал бы видеть десктоп, а тесты — нет.

### Решение: target-gating внутри крейта

`crates/pc-desktop` — обычный член workspace, `default-members` не
вводится. Tauri и его плагины подключаются только для целевых ОС
([платформенные зависимости Cargo](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#platform-specific-dependencies)):

```toml
[target.'cfg(any(windows, target_os = "macos"))'.dependencies]
pc-api.workspace = true
tokio.workspace = true
tauri = { version = "2.11", default-features = false, features = [
    "wry", "compression", "common-controls-v6", "dynamic-acl", "custom-protocol", "tray-icon",
] }

[target.'cfg(any(windows, target_os = "macos"))'.build-dependencies]
tauri-build = "2"
```

Диалоги el-646 используют `rfd` с тем же `cfg`; `tauri-plugin-dialog`
не нужен (его init script меняет синхронный `window.confirm` общего UI).
Координация экземпляров и геометрия находятся в нейтральной библиотеке;
`tray-icon` включён у Tauri, меню трея создаётся только на Windows.
Из фич Tauri по умолчанию убраны линуксовые `x11` и `dbus`. `custom-protocol`
включён всегда: dev-сервера у приложения нет (интерфейс отдаёт `pc-api`),
поэтому обычный `cargo build` собирает то же приложение, что и `tauri
build`, со встроенными ресурсами — `tauri-cli` для сборки не нужен.

Устройство крейта (реализовано в el-2a4):

- `src/lib.rs` — платформенно-нейтральная часть: разрешение data-dir и
  bootstrap-конфиг (`bootstrap`, `resolve`, `error`), правила окна
  (`window`: какие адреса окно может показывать, адрес сервера `127.0.0.1:0`,
  разбор `--data-dir`, двуязычный отчёт об ошибке запуска). Зависит только
  от `pc-core`/`pc-db` и компилируется и тестируется **на всех трёх ОС**,
  включая Linux. Системные каталоги передаются параметром (`SystemDirs`), а
  не берутся из Tauri, — так логика тестируется без окна.
- `src/shell.rs` и `main.rs` под `#[cfg(any(windows, target_os = "macos"))]`
  — окно Tauri. На остальных ОС бинарь `photo-cleanup-desktop` печатает,
  что настольная сборка поддерживается только на Windows и macOS, и
  выходит с кодом 2.
- `build.rs` вызывает `tauri_build::build()` под тем же `cfg`. Сборка
  только нативная (как и в `Dockerfile`): `cfg` в `build.rs` — это
  платформа хоста, и при кросс-компиляции он разошёлся бы с целью.
- `tauri.conf.json` — имя «Photo Cleanup», идентификатор, `frontendDist =
  ui` (только страница ошибки запуска), строгий CSP для неё, окна не
  объявлены (создаются в коде), `bundle.active = false` (установщики — не
  MVP). `icons/` сгенерированы из `assets/icon.svg` (PNG 32/128/256, `.icns`,
  `.ico` — последний обязателен для `tauri-build` на Windows). Каталог
  `gen/`, который `tauri-build` пишет при каждой сборке и который различается
  по ОС, в `.gitignore` крейта.

Что это даёт:

| команда | Linux (ubuntu CI) | Windows / macOS |
|---|---|---|
| `cargo test --workspace --locked` | собирает lib и заглушку, **без webkit2gtk** | собирает и тестирует всё |
| `cargo clippy --all-targets -- -D warnings` | lib и заглушка | всё, включая оболочку |
| `docker build` (`-p pc-cli`) | Tauri не компилируется | — |

`Cargo.lock` один на workspace и содержит зависимости всех платформ, так
что `--locked` продолжает работать везде. Linux-зависимости самого Tauri
(`webkit2gtk`, gtk) не попадают в граф Linux-сборки, потому что `tauri`
для Linux не подключён вовсе.

Проверено в el-2a4 (26.09.2026, macOS arm64 хост + Docker
`rust:1.98-slim-bookworm` aarch64):

- на Linux в графе `cargo tree --locked --workspace -e normal,build,dev` нет
  ни одного пакета `tauri*`/`wry`/`gtk`/`webkit2gtk`, в образе без
  webkit2gtk проходят `cargo clippy --all-targets -- -D warnings` и `cargo
  test --workspace --locked`, заглушка выходит с кодом 2. `cargo tree
  --target x86_64-unknown-linux-gnu`, запущенный **на macOS**, показывает
  `tauri-build` — он оценивает `cfg` build-зависимостей по хосту; мерить
  надо на Linux;
- `docker build --target export .` проходит без изменений `Dockerfile`
  (`-p pc-cli` не собирает `pc-desktop`);
- существующие версии в `Cargo.lock` не изменились, добавлены только новые
  пакеты.

Не проверено: сборка и запуск на Windows (нет машины; CI `windows` job
теперь компилирует оболочку в `cargo test --workspace`) — это el-56k.

### Отвергнутые варианты

- **`default-members`** — см. выше: не исключает из `--workspace` и
  расщепляет clippy и тесты.
- **`exclude` и отдельный workspace** — второй `Cargo.lock`, `--locked` и
  обязательные проверки перестают его покрывать, версии `pc-api` и
  зависимостей расходятся незаметно.
- **Cargo-фича `desktop`, выключенная по умолчанию** — обязательные
  проверки без `--all-features` не компилируют оболочку, а с
  `--all-features` Linux снова требует webkit2gtk.

## Запуск сервера: контракт `pc-api`

Реализовано в el-39i (`crates/pc-api/src/server.rs`). `pc_api::serve(db,
thumbs, quarantine, bind, open)` — тонкая обёртка над `start`: печатает
адрес, при `--open` открывает браузер, ждёт Ctrl+C и вызывает
`shutdown(CancelJob)`. Инициализация (миграции, язык из настроек, пометка
осиротевших задач, флаг `network`) живёт только в `start` — десктоп её не
повторяет.

```rust
pub struct ServerConfig {
    pub db_path: PathBuf,
    pub thumbs: PathBuf,
    pub quarantine: Option<PathBuf>,
    pub bind: SocketAddr,           // десктоп: 127.0.0.1:0
}

pub struct Server { /* state, адрес, канал остановки, задача axum */ }

/// Возвращается, когда сервер готов: AppState создан (миграции, язык из
/// настроек, пометка осиротевших задач), listener уже привязан. Соединения
/// после этого момента принимаются (очередь ядра), поэтому окно можно
/// открывать сразу по `local_addr()`.
pub async fn start(config: ServerConfig) -> anyhow::Result<Server>;

impl Server {
    pub fn local_addr(&self) -> SocketAddr;          // фактический порт
    pub fn active_job(&self) -> Option<ActiveJob>;   // { id, kind }
    pub async fn shutdown(self, mode: Shutdown) -> Result<(), ShutdownError>;
}

pub enum Shutdown {
    /// Отказать, если идёт задача, иначе остановиться.
    IfIdle,
    /// Отменить задачу через Control::cancel и дождаться её конца.
    CancelJob,
}

pub enum ShutdownError {
    /// IfIdle застал задачу. Сервер продолжает работать и возвращается
    /// вызывающему — хэндл не теряется, можно спросить человека и повторить.
    Busy { server: Box<Server>, job: ActiveJob },
    /// Сбой самой остановки; сервера уже нет.
    Failed(anyhow::Error),
}
```

Требования и как они выполнены:

- Ошибки `bind` и инициализации (занятая/битая база, чужая версия схемы)
  возвращаются из `start` как `Err`, а не печатаются: десктоп показывает
  их в окне. Инициализация идёт до `bind`, поэтому неудачный старт не
  оставляет открытого порта.
- `shutdown` сначала поднимает `AppState::closing` и один раз проходит
  mutation gate: всё, что уже было внутри (ручная правка, установка
  задачи), доделывается, а дальше каждая запись — `POST /api/jobs` и все
  ручные изменения через `as_writer` — получает **503** «сервер
  останавливается». Чтение продолжает работать до остановки HTTP.
- Для `CancelJob` — флаг отмены и ожидание **без таймаута**, пока задача
  сама дойдёт до границы файла (`Control::check` стоит между действиями,
  не внутри `rename` + записи журнала), освободит writer lock и запишет
  терминальное состояние в `jobs`. Ждём `JoinHandle` рабочего потока
  (`Jobs::worker`), а не `Jobs::active`: `active` очищается *до* записи
  состояния. Принудительного убийства потока нет.
- Затем — graceful остановка axum; последняя ссылка на `AppState` и его
  соединение SQLite уходят вместе с ней (тикер прогресса держит `Weak`).
- `IfIdle` при идущей задаче опускает `closing` обратно и возвращает
  `Busy` с сервером; в этот короткий промежуток запись может получить 503.
- CLI: первый Ctrl+C = `shutdown(CancelJob)` с сообщением, какая задача
  останавливается; второй Ctrl+C выходит сразу (код 130), дальше
  действует правило ниже. В 0.4.4 и раньше Ctrl+C останавливал только
  HTTP, а рантайм tokio при выходе молча дожидался задачи целиком (drop
  рантайма ждёт `spawn_blocking` без ограничения).
- Если процесс всё же убит (питание, диспетчер задач), действует текущее
  правило `AppState::new`: при следующем старте `queued`/`running`
  становятся `interrupted`, незавершённые записи журнала сверяются
  `journal-reconcile`. Дисковые операции **никогда не повторяются
  автоматически** после перезапуска.
- `state.network` для десктопа всегда `false` (loopback).

Проверка `Host` (el-55m, подключена в `server::start` при интеграции с
el-39i): активна только когда слушатель реально забиндился на loopback-адрес
(`local.ip().is_loopback()` после `bind`, т.е. и для явного
`127.0.0.1:0`/desktop, и для дефолта CLI); при bind на не-loopback (NAS)
поведение не меняется — middleware туда не подключается. Допустимые
значения заголовка — фактический адрес/порт после `bind` (порт `:0`
резолвится в реальный слушаемый порт до навешивания проверки):
`127.0.0.1:<порт>` или `localhost:<порт>` для IPv4-бинда,
`[::1]:<порт>` (localhost тоже принимается) для IPv6-бинда. Отсутствующий
или чужой `Host`, чужое имя хоста и неверный порт — отказ `421 Misdirected
Request`. `X-Forwarded-Host` не учитывается — заголовку доверия нет, так
как его может подставить сама rebinding-страница. Проверка живёт в
`server::start()` (`crates/pc-api/src/server.rs`), навешивается на router
сразу после `bind`, до `axum::serve` — так её получают и CLI (`serve()`,
тонкая обёртка), и desktop (`start()` напрямую), без дублирования. Код и
тесты — `crates/pc-api/src/security.rs`; регрессия на подключение (не
просто на саму функцию) — `crates/pc-api/tests/server.rs`. Для dev-прокси
(`npm run dev`, `crates/pc-api/web/vite.config.ts`) обязателен
`changeOrigin: true` у `/api`: иначе Vite пересылает исходный
`Host: localhost:5173` и loopback pc-api отвечает 421 на каждый запрос.
JSON-запросы из чужого origin и без rebinding уже упираются в CORS
preflight, но rebinding его обходит — поэтому проверка нужна отдельно.

## Где лежат данные

### Раскладка каталога данных

Каталог данных (data-dir) содержит ровно то, что сейчас кладут рядом с
базой CLI и батник:

```
<data-dir>/
  photo-cleanup.db          (+ -wal, -shm во время работы)
  photo-cleanup.db.writer-lock
  thumbs/
```

Карантин в data-dir не входит: по умолчанию он в корне файловой системы
каждого файла (иначе перенос перестал бы быть `rename`).

### Режимы и bootstrap-конфиг

Путь к базе нельзя хранить в самой базе, поэтому выбор режима лежит в
маленьком файле **вне** data-dir и **вне** каталога программы:

- идентификатор приложения (он же имя каталога Tauri):
  `io.github.imcitius.photo-cleanup`;
- `LOCAL` = `app_local_data_dir()` Tauri: `%LOCALAPPDATA%\<id>` на
  Windows, `~/Library/Application Support/<id>` на macOS
  ([PathResolver](https://docs.rs/tauri/latest/tauri/path/struct.PathResolver.html)).
  Roaming-профиль Windows не используется: путь к локальному диску с
  другой машины был бы ложью;
- bootstrap: `LOCAL/desktop.json`, пишется атомарно (временный файл +
  rename):

```json
{ "version": 1,
  "mode": "system",          // "system" | "custom"
  "data_dir": null,          // абсолютный путь для custom
  "previous": null }         // прежний выбор, пока новый не подтверждён запуском
```

Выбор, сделанный **переносом** данных, записывается как `"version": 2` с
привязкой к проверенным объектам (см. «Защищённое пространство имён и
привязка копии»):

```json
{ "version": 2, "mode": "custom", "data_dir": "/Users/me/pc-data",
  "binding": { "volume": "<UUID тома>", "dir": 1234, "db": 5678,
               "thumbs": 5679, "generation": "<32 hex>" },
  "previous": { "mode": "system", "data_dir": null } }
```

Сборка без привязок такой файл не читает («записан более новой версией»)
и не переписывает: тихого понижения привязанного выбора до одного пути
нет. Файлы формата 1 — от прежних версий, первого запуска и явного
«использовать существующую папку» — читаются и работают как раньше; они
не объявляются проверенной копией. Формат 1 с полем `binding` — ошибка
чтения.

Три режима:

1. **system** (по умолчанию) — `LOCAL/data/`.
2. **portable** — только Windows и только явно: рядом с exe лежит файл
   `photo-cleanup.portable`, данные в `<каталог exe>\data\`. Портабельный
   режим не угадывается по доступности каталога на запись. На macOS не
   поддерживается: скачанный браузером `.app` запускается через App
   Translocation из случайного read-only пути, «рядом с программой» там
   нет, а писать внутрь `.app` нельзя.
3. **custom** — каталог, выбранный пользователем (например, большой диск
   рядом с архивом).

### Порядок разрешения при запуске

1. Аргумент `--data-dir <путь>` (тесты, продвинутое использование) — на
   этот запуск, в bootstrap не записывается.
2. Windows: есть `photo-cleanup.portable` рядом с exe → portable. Каталог
   недоступен на запись → экран ошибки; тихого отката в системный каталог
   нет (прежняя редакция предлагала откат — отменено).
3. Есть `LOCAL/desktop.json` → его режим. Файл не читается или не
   разбирается → экран ошибки, файл не перезаписывается.
   Каталог `custom` отсутствует (отключён диск) или в нём нет
   `photo-cleanup.db` → экран «Данные недоступны: <путь>» с действиями
   «Повторить», «Выбрать другую папку», «Вернуться к прежней» (если есть
   `previous`). **Пустая база на месте недоступной не создаётся.**
4. Bootstrap нет → первый запуск: создаётся `LOCAL/data/`, открывается или
   создаётся база, и только после успешного открытия пишется bootstrap
   `system`. Если рядом с exe лежит `photo-cleanup.db` от батника,
   первый экран предлагает использовать её (как custom, без копирования)
   или начать в системном каталоге — молча не подхватывается.

Новая база создаётся только в шаге 4 или по явному действию пользователя
(«создать новую базу в этой папке»). Каталог программы ни в одном режиме,
кроме явного portable, не записывается, поэтому запуск из read-only места
(Program Files, смонтированный образ, translocated `.app`) работает.

Пути с пробелами и кириллицей — обязательный тестовый случай resolver'а и
переноса (el-2be, el-646).

Уточнения, принятые при реализации (el-2be):

- Правило «пустая база не создаётся» действует и для `system`: bootstrap
  есть, а `LOCAL/data/photo-cleanup.db` нет → тот же экран «Данные
  недоступны», а не новая база. Bootstrap существует только после
  успешного открытия базы, значит, данные там были.
- `--data-dir` может создать базу: это явное указание на этот запуск.
  Относительный путь отвергается — и там, и в bootstrap, и при выборе папки:
  текущий каталог приложения, запущенного из Finder/Explorer, случаен.
- Битый bootstrap при запуске не перезаписывается, но явный выбор папки
  пользователем с экрана ошибки его заменяет — это и есть выход. Bootstrap
  более новой версии (`version` > 1) не перезаписывается ничем.
- Каталог проверяется на запись так, чтобы в папке пользователя никогда не
  появлялась именованная запись, которую потом пришлось бы удалять по пути.
  Удалить путь «только если там всё ещё наш объект» на Linux и macOS
  атомарно нельзя: между любой сверкой идентичности и `unlink`/`rmdir`
  другой процесс может переместить на это имя свой файл, symlink или пустой
  каталог с xattr/ACL, и удалён был бы он (review el-1e5d, el-2d03).
  Поэтому ничего не создаётся под именем и ничего не удаляется:
  - Linux: безымянный файл `O_TMPFILE | O_EXCL` в каталоге, в который
    пишутся байты. В каталоге он не появляется, привязать ему имя нельзя,
    ядро освобождает его при закрытии. На файловой системе без `O_TMPFILE`
    (`EOPNOTSUPP`, или `EISDIR` на старом ядре) — вопрос ядру, как ниже,
    через `faccessat(W_OK | X_OK)`.
  - macOS: вопрос ядру без создания чего-либо — `faccessat` с расширенными
    правами «добавить файл», «искать», «удалить файл» (`_WRITE_OK`,
    `_EXECUTE_OK`, `_RMFILE_OK`, `AT_EACCESS`). Проверено: учитываются
    ACL (тесты с `chmod +a ... deny`) и read-only том (вручную на
    read-only APFS-образе — `EROFS`). Спрашиваются права на файлы,
    а не на подкаталоги: папка, где ACL запрещает только `add_subdirectory`,
    годна; где запрещено `add_file` или `delete_child` (SQLite удаляет
    `-wal` и журнал) — нет. Ограничение: это ответ ядра о правах, а не
    пробная запись; сервер сетевого тома или заполненный диск может
    отказать позже, и это проявится ошибкой открытия базы, а не данными.
  - Windows: файл с уникальным именем
    `.photo-cleanup-write-probe-<pid>-<время>-<счётчик>`, `CREATE_NEW`
    (занятое имя — файл, каталог, ссылка — пропускается, не открывается),
    в него пишутся байты; открыт без общего доступа и с
    `FILE_FLAG_DELETE_ON_CLOSE`. Пока он открыт, его нельзя открыть,
    переименовать, удалить или подменить, а удаляет его система по
    дескриптору при закрытии — путь не удаляется никогда. Проверено только
    компиляцией (clippy для `x86_64-pc-windows-msvc`) и тестами, которые
    на Windows ещё не запускались.

  Любой отказ — ошибка «нет записи», успех без выполненной проверки не
  сообщается. Существующая база открывается без флага CREATE и
  проверяется, что SQLite не открыл её молча только на чтение.

### Контракт для оболочки

Крейт `pc-desktop`, `src/lib.rs` и модули `bootstrap`, `resolve`, `error`.
Тесты — `crates/pc-desktop/tests/data_dir.rs`, на временных каталогах;
readonly-случаи — только unix (`chmod 555`; под root пропускаются явно).

```rust
let dirs = SystemDirs::new(app.path().app_local_data_dir()?, exe_dir);
let r = pc_desktop::resolve(&dirs, cli_data_dir)?;   // только чтение
// r.legacy_dir == Some(..) → спросить: choose_data_dir(.., UseExisting) или продолжить с r
let p = pc_desktop::prepare(&dirs, &r)?;             // открыть/создать базу, затем bootstrap
// pc_api::start(p.layout.db, p.layout.thumbs, ..)
pc_desktop::confirm_started(&dirs, &p)?;             // снять `previous`
```

- `SystemDirs { app_local_data, exe_dir, portable_supported }` —
  `SystemDirs::new` ставит `portable_supported = cfg!(windows)`.
- `DataLayout { dir, db, thumbs }` — `photo-cleanup.db` и `thumbs/`.
- `StartupError` сериализуется с тегом `kind`
  (`data_unavailable` с `source`, `dir`, `why.what` ∈ `missing`,
  `not_a_directory`, `no_database`, `not_a_database`, `not_writable`, и
  `previous`; `bootstrap_unreadable`, `bootstrap_unsupported`,
  `bootstrap_write`, `database_exists`, `relative_path`,
  `portable_active`, `no_previous`, `create_failed`) — по нему экран
  ошибки выбирает действия; `Display` двуязычный через `pc_core::tf!`.
- Действия экрана ошибки: «Повторить» — снова `resolve`; «Выбрать другую
  папку» — `choose_data_dir(dir, UseExisting | CreateNew)` →
  `prepare`; «Вернуться к прежней» — `revert_to_previous` → `prepare`.
  В portable-режиме выбор и возврат отвергаются (`portable_active`).

Контракт для переноса (el-646): перенос копирует базу и миниатюры сам,
а завершает его запись `Bootstrap::new(Choice::custom(new), Some(old))`
через `write_bootstrap` (атомарно) и перезапуск. Дальше обычный путь:
новый каталог поднялся → `confirm_started` снимает `previous`; не поднялся
→ `data_unavailable` с `previous` и `revert_to_previous`. Своего API
настроек у переноса нет, «текущий выбор» — только bootstrap.

### Смена каталога данных

Это перенос **данных приложения** (база и миниатюры), не фотографий.
Выполняет нативная оболочка, потому что серверу нужно остановиться.

1. **Предпросмотр** (ничего не меняет): текущий и новый путь, размер базы
   вместе с WAL и миниатюр, свободное место в цели, конфликты. «Отмена» на
   шаге предпросмотра оставляет всё как было. После подтверждения
   отмены посреди копирования нет.
2. **Конфликт**: занято имя `photo-cleanup.db`, любой его sidecar
   (`-wal`, `-shm`, `-journal`), `thumbs`, старый `.partial` или его sidecar →
   копирование запрещено. Проверяется сама directory entry через
   `symlink_metadata`, включая symlink/dangling; ошибка чтения означает отказ.
   Отдельное явное действие — «переключиться на существующую базу» без
   копирования. Наличие sidecars у существующей БД не скрывает это действие:
   оно доступно и для проверенной копии с пустыми резервациями после отказа
   spawn и восстановления bootstrap. UI требует `existing_database=true`
   и только конфликты DB/cache/sidecars; прочие blockers сохраняют запрет.
   Одни чужие sidecars без основной БД, symlink/dangling вместо БД и
   оставшиеся `.partial` не предлагают переключение. При подтверждении
   backend заново проверяет существующую БД и writer lock.
   Том цели, на котором временные папки переноса нельзя закрыть от других
   пользователей (FAT/exFAT, noowners, без ACL), запрещает копирование
   блокером `no_private_folders` с путём и причиной, но не переключение на
   уже лежащую там базу — см. «Том цели: владельцы и ACL». Том без
   rename без замены (exFAT) — так же, блокером `no_exclusive_rename`
   (см. «Том цели: переименование без замены»).
3. **Остановка записей**: `Server::shutdown(IfIdle)` отказывает при
   идущей задаче; пользователь ждёт или останавливает её обычным UI.
   Mutation gate завершает начатые записи и запрещает новые. Writer locks
   исходной и целевой БД удерживаются до завершения записи bootstrap
   (`Copied::commit`); CLI и второй сервер не могут писать в этот промежуток.
4. **Захват имён и копия базы**: после повторного preview под обоими замками
   каждый final sidecar эксклюзивно создаётся через `create_new`. Это пустые
   файлы текущего переноса, а не WAL исходника. Затем эксклюзивно создаётся
   **каталог** `photo-cleanup.db.partial/` (только для пользователя с момента
   создания, см. «Регистрация staging-каталога»); он принимается, только если
   это запись в целевом каталоге, открытом до создания (`TargetDir`).
   Внутри него этот перенос сам эксклюзивно создаёт пустой `photo-cleanup.db`
   (`openat(O_CREAT|O_EXCL|O_NOFOLLOW)` относительно дескриптора staging), и
   `VACUUM INTO` заполняет **этот** файл, только пока путь ведёт к нему.
   SQLite владеет всем этим staging
   namespace, не открывает и не очищает соседние старые `.partial-wal/shm/journal`.
   Снимок включает содержимое исходного WAL; sidecars побайтно не копируются.
5. **Проверка копии**: `PRAGMA integrity_check` = `ok`, совпадает
   `MAX(version)` в `schema_version` и число строк **каждой** пользовательской таблицы.
   Проверяющее соединение читает созданный этим переносом объект (macOS —
   `/dev/fd/N` удерживаемого дескриптора), а не то, что лежит по имени.
   `photo-cleanup.db` публикуется последним, после кэша, переносом **из
   открытого staging-каталога в открытый целевой** без замены существующего
   имени (`renameatx_np(RENAME_EXCL)` / `renameat2(RENAME_NOREPLACE)` между
   дескрипторами; Windows — `FILE_RENAME_INFO` с `RootDirectory` через handle
   объекта), см. «Публикация через открытые каталоги».
6. **Миниатюры** — в `thumbs/` **внутри** того же приватного
   `photo-cleanup.db.partial/` (отдельного `thumbs.partial/` больше нет; это
   имя, оставшееся от старых версий, по-прежнему блокирует перенос), сверка
   числа и суммарного размера файлов, затем публикация так же, как база.
   Ошибка здесь отменяет весь перенос, как и ошибка базы: полуперенесённого
   состояния нет.
7. **Bootstrap**: перед публикацией и перед commit проверяются идентичность
   открытых final sidecar-файлов и их нулевой размер, а также что путь цели
   всё ещё ведёт в открытый целевой каталог, а `photo-cleanup.db` и `thumbs/`
   в нём — проверенные объекты. Замена или изменение
   запрещает переключение. Bootstrap пишется атомарно с новым режимом,
   привязкой и `previous` = старый; последняя проверка идёт после записи и
   fsync временного файла, непосредственно перед rename. Затем перезапуск
   приложения. Запуск сверяет привязку до SQLite и после открытия сервером.
   Успешный старт на новом месте очищает
   `previous`; неуспешный показывает экран ошибки с «Вернуться к прежней».
8. **Исходные данные не удаляются никогда** — ни при успехе, ни при
   ошибке. Экран настроек показывает, где осталась старая копия; удалить её
   пользователь может сам.

Любая ошибка (нет места, ошибка копирования, проверка не сошлась,
процесс перезапуска не удалось создать) сохраняет исходные данные.
При отказе spawn восстанавливается прежний bootstrap и сервер; ошибка
восстановления bootstrap явно сообщается. Если новый процесс запущен, но
хранилище недоступно, `previous` остаётся до явного возврата со страницы
ошибки. Cleanup удаляет только захваченные staging-каталоги и собственные
неизменённые пустые резервации: идентичность сверяется с открытым handle
через `same-file` (пакет уже был в Cargo.lock через walkdir; версии не менялись).
Заменённые имена, symlink и записанные кем-то sidecars сохраняются.

Удаление не устроено как «проверить имя, затем удалить имя» (el-3p7c):
в POSIX нет unlink «только если это всё ещё тот inode», и такая пара
удаляла бы то, что другой процесс переименовал на наше имя между
проверкой и удалением (воспроизведено до исправления: 0/2, чужие payload
каталога и sidecar удалены). Теперь `remove_owned` (`relocate.rs`):
проверяет запись по имени; создаёт рядом новый каталог с уникальным
именем `.photo-cleanup-removing-*`, доступным только пользователю с момента
создания и проверенным как staging (см. «Регистрация staging-каталога»); атомарно переносит туда
запись через rename без замены — переносится ровно то, что лежит по имени
в этот момент, symlink не разыменовывается; сверяет идентичность (и для
резерваций нулевой размер) уже там; только доказанно своё удаляется.
Чужая запись возвращается на место rename без замены; если имя тем
временем снова занято, она остаётся в приватном каталоге, и ошибка
называет путь. Ничего не удаляется.

**Привязка к открытым каталогам, а не к именам (review el-5null).** Имя
приватного каталога лежит в общем родителе. Другая учётная запись с
правом переименовывать записи в нём (macOS `delete_child`/
`add_subdirectory` в ACL, запись в родителе без sticky-бита) могла после
проверки переименовать **весь** приватный каталог, не заходя внутрь, и
создать под прежними именами чужое дерево: `remove_dir_all` по пути
удалял `foreign-photo.jpg`, очистка возвращала `Ok`, наша копия оставалась
без сообщения (воспроизведено review 0/1 и нашими регрессиями 0/4 до
исправления). Теперь на Unix после открытия родителя ни один шаг не
адресуется путём: родитель открывается один раз (`O_DIRECTORY`),
проверка, перенос и возврат идут через `fstatat`/`renameatx_np(RENAME_EXCL)`
(macOS) / `renameat2(RENAME_NOREPLACE)` (Linux) относительно дескрипторов;
приватный каталог открывается относительно родителя с `O_NOFOLLOW` и
проверяется через свой дескриптор; доказанно своё удаляется `unlinkat`
относительно дескриптора приватного каталога, дерево — поуровнево через
`openat(O_NOFOLLOW)` (ссылки внутри удаляются, не разыменовываются).
Переименование родителя, приватного каталога или любого предка ничего
не перенаправляет. Имя приватного каталога удаляется `rmdir` только если
по нему всё ещё наш каталог (тот же dev/ino, что у дескриптора); иначе
имя не трогается, а ошибка называет прежний путь и текущее место
приватного каталога (`F_GETPATH` на macOS, `/proc/self/fd` на Linux).
Прочие Unix без exclusive `renameat` отказываются (ошибка, ничего не
удаляется).

Windows: объект удаляется через handle, а не через имя. Handle
регистрации staging и резерваций открывается с `DELETE`; после проверки
имени удаляется именно этот объект, где бы он ни был: содержимое
перечисляется через handle каталога (`FileIdBothDirectoryInfo`),
открывается по file ID (`OpenFileById`, `FILE_FLAG_OPEN_REPARSE_POINT` —
junction/symlink удаляются как запись, не разыменовываются) и удаляется
`SetFileInformationByHandle(FileDispositionInfoEx, POSIX semantics)` с
откатом на классический `FileDispositionInfo`. Приватного каталога на
Windows нет, путь при удалении не используется. Для резервации длина
перечитывается через handle непосредственно перед удалением. **Не
запускалось на Windows** — только type-check выдержки (ниже).

#### Защищённое пространство имён и привязка копии (el-2xri; review el-59w6z, диагноз el-49o3y)

Review el-59w6z (913fcb2, NOT APPROVED) показал, что проверки имён вокруг
записи не закрывают перенаправление пути: при цели, где другая учётная
запись могла переименовывать записи, SQLite записывала копию базы
(262144 байта) в чужой каталог, заполняла чужой **пустой**
`photo-cleanup.db` (тот же inode, новый mtime), подменённые после публикации
`photo-cleanup.db`/`thumbs` давали `Ok` и переключали bootstrap, FIFO-пауза
в чтении bootstrap после последней проверки давала выбор чужой папки, а
`Incomplete` называл чужие байты «готовой и проверенной копией». Путь
остаётся строкой: сколько бы раз его ни проверяли, следующее
переименование может прийти сразу после проверки. Решение пользователя
(27.09.2026, «разрешаю, продолжай планы дальше»): переносить **только**
туда, где путь не может перенаправить никто, кроме этого пользователя и
системы, а сам перенос и все последующие запуски привязать к проверенным
объектам. Решение A остаётся в силе.

**Допуск (`namespace.rs`), только чтение, до любой записи.** Для каждого
каталога от `/` до цели (для несуществующей — до ближайшего существующего
предка), до текущей папки данных и до папки настроек (`LOCAL`) — каталоги
открываются по одному (`openat(O_DIRECTORY|O_NOFOLLOW)` от дескриптора
родителя), проверка через дескриптор:

- владелец — root или этот пользователь: никто другой не может сменить
  права, ACL или владельца каталога;
- нет записи для group/other: никто другой не может добавить,
  переименовать или удалить записи. Исключение — sticky-каталог **выше**
  последнего (`/tmp`): там другие добавляют свои записи, но не могут
  переименовать следующий каталог нашего пути (он root или наш). Сама
  цель (где создаются записи) — без исключения;
- ACL: macOS — нет ни одной `allow`-записи с `add_file`,
  `add_subdirectory`, `delete_child`, `delete`, `writeattr`,
  `writesecurity`, `chown` (с любыми флагами наследования); `deny`-записи
  (`everyone deny delete` на домашних папках) и `allow` только на чтение
  допустимы. Linux — любой POSIX ACL (`system.posix_acl_access`/`_default`)
  отвергается. Чужой ACL для прохождения проверки не меняется;
- том: владельцы и права хранятся и применяются (решение A). macOS теперь
  принимает только локальные (`MNT_LOCAL`) `apfs`/`hfs` без
  `MNT_IGNORE_OWNERSHIP` и с ACL; сетевые (smbfs/nfs/afp/webdav), FUSE,
  FAT/exFAT/NTFS — отказ. Linux — прежний список `f_type`;
- у тома цели есть постоянный идентификатор (macOS — UUID тома через
  `fgetattrlist(ATTR_VOL_UUID)`, Linux — `statfs.f_fsid`), к которому
  привязывается копия.

Ссылки в запрошенном пути разрешаются один раз (`canonicalize`), обход
ссылок не принимает; дальше везде используется канонический путь, в том
числе в bootstrap. Почему этого достаточно: переименовать, заменить или
перенастроить компонент пути может только тот, у кого есть право на
запись в родителя или владение компонентом; допуск доказывает, что такие
права есть только у пользователя и root — они вне модели угроз. Дескрипторы
цепочки удерживаются до конца операции, и `Protected::recheck` перед
публикацией и перед записью bootstrap повторяет обход и сравнивает dev/ino
каждого каталога — это ловит изменения собственными программами
пользователя (Finder, chmod), но **само удержание дескриптора rename не
запрещает**: гарантия — от прав, не от дескриптора.

Отказ — `Blocker::UnprotectedFolder { role, path, component, reason }`
(`kind: "unprotected_folder"`, `role`: `target`/`source`/`settings`) в
preview и тот же блокер из `copy_data` **до** writer lock, создания цели,
резерваций, staging и bootstrap. Текст: «папка назначения `<путь>` лежит там,
где путь могут подменить или перенастроить другие пользователи:
`<компонент>` `<причина>`. Выберите папку, путь к которой принадлежит
только вам и системе, например внутри домашней папки». Недостающие каталоги
цели создаются только после допуска, по одному относительно открытого
родителя, с режимом 0700, и каждый проверяется до следующего; при отказе
переноса пустые созданные каталоги удаляются `rmdir` по дескриптору
родителя (непустой остаётся). «Использовать существующую папку»
(`switch_to_existing`) временных папок и копии не создаёт и остаётся
доступным: UI показывает эту кнопку и при `unprotected_folder`.

**Намеренное ограничение совместимости**: сверх решения A отвергаются цели
в общих каталогах (например, `/Users/Shared` 1777 как сама цель, папка с
`chmod +a "everyone allow add_file…"`, group-writable каталоги, каталоги,
принадлежащие другому пользователю, в том числе на пути), сетевые тома и
текущая папка данных/папка настроек, лежащие в таком месте. Модель угроз
не ослаблена; исключение того же UID/root/admin не расширено.

**Копия как объект** (`relocate.rs`, `snapshot`, `Payload`):

1. `photo-cleanup.db` создаёт этот перенос: `openat(O_CREAT|O_EXCL|O_NOFOLLOW,
   0600)` в открытом staging. Любая существующая запись, включая чужой
   пустой файл, — отказ без изменений.
2. `VACUUM INTO` (SQLite 3.50.2 заполняет существующий файл, только если он
   пуст) запускается, только если и запись в открытом staging, и объект по
   пути — этот файл; после копии — та же проверка, `fsync`, на файл через
   дескриптор пишется `generation` (16 случайных байт `getentropy`, xattr
   `io.github.imcitius.photo-cleanup.generation` / `user.photo-cleanup.generation`).
3. Проверка (`integrity_check`, схема, число строк каждой таблицы) читает
   **этот объект**: macOS — `file:/dev/fd/N?mode=ro&immutable=1` удерживаемого
   дескриптора (открытие `/dev/fd/N` на macOS — тот же открытый файл,
   переименования имён его не меняют; `immutable` — без блокировок и
   журнала). Linux — по пути, который допуск удерживает от чужих
   переименований, и после проверки снова сверка объекта по пути и в
   staging. Любое расхождение — отказ, ничего не опубликовано, ошибка
   называет текущее место нашего файла.
4. `thumbs/` создаётся в staging всегда (пустым, если кэша нет), заполняется
   и считается через дескрипторы; его handle — часть полезной нагрузки.
5. Публикация переносит **эти** объекты (`Payload.db`, `Payload.thumbs`) из
   открытого staging в открытую цель без замены; `Copied` несёт их,
   допуски и оба writer lock до конца commit.

**Commit** (`Copied::commit`): сначала всё, что может ждать внешнего
(чтение текущего bootstrap, запись и fsync временного файла), затем без
ожиданий — доказательство: путь цели ведёт в открытый каталог, цепочка
цели, текущей папки и папки настроек не изменилась, `photo-cleanup.db` и
`thumbs` в цели — объекты полезной нагрузки и через открытый каталог, и по
пути, у базы та же generation; только после этого rename временного файла
поверх bootstrap. Иначе — `RelocateError::Displaced`: где наша проверенная
копия сейчас (`F_GETPATH`/`/proc/self/fd`) или что место неизвестно, и что
лежащее по пути не является проверенной копией; bootstrap не меняется,
временный файл удалён. `Incomplete` («копия готова и проверена… выберите
как существующую») возвращается только сразу после успешного
доказательства.

**Привязка и запуск** (`bootstrap.rs`, `binding.rs`, `resolve.rs`, `shell.rs`):
bootstrap формата 2 хранит UUID/fsid тома, inode каталога, базы и `thumbs`
и generation; путь — только адрес. `resolve` и затем `prepare` **до**
пробы записи, SQLite, `-wal`/`-shm` и миграций: допуск пути каталога,
открытие каталога, базы (`O_RDONLY|O_NOFOLLOW|O_NONBLOCK`, без создания) и
`thumbs` относительно него, сравнение тома, inode и generation, затем
защищённость самих объектов (ниже). Несовпадение —
`StartupError::DataUnavailable { why: NotTheBoundCopy(причина), previous }`
(экран ошибки с «Вернуться к прежней», если она есть); ничего не создаётся,
не открывается SQLite и не меняется; пустая база вместо привязанной не
создаётся; прежний выбор автоматически не выбирается. `confirm_started`
сохраняет привязку; `previous` хранит привязку прежнего выбора.

**Привязка управляет записями сервера, а не только стартом** (review
el-146id, B1/B2). Раньше `Prepared.guard` проверялся *после* того, как
`pc_api::start` открыл базу по пути: подменённый после `prepare` пустой
файл SQLite успевала вырастить с 0 до 266240 байт (тот же inode), а
текст ошибки утверждал «ничего не открыто и не изменено»; работающий
сервер по обычному `POST /api/reset` с подтверждением `RESET` удалял
содержимое подложенной вместо `thumbs` папки. Теперь guard — это
`pc_core::storage::StorageBinding`, и его передают самому серверу
(`ServerConfig.binding`, `Prepared::storage_binding()`); оболочка при
старте и `recover` после неудачной смены папки запускают сервер с ним.
Вопрос задаётся **перед** каждой записью, а не после:

- `check_database` — перед каждым открытием базы (`AppState::open` при
  старте, соединение каждой задачи, её прогресс и итог) и перед каждым
  writer lock (задачи, ручные изменения, сброс, отметка прерванных задач
  при старте): повторный обход цепочки каталогов от `/`; путь к базе,
  разрешённый системой так же, как его разрешит SQLite, ведёт к
  удерживаемому файлу; этот файл — обычный, с одним именем (`nlink = 1`),
  принадлежит пользователю, без записи для group/other и без ACL,
  разрешающего другим запись, удаление, xattr, права или владельца; на нём
  generation этой копии. Рядом `-wal`, `-shm`, `-journal` — нет или такие
  же защищённые файлы; `.writer-lock` — нет или обычный собственный файл с
  одним именем. SQLite и замок пишут в них по имени: ссылка передала бы
  запись чужому файлу.
- Открытие базы — `pc_db::Db::open_bound`: проверка; SQLite открывает путь
  `READ_WRITE` **без** `CREATE` и с `NOFOLLOW` (открытие ничего не читает и
  не пишет); SQLite сама отвечает, тот ли файл она держит, что сейчас по
  пути (`SQLITE_FCNTL_HAS_MOVED`), и проверка повторяется; только потом
  `journal_mode=WAL`, pragma и миграции. Для того чтобы SQLite держала
  другой объект, имя должно смениться на другой файл и обратно между этими
  вызовами; в допущенном пространстве имён это может сделать только сам
  пользователь (вне модели угроз). Замена в любой другой момент ловится до
  первой записи. Отказ закрывает соединение, ничего не записав.
- `check_thumbnails` — перед каждой записью миниатюры (`ThumbStore::put`,
  `put_at`) и очисткой (`ThumbStore::clear`): путь `thumbs` ведёт к
  удерживаемой папке, она принадлежит пользователю, без записи для
  group/other, ACL и том проходят те же проверки, что каталоги цепочки
  (`namespace::check_own_folder`). Проверяется только сама папка: цепочка
  выше повторно обходится перед каждым открытием базы и writer lock, через
  которые проходит любая задача и изменение. Сброс сначала спрашивает кэш,
  потом стирает индекс: отказ не оставляет полусброшенного индекса.
- Текст отказа честный: «`<путь>`: не та копия, которую программа
  проверила и выбрала (`<причина>`); туда ничего не записано», для
  подменённого объекта — где проверенный объект сейчас (`F_GETPATH` /
  `/proc/self/fd`) или что система этого не сообщает. Поиска по диску и
  удаления незнакомого нет. Для старта — `DataUnavailable/NotTheBoundCopy`
  с `previous`, для запроса — ошибка ответа; положительный сброс, повторный
  старт и `recover` на настоящих объектах работают как раньше.

Защищённость объектов проверяется отдельно от каталога: папка `thumbs` с
`chmod 777` или база `0666` внутри обычной `0755`-папки больше не
принимаются при старте (`resolve`): identity и generation целы, но
изменить их может любой.

**Файлы, в которые перенос пишет по имени** (review el-146id, B3). Допуск
каталогов не делал безопасными уже существующие *записи* в них. Два
случая, воспроизведённые без гонки: символическая ссылка вместо
`photo-cleanup.db.writer-lock` в текущей папке — замок открывался по ссылке
и записывал заметку в чужой файл; жёсткая или символическая ссылка
`desktop.json.tmp` в папке настроек — `File::create` записывал в чужой
inode 386 байт bootstrap. Теперь:

- в preview и повторно в `copy_data` **до** writer lock, резерваций,
  staging и bootstrap проверяются база, `-wal`, `-shm`, `-journal` и
  `.writer-lock` текущей папки (`namespace::check_file_at`, только чтение:
  `fstatat(AT_SYMLINK_NOFOLLOW)`, для содержимого — ACL через
  `O_RDONLY|O_NOFOLLOW|O_NONBLOCK`). Отказ — `Blocker::UnsafeFile { path,
  reason }` (`kind: "unsafe_file"`): «перенос записывает в `<путь>`, но
  `<это символическая ссылка… / у файла N имени… / принадлежит…/ права…>`.
  Файл не тронут; уберите или замените его и повторите». Кнопка «Использовать
  существующую» при нём не показывается;
- сам `pc_core::lock::take_writer` открывает замок с `O_NOFOLLOW` и до
  записи заметки отказывает, если это не обычный файл или у него больше
  одного имени: ни ссылка, ни второе имя чужого файла не обрезаются;
- bootstrap пишется через **новое** имя `desktop.json.<pid>-<время>-<n>.tmp`,
  созданное эксклюзивно (`create_new`, 0600, ссылку не открывает и не
  проходит); занятое имя пропускается, до 16 попыток. Прежний
  `desktop.json.tmp` и любые чужие записи не открываются, не
  обрезаются и не удаляются. Свой временный файл при ошибке удаляется,
  только пока его имя ведёт к тому же inode (иначе остаётся). Сам
  bootstrap заменяется `rename` — ссылка на месте `desktop.json`
  заменяется как имя, через неё ничего не пишется.

#### Публикация через открытые каталоги (review el-2ztq8)

До исправления VACUUM INTO, копирование миниатюр, их `rename_no_replace` и
публикация базы шли по путям через имена в общем целевом каталоге. Review
el-2ztq8 (B1/P1, нативный macOS, 0/1 повторяемо): после проверенной копии
базы весь зарегистрированный `photo-cleanup.db.partial/` переименовывался
в `saved-db-staging`, а на его имя ставился заранее подготовленный чужой
каталог 0777 с `photo-cleanup.db` (не SQLite, xattr). Публикация по пути
переносила **чужой** файл в `photo-cleanup.db`, очистка замечала подмену
слишком поздно, а `Incomplete` сообщал «копия … готова и проверена» и
предлагал «использовать существующую папку»; настоящая копия оставалась в
`saved-db-staging` без упоминания. Повторять «проверить путь, затем
переименовать путь» нельзя — это то же окно.

Теперь всё, что решает, **что** публикуется, привязано к открытым handle:

- целевой каталог открывается один раз до создания staging (`TargetDir`;
  путь пользователя, ссылки на пути разыменовываются как везде). Staging
  принимается, только если запись `photo-cleanup.db.partial` в **этом
  открытом каталоге** — тот же объект, что зарегистрирован
  (`a_staging_folder_outside_the_opened_target_is_refused`);
- миниатюры копируются в `thumbs/` **внутри** приватного staging. Unix:
  `mkdirat`/`openat(O_CREAT|O_EXCL|O_NOFOLLOW)` относительно дескриптора
  staging, подсчёт числа и байт — через дескрипторы (`at::copy_tree`,
  `at::tree_size`); переименование имён в цели на копию не влияет;
- база: SQLite принимает только путь, поэтому файл принимается, только если
  запись `photo-cleanup.db` открытого staging — тот же объект, что по пути,
  сразу после `VACUUM INTO` и ещё раз после проверки копии. Иначе
  `RelocateError::Copy` называет файл, записанный по подменённому имени
  (он остаётся на месте), и «Nothing was published»;
- перед публикацией путь цели должен вести в открытый каталог, иначе ничего
  не публикуется (ошибка называет путь и текущее место открытого каталога);
- публикация переносит `thumbs` и затем `photo-cleanup.db` **из открытого
  staging в открытый целевой каталог** без замены: Unix — `renameatx_np
  (RENAME_EXCL)` / `renameat2(RENAME_NOREPLACE)` между дескрипторами, запись
  до и после сверяется по dev/ino; Windows — `SetFileInformationByHandle
  (FileRenameInfo, ReplaceIfExists = 0, RootDirectory = handle цели)` через
  handle самого объекта, найденного перечислением handle staging и открытого
  по file ID. То, что к этому моменту лежит по имени staging, не читается,
  не переносится и не удаляется; внутрь приватного staging другая учётная
  запись ничего положить не может, поэтому переносится только наше;
- `Copied::commit` сверяет путь цели с открытым каталогом до `Incomplete`
  и ещё раз непосредственно перед записью bootstrap. Если путь ведёт в
  другое место — новая ошибка `RelocateError::Displaced { target, reason }`:
  «проверенная копия опубликована в папке, открытой как …, но папку …
  переименовал или подменил кто-то другой; открытая папка теперь …; то, что
  лежит по пути …, не является проверенной копией». Bootstrap не
  меняется. Поэтому `Incomplete` («копия в … готова и проверена») теперь
  возвращается только когда путь проверенно ведёт к опубликованной
  проверенной копии;
- очистка больше не считает «имени нет» успехом, если наш объект жив
  (`not_at_name`: Unix — `nlink > 0` через дескриптор, Windows —
  `GetFinalPathNameByHandleW`): ошибка называет, куда унесли наш staging или
  резервацию, и объект остаётся там. Для заменённого staging сообщение
  дополнительно называет текущее место нашего каталога (`F_GETPATH` /
  `/proc/self/fd` / `GetFinalPathNameByHandleW`).

Результат для сценария B1 (`publication_tests::a_staging_folder_replaced_
after_verification_is_not_published`, подмена на `Step::Verified` и на
`Step::Publish`, цель с `chmod +a everyone … delete_child,add_subdirectory`):
чужой каталог по имени staging сохраняется целиком — inode, mode, uid/gid,
mtime (до нс), байты и xattr каждого файла; опубликованы наша проверенная
база и наши миниатюры; `Incomplete` называет чужую запись по имени
`.partial` («replaced … by someone else») и пустой наш staging в
`saved-db-staging`; bootstrap не меняется; «использовать существующую»
после этого работает. Подмена на `Step::Registered` (до `VACUUM INTO`):
с чужим `photo-cleanup.db` SQLite отказывает («file is not a database»),
без него файл SQLite попадает в чужой каталог, дескриптор это показывает —
в обоих случаях ничего не опубликовано, чужие записи неизменны, ошибка
называет пути. Цель переименована и на путь поставлен чужой каталог:
до проверки пути — ничего не опубликовано ни там, ни там, наш staging и
резервации названы в перенесённом каталоге; после проверки — копия
опубликована только в открытый (перенесённый) каталог, `Displaced`,
чужой каталог по пути неизменен, bootstrap не меняется.

Mutation (каждая по отдельности): публикация базы по пути → 2 FAIL; без
проверки пути цели перед публикацией → 1 FAIL; без проверки в `commit` →
1 FAIL; «имени нет = успех» → 1 FAIL; без сверки файла SQLite с
дескриптором staging → 1 FAIL; без проверки staging в открытой цели →
1 FAIL.

Прежние «пределы» этого раздела (утечка копии базы в чужой каталог,
проверка по пути с подменой «туда и обратно», окно между последней сверкой
и записью bootstrap, копирование миниатюр на Windows по путям) закрыты
разделом «Защищённое пространство имён и привязка копии»: в
непроверяемом пространстве имён перенос не начинается, в допущенном другие
учётные записи не могут переименовать ни один компонент, а копия,
bootstrap и запуск привязаны к объектам. Процесс того же UID и root/admin
— по-прежнему вне модели. Windows-копирование отклоняется до записи;
описанные выше handle-операции Windows (публикация, удаление) остаются в
коде для регистрации/очистки, но нативно **не запускались**.

Где запускалось (исправление el-2ztq8): macOS arm64, uid 501 — `cargo test
--workspace --locked`, `cargo fmt --all --check`, `cargo clippy
--all-targets -D warnings` (итоги — в отчёте задачи на итоговом SHA);
mutation выше — на macOS. Linux Docker `rust:1.98-slim-bookworm`, uid 1000
— `cargo test -p pc-desktop --lib` (включая `publication_tests`; ACL-часть
macOS там заменена mode 0777). Другой UID не запускался: применимость к
другим учётным записям — из прав общего родителя, как в review.

#### Очистка временных файлов: условия и пределы гарантии

Модель угроз (решение Director по el-3p7c): защищаются заранее существующие
и чужие записи от гонок с процессами **других пользователей ОС** и от
обычной работы приложения. Намеренно враждебный процесс с тем же
эффективным UID, root/admin или иной полной властью над файлами
пользователя — вне модели: он и так может менять эти файлы напрямую. Доступ
«только владелец» (mode 0700 без extended ACL на macOS, защищённый DACL на
Windows) изолирует только от других пользователей и **не** является
границей против процесса того же пользователя.

Что доказано (детерминированные вставки в окно гонки для каталога, файла,
пустого файла и symlink, всех трёх sidecars; macOS и Linux): если исходный
handle действительно указывает на объект этого переноса, то никакая
другая запись не удаляется — ни оказавшаяся по публичному имени
`.partial`/`thumbs`/sidecar в момент переноса в сторону (она
возвращается на место или остаётся в приватном каталоге с ошибкой), ни
чужое дерево, поставленное под имя приватного каталога или под имя
родителя после любой проверки (el-5null; очистка возвращает ошибку с
путями). Гарантия условна:

- handle должен быть захвачен правильно — см. «Регистрация staging-каталога»
  ниже (el-2xri);
- приватный каталог и наш staging не меняются процессом с полномочиями
  пользователя (см. модель угроз); имена в родителе и выше может менять
  кто угодно — операции к ним не привязаны.

Известные пределы, закреплённые тестами: (a) чужая запись на мгновение
отсутствует по своему имени, пока лежит в приватном каталоге; (b) то, что
перемещено внутрь приватного каталога или нашего staging после финальной
проверки, считается нашим (`the_private_folder_is_trusted_after_the_proof`);
(c) байты, записанные через дескриптор на нашей пустой резервации (его
можно открыть по публичному имени до переноса), уходят вместе с ней;
(d) между проверкой «по имени приватного каталога всё ещё он» и `rmdir`
остаётся окно: **пустой** каталог, переименованный на это имя, будет
удалён (`rmdir` содержимого не удаляет; то же для rmdir целевого
каталога, созданного переносом). Частота гонок в production не
измерялась.

Ошибки cleanup не глотаются. При неудачном переносе `copy_data` возвращает
`RelocateError::Cleanup { error, left }` — исходную ошибку и по строке на
каждый остаток (заменённая запись, не удалённый приватный каталог
`.photo-cleanup-removing-*`, отказ прав). Если копия уже опубликована и
проверена, но её пустой staging убрать не удалось, `Copied::staging_left`
хранит путь и причину, а `Copied::commit` — и `move_data`, который вызывает
оболочка, — возвращает `RelocateError::Incomplete { copy, left }`:
bootstrap **не** переписывается, перезапуска нет, оболочка поднимает
прежний сервер и показывает текст ошибки с путём копии, путём остатка и
причиной. Копия не откатывается: после ручного удаления остатка её можно
выбрать действием «использовать существующую папку». `Incomplete` возвращается
только после сверки пути цели с открытым каталогом, в который перенесена
проверенная копия; если путь ведёт в другое место — `Displaced` без
предложения переключиться (см. «Публикация через открытые каталоги»). Остаток может лежать
по исходному имени `photo-cleanup.db.partial/` (тогда следующий перенос в
ту же папку блокируется как `LeftoverPartial`) или внутри
`.photo-cleanup-removing-*/` — такие имена `LeftoverPartial` не
проверяет. Регрессии через фактический путь
оболочки: `relocate::caller_tests` (реальный `PermissionDenied`, оба места
отказа; без исправления 3 из 3 падают). Нативный Tauri-перезапуск не
запускался. `Drop` остаётся только страховкой на панику и сообщить не
может. Windows: удаление через handle (выше); на Windows не запускалось
(машины нет, см. el-56k). Linux: Docker `rust:1.98-slim-bookworm`, uid
1000, `cargo test -p pc-desktop --lib` 51/51 (включая
`aside_namespace_tests`).

Проверенная копия при поздней ошибке остаётся. После публикации пустые
final sidecars **не удаляются переносом**: они резервируют имена через commit
и перезапуск до первого открытия SQLite. Если read-only инспекция новой БД
уже убрала пустой sidecar, commit захватывает освободившееся имя снова через
`create_new`. SQLite открывает такой набор без транзакций из sidecars;
проверены два последовательных запуска через `prepare` и `Db::open`.
Сбой процесса до публикации может оставить пустые резервации/staging —
следующий перенос отказывает, не объявляя эти файлы своими.
Замки остаются advisory: захват имён защищает от конкурирующего создания,
но не запрещает стороннему процессу намеренно перезаписывать уже занятые
файлы без соблюдения writer lock.
Исходник не удаляется автоматически ни на одном пути.

#### Регистрация staging-каталога (el-2xri)

`mkdir` не возвращает дескриптор, поэтому идентичность нового
`photo-cleanup.db.partial/` (до el-2ztq8 — и `thumbs.partial/`) берётся открытием имени
уже после создания. До исправления между этими вызовами можно было
переименовать наш пустой каталог и поставить на имя чужой с
`foreign-photo.jpg`: он регистрировался как наш и затем удалялся вместе с
содержимым (воспроизведено review el-3xm8 на main, 1/1).

**Создание** (`create_private_dir`, `relocate.rs`) — доступ «только этот
пользователь» задаёт сам создающий вызов, не последующий chmod/SetACL.
Тот же вызов создаёт и приватный каталог очистки `.photo-cleanup-removing-*` (только Unix; Windows удаляет через handle без него):

- Linux и прочие Unix: `mkdir` с mode 0700 (umask может только убрать
  биты). POSIX default ACL родителя наследуется, но маска ACL берётся из
  group-битов режима, т. е. 0: именованные записи ничего не дают. Это
  семантика POSIX.1e; тестом с `setfacl` не проверялось (в образе нет
  пакета `acl`);
- macOS: extended ACL (`chmod +a`) действует **поверх** режима, и plain
  `mkdir` 0700 в каталоге с наследуемой записью `everyone allow add_file,
  delete_child,… directory_inherit` получал её — каталог был открыт всем,
  а проверка режима его принимала (review el-1wh7b, 0/1). Теперь
  `mkdirx_np` с mode 0700 и пустым ACL с флагом `ACL_FLAG_NO_INHERIT`:
  ничего не наследуется (проверено тестом на таком родителе);
- Windows: `CreateDirectoryW` с security descriptor
  `O:<SID>D:P(A;OICI;FA;;;<SID>)` — владелец текущий пользователь,
  защищённый (не наследующий от родителя) DACL с единственной записью:
  полный доступ этому пользователю, наследуется содержимым.

**Проверка** (`open_created_dir`) — ни одна платформа не доверяет
созданию, запись по имени проверяется:

- Unix: имя открывается с `O_DIRECTORY | O_NOFOLLOW` (symlink и файл не
  открываются); через **этот же дескриптор** требуется каталог, владелец —
  эффективный UID, нет битов group/other, на macOS — нет ни одной записи
  extended ACL (`acl_get_fd_np`; `ENOTSUP` файловой системы без ACL
  считается «нет записей», любая другая ошибка — отказ), каталог пуст
  (`fdopendir` по дубликату дескриптора; ошибка чтения — отказ);
- Windows: открытие с `FILE_FLAG_OPEN_REPARSE_POINT`, через handle: каталог
  без reparse point (junction/symlink отвергаются), владелец — SID
  текущего пользователя, DACL защищён от наследования, allow-записи только
  для этого SID (deny-записи допустимы, записи неизвестных типов — отказ),
  каталог пуст (`GetFileInformationByHandleEx`, ошибка — отказ).

При несоответствии staging-каталога ничего не регистрируется и **ничего не
удаляется**: ни то, что лежит по имени, ни наш каталог, где бы он ни
оказался. Перенос завершается `RelocateError::Copy` с путём и причиной
(«…cannot be proven to be it (it has an access list…); nothing was
removed…»), bootstrap и исходные данные не меняются; остаток по имени
`.partial` блокирует следующий перенос как `LeftoverPartial`. При
несоответствии приватного каталога очистки (Unix, `Step::AsideCreated`)
очистка останавливается **до** переноса: staging остаётся по своему имени
с содержимым, приватный каталог — на месте, ошибка называет оба пути
(`RelocateError::Cleanup`/`Incomplete` как у прочих отказов очистки).

Что это даёт в модели угроз: каталог, подставленный **другим
пользователем ОС**, отвергается по владельцу — создать каталог с нашим
владельцем может только root (Unix) или учётная запись с привилегиями
restore/take ownership (Windows, уровень администратора). Каталог с
доступом для других (биты group/other, ACL на macOS, наследуемый или
чужой allow в DACL на Windows), непустой каталог, symlink, junction и файл
отвергаются независимо от владельца. Созданные нами staging и приватный
каталог закрыты для других учётных записей с момента создания, в том
числе под родителем с наследуемыми разрешениями. Чего это **не** даёт:
пустой приватный каталог того же пользователя (без ACL / с тем же
защищённым DACL) неотличим от нашего; он будет зарегистрирован и при
очистке удалён вместе с тем, что положил туда перенос (закреплено тестом
`metadata_decides_for_empty_swaps_and_the_same_user_limit_is_pinned`;
соседние записи не трогаются). Это случай процесса того же UID/учётной
записи — вне модели, как и root/admin. Если наш каталог утащили до
открытия, он остаётся там, куда его перенесли; найти его перенос не может.
Побочный эффект: опубликованный `thumbs/` и каталог базы после переноса
остаются доступны только владельцу (на Unix так было и раньше).

#### Том цели: владельцы и ACL (решение Director A по review el-6d0i0)

Приватность staging и каталога очистки держится на томе: он должен
хранить и применять владельцев файлов и принимать ACL, с которым каталоги
создаются. Review el-6d0i0 нашёл, что `mkdirx_np` с ACL на FAT32 даёт
`EINVAL`: перенос, работавший на main, падал без пути и причины, а
неубранные sidecar-резервации блокировали повтор. Простой откат к
`mkdir 0700` приватности не доказывает: на томе с `noowners`
(`MNT_IGNORE_OWNERSHIP`) любой пользователь видит любую запись своей,
`drwx------`, и проверка владельца бессмысленна. Решение A: такой том
**намеренно не поддерживается** как цель копирования.

Что считается неподдерживаемым (`relocate/volume.rs`, читается у тома, а
не выводится из типа ФС):

- macOS: том смонтирован с `MNT_IGNORE_OWNERSHIP` (FAT16/FAT32/exFAT
  всегда; внешние HFS+/APFS — по умолчанию, пока в Finder не снята
  галочка «Игнорировать владельцев на этом томе»), либо
  `pathconf(_PC_EXTENDED_SECURITY_NP) != 1` (нет ACL), либо это не
  локальный (`MNT_LOCAL`) `apfs`/`hfs` (сетевые тома, FUSE, NTFS — отказ,
  el-2xri lifecycle). Системный APFS и
  внешний HFS+/APFS с учётом владельцев поддерживаются;
- Windows: у тома нет `FILE_PERSISTENT_ACLS` (FAT32, exFAT) —
  `GetVolumePathNameW` + `GetVolumeInformationW`;
- Linux (не целевая настольная платформа, библиотека там тестируется):
  принимаются только ФС из списка по `statfs.f_type`, хранящие POSIX
  владельцев и режимы (ext2/3/4, xfs, btrfs, tmpfs, ramfs, overlayfs, zfs,
  f2fs, bcachefs, jfs, reiserfs, nilfs); vfat, exfat, fuse, cifs, nfs и
  неизвестные — отказ;
- прочие платформы — отказ (свойства тома неизвестны).

Где проверяется:

1. **Preview** (`preview_move`): для существующей цели — её том, для
   несуществующей — том ближайшего существующего предка (там её создаст
   перенос после допуска пространства имён, каталог за каталогом). Блокер `Blocker::NoPrivateFolders { path, reason }`
   (`kind: "no_private_folders"`): «`<цель>` cannot hold the move's
   temporary folders private to this user: volume `<точка монтирования>`
   (`<ФС>`) is mounted with ownership ignored (noowners)… Choose a folder on
   another volume». Ошибка чтения свойств тома — тоже отказ с путём.
2. **Backend до первой записи**: `copy_data` повторяет preview до writer
   lock, до `create_dir_all`, до резерваций sidecars и staging, т. е. на
   неподдерживаемом томе не создаётся ничего — ни каталога цели, ни
   `.writer-lock`, ни резерваций, ни `.partial`; повтор встречает то же
   состояние. Под writer lock цели preview повторяется ещё раз.
3. **Через дескриптор созданного каталога**: `fresh_private_dir`
   (staging и `.photo-cleanup-removing-*`) и Windows `open_created_dir`
   спрашивают свойства тома у открытого дескриптора/handle
   (`fstatfs`/`fpathconf`, `GetVolumeInformationByHandleW`). Если том
   сменился после preview или вызывающий обошёл preview, созданный нами
   каталог не регистрируется, **не удаляется**, ошибка называет путь и
   причину (как прочие отказы регистрации). Ошибка самого создания
   (`mkdirx_np` `EINVAL` на FAT) теперь тоже называет путь.

Переключение на уже существующую базу (`switch_to_existing`) временных
папок не создаёт и на таких томах остаётся доступным; UI показывает эту
кнопку и при блокере `no_private_folders`. Отказ от fallback означает:
данные приложения нельзя перенести копированием на SD-карту/флешку с
FAT/exFAT или на внешний диск с игнорированием владельцев — это
намеренное ограничение совместимости; путь — включить учёт владельцев или
выбрать другой том. Отдельная проблема exFAT (`RENAME_EXCL` →
`ENOTSUP`) — см. «Том цели: переименование без замены (el-21zyg)»;
семантика no-overwrite не ослаблялась.

Регрессии на настоящих томах (`relocate::volume_tests`, macOS,
одноразовые образы `hdiutil create/attach`, без root, данные — tempfile):

- `volumes_that_ignore_owners_are_refused_before_anything_is_written`:
  MS-DOS (FAT16), MS-DOS FAT32 (даже с `-owners on`), ExFAT, HFS+ и APFS
  подключённые по умолчанию (noowners); существующая папка с
  `foreign-photo.jpg` и несуществующая `new/data`; по две попытки: preview
  и `move_data` дают один и тот же `NoPrivateFolders` с путём цели и
  `<точка монтирования> (<ФС>)`, дерево тома байт в байт неизменно
  (нет `.writer-lock`, резерваций, `.partial`, каталога `new`), bootstrap,
  выбранная папка и исходная база не меняются;
- `volumes_that_record_owners_take_the_move`: HFS+ и APFS с `-owners on` —
  перенос проходит, без остатков staging и приватных каталогов;
- `a_folder_made_on_a_volume_without_owners_is_not_registered`:
  `OwnedDirectory::create` на noowners APFS — отказ с путём и «noowners»,
  каталог оставлен на месте; на FAT — отказ создания с путём, ничего не
  создано.
- `relocate::volume::tests`: классификация недостающих свойств с именем
  тома; несуществующая цель проверяется по предку и не создаётся; Linux —
  список `f_type` (vfat/exfat/fuse/cifs/nfs — отказ).

Mutation: без блокера в preview → `volumes_that_ignore…` FAIL; без
проверки тома через дескриптор → `a_folder_made…` FAIL. Вызовы `hdiutil`
в тестах сериализованы: параллельные `hdiutil create` зависали.

Где запускалось (решение A): macOS arm64 — `cargo test --workspace
--locked` 450/0/0, fmt и clippy `-D warnings` PASS, web `npm run build`,
`check:unused`, `npm test` 82/82; Linux Docker `rust:1.98-slim-bookworm`,
uid 1000 — `cargo test -p pc-desktop --lib` 54/54 (overlayfs принят;
настоящий vfat в контейнере без привилегий не монтировался). Windows —
только type-check модуля `volume.rs` в scratch-крейте (`cargo clippy

#### Том цели: переименование без замены (el-21zyg)

Сам вызов (`rename_no_replace_at` / `rename_no_replace`) и запрос
`VOL_CAP_INT_RENAME_EXCL` (`exclusive_rename`) с el-usdqi живут в
`pc_core::disk` и общие с переносами `pc-apply` (apply, откат, organize):
`relocate.rs` `at::rename_no_replace` и `relocate/volume.rs`
`exclusive_rename` только делегируют туда (тестовая эмуляция `at::fault`
осталась в `pc-desktop`). Поведение переноса данных не менялось.

Для данных архива действует то же правило без переключателя: том без
rename-без-замены отказывает закрыто, без fallback и без пробной записи
(DESIGN.md §11.2). На Unraid прямые диски `/mnt/diskN` (xfs/btrfs)
ожидаемо поддерживаются; `/mnt/user` (shfs), NFS, CIFS/SMB и FUSE могут
отказывать каждому переносу. На настоящем NAS это не проверялось. Перенос
данных приложения (relocation) с этим не связан: его папка выбирается на
машине с приложением.

Карантин, откат и раскладка фотографий в окне приложения идут через
`pc-api` в `pc-apply` и подчиняются его правилам (DESIGN.md §11.2,
el-usdqi): файл признаётся своим только по доказательству, записанному до
переноса; итог остановленного прогона — тот же, что в командной строке;
заметка о раскладке карантина и пустые каталоги удаляются только через
удерживаемый каталог и только пока это тот же объект, иначе остаются и
называются. **На Windows** перенос, откат, сверка и запись заметки о
раскладке отказываются с причиной до проверки на настоящей системе — в
приложении для Windows эти действия недоступны. Перенос данных приложения
(relocation) этим не затронут: у него свой протокол, описанный здесь.

Экран «Превью и кэши» в окне — тот же веб и тот же `pc-apply`: ничего из
Lightroom и библиотек Фото не переносится, а системный мусор — только если
байты целиком подтверждают имя и у спутника нет его файла (DESIGN.md §10.0,
el-126jk). Причина отказа показывается у
строки и в предпросмотре теми же словами, что печатает `derived clean`.

Всё, что перенос двигает, двигается одним вызовом — rename без замены
(`renameatx_np(RENAME_EXCL)` на macOS, `renameat2(RENAME_NOREPLACE)` на
Linux): публикация `thumbs/` и `photo-cleanup.db` из staging и перенос
собственных остатков в `.photo-cleanup-removing-*` при очистке. Замены у
этого вызова нет: обычный `rename` может заменить чужую запись, а
«проверить имя, потом переименовать/удалить» этого не исключает. Поэтому
том, где вызова нет, — отказ, а не fallback; поддержка exFAT **не**
добавлялась.

Наблюдение на нативных образах (macOS 27 arm64, `hdiutil create -fs …`,
синтетические файлы, main 5a83474):

| ФС (attach) | `RENAME_EXCL` | `VOL_CAP_INT_RENAME_EXCL` | noowners |
|---|---|---|---|
| ExFAT (по умолчанию и `-owners on`) | `ENOTSUP` (45) | valid, **нет** | да, всегда |
| MS-DOS FAT32 `-owners on` | работает | valid, **нет** | да, всегда |
| HFS+ по умолчанию / `-owners on` | работает | есть | да / нет |
| APFS `-owners on`, системный APFS | работает | есть | нет |

На main 5a83474 exFAT как цель уже отклонялся до первой записи (noowners,
решение A): `move_data` дважды — тот же `NoPrivateFolders`, том байт в
байт неизменен. Путь `ENOTSUP` через настоящий exFAT поэтому не
достижим; он воспроизводился эмуляцией (`at::fault`, только в тестах:
`rename_no_replace` на этом потоке отвечает `ENOTSUP`) на томе, прошедшем
допуск. Результат на main: публикация `thumbs` падала с `ENOTSUP`, очистка
тем же вызовом не могла унести свои записи, в цели оставались
`photo-cleanup.db.partial/` (с копией внутри), пустые резервации
`photo-cleanup.db-wal`/`-shm`/`-journal` и `.writer-lock`; ошибка их
называла, но повтор отклонялся из-за них же (`SidecarExists` ×3 и
`LeftoverPartial`).

Что теперь (`relocate/volume.rs` `check_exclusive_rename`,
`relocate.rs` `probe_exclusive_rename`):

1. **Preview, только чтение**: macOS спрашивает у тома
   `getattrlist(ATTR_VOL_CAPABILITIES)`; если `VOL_CAP_INT_RENAME_EXCL` не
   объявлен действительным и установленным — блокер
   `Blocker::NoExclusiveRename { path, reason }` (`kind:
   "no_exclusive_rename"`): «`<цель>` cannot receive the data: its volume
   cannot rename without replacing (volume `<точка монтирования>` (exfat)
   cannot rename without replacing what is at the new name (RENAME_EXCL))…
   Choose a folder on another volume». На exFAT он стоит рядом с
   `NoPrivateFolders`; FAT32 по признаку тоже его получает, хотя вызов там
   срабатывает (том и так отклонён за noowners). Linux такого запроса не
   имеет, Windows копирование не выполняет; проба шага 2 там — пустая
   заглушка (`probe_exclusive_rename` для `cfg(not(unix))`), до неё дело не доходит.
2. **Проба до первой записи, которую пришлось бы убирать**: после допуска
   цели и создания её недостающих каталогов, но до `.writer-lock`,
   резерваций и staging, в цели создаётся свежий приватный
   `.photo-cleanup-removing-*` (`Aside::create`), в нём эксклюзивно —
   пустой файл `rename-probe`, и он переименовывается без замены внутри
   того же каталога. Файл удаляется только через дескриптор приватного
   каталога и только пока запись — тот самый файл (`dev`/`ino`), затем
   каталог убирается как обычно (`Aside::remove`). Ошибка вызова → тот же
   блокер `NoExclusiveRename` с текстом ошибки ОС (`Operation not
   supported (os error 45)`), созданные переносом каталоги цели удаляются
   (`rmdir` пустых), в цели не остаётся ничего; повтор встречает то же
   состояние и тот же ответ. Остаток самой пробы не удаляется по имени, а
   называется в `RelocateError::Cleanup`.
3. **Если вызов перестал работать уже после пробы** (том сменился, сбой):
   публикация отменяется; если очистка своим вызовом может унести записи —
   они убираются как всегда, и повтор после восстановления вызова проходит
   как первая попытка. Если не может — ничего не удаляется по имени и не
   переименовывается с заменой: `.partial` с копией и резервации остаются,
   каждая названа в ошибке (`<путь> was left in place: Operation not
   supported`), повтор отклоняется блокерами `SidecarExists`/
   `LeftoverPartial` с путями и ничего не меняет (fail closed).

UI: `no_exclusive_rename`, как `no_private_folders`, запрещает копирование,
но не переключение на уже лежащую там базу. `switch_to_existing` ничего на
томе не публикует и не переименовывает, но не «только bootstrap»: под
writer lock целевой базы он создаёт/открывает `photo-cleanup.db.writer-lock`
(на ExFAT macOS при этом может появиться AppleDouble-спутник `._*`) и
проверяет базу (`looks_like_ours`), затем пишет bootstrap
(`relocate.rs`, `switch_to_existing`).

Регрессии: `relocate::rename_tests` (Unix) —
`a_volume_that_cannot_rename_without_replacing_is_refused_without_leftovers`
(все переименования `ENOTSUP`; существующая папка с чужим файлом и
несуществующая `new/data`; по две попытки, одинаковый
`NoExclusiveRename` с путём, листинг цели неизменен, `new` не создан,

выше), `an_unsupported_rename_at_publication_is_undone_and_a_retry_completes`
(`ENOTSUP` только на публикации `thumbs`, затем `photo-cleanup.db`: ничего
не осталось, повтор проходит),
`leftovers_that_cannot_be_moved_aside_are_kept_and_named_never_removed_by_name`;
`relocate::volume_tests::exfat_cannot_rename_without_replacing_and_is_refused_for_it`
(нативный ExFAT: `ENOTSUP` 45 у `pc_core::disk::rename_no_replace`,
блокер в preview и в `move_data` дважды, том неизменен; APFS/HFS+
`-owners on` — признак есть).

Не покрыто: карантин фотографий (`pc-apply`) этим вызовом не пользуется и
здесь не менялся. Windows/Linux нативно в рамках el-21zyg не запускались
(Linux: проба шага 2 — единственная проверка, признака тома нет).

Где запускалось (исправление el-5null): macOS — `cargo test --workspace`

## Окно и безопасность

Реализовано в el-2a4 (`crates/pc-desktop/src/shell.rs`, правила — в
`src/window.rs`):

- Порядок запуска в `setup()`: `resolve` → `prepare` → `pc_api::start` на
  `127.0.0.1:0` (возвращается после готовности: миграции, bind) →
  `confirm_started` → окно `main` с `WebviewUrl::External("http://127.0.0.1:<порт>/")`.
  Окно не создаётся, пока не решено, что в нём показывать, поэтому
  интерфейс не гоняется со стартом сервера. Название «Photo Cleanup»,
  начальный размер 1280×820, минимальный 960×600, по центру.
- Любая ошибка на этом пути — страница ошибки из ресурсов бинаря
  (`ui/error.html`) в том же окне: сообщение на обоих языках (язык из
  настроек ещё не прочитан — он в той базе, что не открылась; первым идёт
  язык системы), подсказка, что фотографии не тронуты, и подробности
  (`StartupError` c тегом `kind`). Отчёт передаётся
  `initialization_script`, строки вставляются через `textContent`. Тот же
  текст печатается в stderr — для запуска из терминала и smoke-тестов. На
  Windows приложение собирается как GUI subsystem (`windows_subsystem =
  "windows"` безусловно), консоли нет. Если окно не создаётся вовсе
  (например, нет WebView2), показать ошибку нечем — только stderr и код 1;
  понятное сообщение для этого случая — el-56k.
- Аргументы: только `--data-dir <путь>` (и `-psn_…` от старых Finder);
  остальное — ошибка запуска, а не молча открытая база по умолчанию.
- Старая база рядом с exe предлагается на экране папки данных как явное
  переключение без копирования. При первом запуске используется system.
- **Capabilities (el-646)**: динамическая capability окна `main`,
  `local: false`, `remote.urls: ["http://127.0.0.1:<порт>"]`. Порт известен
  после bind, wildcard и localhost отсутствуют. Только `desktop_info`,
  `pick_folder`, `reveal_data_dir`, `preview_data_dir_change`, `change_data_dir`.
  Bundled error page получает отдельную local capability с
  `revert_data_dir` и `restart_app`; удалённый UI их не получает.
  `build.rs` объявляет все app commands, поэтому невыданная команда запрещена.
  Реальный `RuntimeAuthority` Tauri проверяется тестом на точный origin,
  чужой порт/host/protocol/window и раздельные команды страницы ошибки.
  Общих `fs:*`, `shell:*`, `opener:*`, `core:default` нет.
- В общем UI адаптер `desktop.ts` выбирает native folder dialog при наличии
  IPC; в браузере/NAS остаётся серверный browser. Панель показывает режим,
  пути, размеры БД с WAL и кэша, свободное место, открывает текущую папку в
  Finder/Explorer. Custom может вернуться к system через предпросмотр;
  portable только Windows, маркер рядом с exe. Portable и `--data-dir`
  фиксируют папку запуска, менять её через bootstrap в этом режиме нельзя.
- **Навигация**: `on_navigation` окна интерфейса пропускает только
  `http://<адрес bind>:<порт>` — тот же IP и порт, `localhost`, другой порт,
  `https`, `file:` и внешние сайты отклоняются (`is_server_page`); окно
  ошибки — только собственный origin ресурсов (`tauri://localhost`,
  `http(s)://tauri.localhost`). `on_new_window` → `Deny`: новых окон нет.
  Внешние ссылки **не открываются вовсе** — ни в окне, ни в системном
  браузере: интерфейс ссылается только на себя (`#…`), а открывать URL
  через `cmd /C start` небезопасно (`&` в URL — разделитель команд cmd).
  Понадобится внешняя ссылка — через проверенный opener по явному клику.
  Предупреждение Tauri о неотличимости iframe от окна касается Linux и
  Android — их мы не собираем; интерфейс iframe не использует.
- Сервер слушает только `127.0.0.1:0` (`SERVER_BIND`), проверка `Host` в
  `pc-api` действует (окно шлёт `Host: 127.0.0.1:<порт>`).
- Закрытие окна скрывает его; явный выход проходит через
  `ExitRequested` и согласованную остановку сервера (см. следующий раздел).
- Веб-UI распознаёт десктоп по наличию Tauri IPC и только тогда
  показывает нативный выбор папок и настройки data-dir (el-646); в браузере
  и на NAS остаётся серверный браузер папок (`/api/fs`). Зависимость
  `@tauri-apps/api` допустима, если укладывается в лимит 400 КиБ gzip и
  `check:unused`.

## Жизненный цикл

- **Один экземпляр на профиль**: до `resolve/prepare` и открытия БД
  берётся отдельный OS-lock `desktop-instance.writer-lock`. Второй запуск
  посылает только `show` на локальный activation listener и завершается;
  аргументы, пути и команды операций первому не передаются. Нового API
  listener/БД второй запуск не создаёт. Протокол принимает только `show`,
  отвечает `ok`, слушает исключительно `127.0.0.1`.
- Координация (`desktop-instance.port`, файл замка) и `window.json` находятся
  в app-local-data; в Windows portable — в `data` рядом с exe, без записи
  в профиль. Поэтому вместо запланированных plugins используются
  нейтральные `instance`/`geometry` и существующий `pc_core::lock`:
  сохраняются portable-контракт и проверяемая передача владения при restart.
  Custom/`--data-dir` не создают второй экземпляр в том же профиле;
  разные portable-копии имеют отдельные экземпляры, но общий writer-lock
  БД всё равно запрещает одновременную запись в один архив.
  `desktop-instance.port` и `window.json` никогда не пишутся сквозь то,
  что стоит на их имени: байты идут в новый файл с уникальным именем
  (`create_new`, ссылка не разыменовывается) и переименовываются на место.
  Символическая ссылка или второе имя чужого файла заменяются как имя,
  их цель остаётся байт в байт — то же правило, что у файла `.writer-lock`
  в `pc_core::lock` (O_NOFOLLOW, отказ при втором имени). Временный файл
  (`create_new`, на Unix 0600, `fsync` перед rename), оставшийся после
  сбоя записи, sync или rename (на имени каталог, EIO), не удаляется по
  пути: имя мог занять кто-то другой. Вместо этого ошибка называет целевой
  путь, путь оставленного временного файла и то, что он сохранён; вид
  ошибки ОС не меняется. `Geometry::save` пишет её в журнал оболочки,
  ошибка `Instance::claim` показывается в диалоге отказа запуска и в
  stderr. Убрать такой файл может только пользователь.
- **Перезапуск после смены data-dir**: дочерний процесс получает внутренний
  `PC_DESKTOP_REPLACEMENT=1` и ждёт освобождения instance-lock до 60 секунд.
  Старый процесс держит его до остановки сервера, записи геометрии и выхода.
  Ошибка spawn по-прежнему возвращает прежний bootstrap и сервер;
  недоступный владелец не обходится удалением lock-файла.
  Обычный повторный запуск во время quit тоже ждёт владельца: пока открыт
  диалог или идёт остановка, listener отвечает отказом активации. После
  отмены quit следующий запрос активирует прежнее окно; после выхода
  новый процесс захватывает освободившийся lock и запускает сервер.
- **Закрытие окна** скрывает существующий webview, сохраняя сервер, задачи,
  страницу и её прогресс. Windows: трей «Открыть», «Остановить работу»,
  «Выйти»; остановка вызывает общую кооперативную отмену, сервер остаётся.
  macOS: приложение остаётся в Dock; `RunEvent::Reopen` показывает и
  фокусирует окно, как и повторный запуск. Ошибочное окно доступно так же.
- **Геометрия**: сохраняются нормальное положение/размер и maximized;
  hidden/minimized не восстанавливаются как скрытое окно. При отключённом
  мониторе координаты ограничиваются рабочей областью основного экрана.
  Повреждённый JSON игнорируется. Геометрия не меняет data bootstrap.
- **Явный выход** (трей, Cmd+Q, «Завершить» в Dock): `shutdown(IfIdle)`
  атомарно проверяет отсутствие работы. Busy возвращает работающий сервер
  и открывает нативное подтверждение с номером и видом задачи.
  «Продолжить работу» — безопасная кнопка по умолчанию, задача не отменяется.
  «Остановить и выйти» вызывает `shutdown(CancelJob)`; заголовок окна
  показывает ожидание, текущие rename/journal завершаются без таймаута.
  Повторный quit не создаёт второй диалог. Выход сериализован со сменой
  папки данных, поэтому временное отсутствие сервера во время копирования
  не принимается за состояние покоя.
  Известное поведение (не исправлено, операторская проверка 03.10.2026):
  quit во время копирования при смене папки данных не показывает ничего —
  ни листа, ни индикатора — и молча ждёт конца переноса (на 2,4 ГБ около
  10 минут). После переноса отложенный quit не завершает приложение:
  открывается процесс-замена с новой папкой, как и при переносе без quit.
- **macOS native Quit**: у Tao 0.35 `terminate:` из стандартного меню/Dock
  обходит `ExitRequested`. Подкласс текущего AppKit delegate без новых ivars
  добавляет `applicationShouldTerminate:`: возвращает `NSTerminateLater`
  и запускает тот же согласованный путь. Затем на главном потоке вызывает
  `replyToApplicationShouldTerminate:`: NO при «Продолжить», YES только
  после остановки сервера. Перезапуск после смены папки учитывает ожидающий
  native reply тем же путём. Это [контракт AppKit](https://developer.apple.com/documentation/appkit/nsapplication/reply(toapplicationshouldterminate:));
  прежний безусловный `NSTerminateCancel` ошибочно сообщал отмену даже при
  idle quit. Остальные callbacks Tao, включая reopen и willTerminate/Exit,
  наследуются. `objc2` уже был в lockfile через Tauri, версии не менялись;
  зависимость включена только на macOS.
- **SIGTERM/SIGINT на macOS** кооперативно отменяют и дожидаются задачи
  без диалога. Windows Ctrl+C обрабатывается аналогично, если консоль есть.
  Обработчики регистрируются сразу после захвата instance-lock, **до**
  запуска сервера: пока API не слушает, принять работу некому, а после
  регистрации действие ОС по умолчанию (убить процесс) уже снято. Сигнал,
  пришедший до готовности окна, удерживается рантаймом; читать сигналы
  начинает `ready()`, когда сервер уже сохранён в состоянии оболочки, так
  что выход во время запуска сериализован с ним и затем идёт обычным путём
  (`IfIdle`, при занятости — подтверждённая остановка `CancelJob`, код 0,
  задача `cancelled`). Не удалось зарегистрировать обработчики — сервер не
  запускается: диалог отказа, stderr, код 1, база не открывается. Отказ
  запуска завершает процесс сам (`exit(1)`): ни сервера, ни экземпляра ещё
  нет, а `App::run` на macOS заканчивает процесс с кодом 0, какой бы код ни
  передали в `exit`, — отказ выглядел бы чистым выходом. Ошибка
  setup после запуска сервера сначала останавливает его через `CancelJob`
  (иначе паника цикла событий оборвала бы принятую работу).
  Обработчик слушает сигналы в цикле. Сигнал при открытом подтверждении
  переводит текущую попытку в подтверждённую остановку; поздний ответ
  диалога игнорируется. Сигнал и отмена диалога сериализованы: уже принятый
  сигнал не теряется, а сигнал после «Продолжить» начинает новую попытку.
  Завершение сеанса ОС — best effort; SIGKILL, force quit и выключение
  питания могут оставить `pending`. При старте jobs получают `interrupted`,
  журнал и файлы не проигрываются и не reconcile автоматически.
- **Файл `.writer-lock` не означает захваченный замок**. Он намеренно
  остаётся и после чистого выхода, и после аварии; блокировкой владеет
  открытый OS handle (`flock`/`LockFileEx`). Закрытие handle/смерть процесса
  освобождают блокировку. Удалять файл живого владельца нельзя: новый файл
  будет другой блокировкой и позволит двух writers. Состояние проверяют
  попыткой взять lock, не наличием файла.

## Приёмка MVP

Проверки на временных данных, никаких записей в настоящий архив и `purge`:

1. Первый и повторный запуск: создаётся и затем находится та же база в
   `LOCAL/data`.
2. Запуск из read-only каталога программы; portable на Windows; custom на
   отключённом диске даёт экран ошибки, а не пустую базу.
3. Пути с пробелами и кириллицей в data-dir и в корнях архива.
4. База занята другим процессом (writer lock) — понятная ошибка.
5. Выбор и отмена нативного диалога папок.
6. Закрытие и открытие окна во время индексации — прогресс сохраняется.
7. Выход при идущей задаче: отмена выхода оставляет задачу работать;
   подтверждение останавливает на границе файла; повторный старт ничего
   не повторяет сам.
8. Смена data-dir: успех, отмена, конфликт с существующей базой, нехватка
   места, ошибка копирования, неудачный перезапуск — исходные данные целы.
9. Полный путь в окне: опись → индекс → план → карантин → откат; защиты
   устаревшего плана (preview token) и writer lock работают как в браузере.
10. Посторонняя страница (внешняя ссылка, другой порт) не получает IPC.

Обязательные проверки кода: `cargo fmt --all --check`,
`cargo clippy --all-targets -- -D warnings`,
`cargo test --workspace --locked`; при изменении веба — `npm run build`,
`npm run check:unused`, `npm test`, закоммиченный `dist`.

`cargo clippy --all-targets -- -D warnings`, `cargo test --workspace --locked`
(402 passed), сборка cli/desktop, web build/check:unused под Node v24.21.0

проверены: машины Windows нет, это остаётся приёмке el-56k. Unit-тесты
