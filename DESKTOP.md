# Настольное приложение на Tauri v2

Рабочий документ разработки. Сверено с кодом 0.4.4 (коммит `da2cd09`)
26.09.2026; первая редакция — 21.09.2026 на базе 0.2.15. Спецификация, а
не описание готового: из `pc-desktop` пока есть только платформенно-нейтральная
библиотека выбора каталога данных (el-2be, см. «Контракт для оболочки»);
Tauri в workspace нет. В публичную часть репозитория не предназначен.

## Зачем

Сейчас на Windows продукт раздаётся как zip с exe и батником
(`packaging/windows`): батник поднимает `serve --open` с базой и
миниатюрами рядом с exe, дальше интерфейс живёт вкладкой браузера. На
macOS — голый CLI-бинарь arm64. Для инструмента, которым архив разбирают
неделями, это неудобно.

Нужно окно приложения: запуск двойным кликом на **Windows x64** и
**macOS arm64**, свой значок, понятное «запущено» и «выключено», без
терминала и без вкладки браузера.

## Что это не меняет

- Сервер, база, миниатюры, вся логика — как есть. Десктоп — окно поверх
  того же `pc-api` и того же встроенного `dist`, а не вторая реализация и
  не свои экраны.
- CLI (`serve`, `--open`, Ctrl+C), Docker-образ `FROM scratch` и
  статические Linux-бинари остаются; на NAS нужен сервер, а не окно.
- Нативный код не выполняет бизнес-операций. Всё, что трогает архив, идёт
  через HTTP API с его защитами: preview token плана, подтверждение
  `purge`, writer lock (`pc_core::lock`), один исполнитель задач.
- **Никаких автоматических сетевых запросов.** Проверка обновлений, updater
  и телеметрия в MVP не входят (см. «Следующий этап»).

## Сборка и изоляция в workspace

### Что было неверно

Прежняя редакция предлагала исключить крейт из `default-members`, чтобы
«`cargo test --workspace` на ubuntu его не трогал». Это не так. По
[документации Cargo](https://doc.rust-lang.org/cargo/reference/workspaces.html#package-selection)
`default-members` действует только тогда, когда команда запущена в корне
workspace **без** `-p`/`--workspace`; `--workspace` выбирает всех членов.
А корневой `Cargo.toml` задаёт `members = ["crates/*"]` — новый каталог
`crates/pc-desktop` станет членом сам.

Хуже того, `default-members` развёл бы проверки: CI вызывает
`cargo clippy --all-targets` без `--workspace` (в виртуальном workspace
без `default-members` это все члены), а `cargo test --workspace` — всех.
С `default-members` clippy перестал бы видеть десктоп, а тесты — нет.

### Решение: target-gating внутри крейта

`crates/pc-desktop` — обычный член workspace, `default-members` не
вводится. Tauri и его плагины подключаются только для целевых ОС
([платформенные зависимости Cargo](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#platform-specific-dependencies)):

```toml
[target.'cfg(any(windows, target_os = "macos"))'.dependencies]
tauri = { version = "2", features = [] }
tauri-plugin-single-instance = "2"
tauri-plugin-window-state = "2"
tauri-plugin-dialog = "2"

[target.'cfg(any(windows, target_os = "macos"))'.build-dependencies]
tauri-build = "2"
```

Устройство крейта:

- `src/lib.rs` — платформенно-нейтральная часть: разрешение data-dir и
  bootstrap-конфиг, перенос данных, проверка целостности копии. Зависит
  только от `pc-core`/`pc-db`/`pc-api` и компилируется и тестируется **на
  всех трёх ОС**, включая Linux. Системные каталоги передаются параметром
  (`SystemDirs`), а не берутся из Tauri, — так логика тестируется без окна.
- `src/shell/` и `main.rs` под `#[cfg(any(windows, target_os = "macos"))]`
  — окно, трей, IPC-команды. На остальных ОС `main` печатает, что
  настольная сборка поддерживается только на Windows и macOS, и выходит с
  ненулевым кодом.
- `build.rs` вызывает `tauri_build::build()` под тем же `cfg`. Сборка
  только нативная (как и в `Dockerfile`): `cfg` в `build.rs` — это
  платформа хоста, и при кросс-компиляции он разошёлся бы с целью.

Что это даёт:

| команда | Linux (ubuntu CI) | Windows / macOS |
|---|---|---|
| `cargo test --workspace --locked` | собирает lib и заглушку, **без webkit2gtk** | собирает и тестирует всё |
| `cargo clippy --all-targets -- -D warnings` | lib и заглушка | всё, включая оболочку |
| `docker build` (`-p pc-cli`) | Tauri не компилируется | — |

`Cargo.lock` один на workspace и содержит зависимости всех платформ, так
что `--locked` продолжает работать везде. Linux-зависимости самого Tauri
(`webkit2gtk`, gtk) не попадают в граф Linux-сборки, потому что `tauri`
для Linux не подключён вовсе.

**Проверить при реализации (el-5re)**, а не принимать на веру: `cargo tree
-p pc-desktop --target x86_64-unknown-linux-gnu` не содержит `tauri`/`wry`;
`docker build --target export .` проходит без изменений `Dockerfile`;
релизная сборка без `tauri-cli` не уходит в dev-режим (у Tauri v2
продакшн-поведение включается фичей `custom-protocol`, которую `tauri build`
выставляет сам) — собирать артефакты через `cargo tauri build` либо явно
включать эту фичу.

### Отвергнутые варианты

- **`default-members`** — см. выше: не исключает из `--workspace` и
  расщепляет clippy и тесты.
- **`exclude` и отдельный workspace** — второй `Cargo.lock`, `--locked` и
  обязательные проверки перестают его покрывать, версии `pc-api` и
  зависимостей расходятся незаметно.
- **Cargo-фича `desktop`, выключенная по умолчанию** — обязательные
  проверки без `--all-features` не компилируют оболочку, а с
  `--all-features` Linux снова требует webkit2gtk.

## Запуск сервера: контракт `pc-api`

Сейчас (0.4.4) `pc_api::serve(db, thumbs, quarantine, bind, open)` сам
биндит адрес, печатает его, ждёт Ctrl+C и ничего не возвращает. Задача
el-39i выделяет управляемый запуск; `serve()` остаётся тонкой обёрткой над
ним, поведение CLI не меняется.

```rust
pub struct ServerConfig {
    pub db_path: PathBuf,
    pub thumbs: PathBuf,
    pub quarantine: Option<PathBuf>,
    pub bind: SocketAddr,           // десктоп: 127.0.0.1:0
}

pub struct Server { /* state, handle, shutdown-канал */ }

/// Возвращается, когда сервер готов: AppState создан (миграции, язык из
/// настроек, пометка осиротевших задач), listener уже привязан. Соединения
/// после этого момента принимаются (очередь ядра), поэтому окно можно
/// открывать сразу по `local_addr()`.
pub async fn start(config: ServerConfig) -> Result<Server>;

impl Server {
    pub fn local_addr(&self) -> SocketAddr;      // фактический порт
    pub fn active_job(&self) -> Option<(i64, String)>; // id и kind
    pub async fn shutdown(self, mode: Shutdown) -> Result<()>;
}

pub enum Shutdown {
    /// Отказать, если идёт задача (Err с её id), иначе остановиться.
    IfIdle,
    /// Отменить задачу через Control::cancel и дождаться её конца.
    CancelJob,
}
```

Требования:

- Ошибки `bind` и инициализации (занятая/битая база, чужая версия схемы)
  возвращаются из `start` как `Err`, а не печатаются: десктоп показывает
  их в окне. Логика инициализации не дублируется в десктопе.
- `shutdown` сначала закрывает приём новых задач и ручных изменений (ответ
  503 с понятным текстом), затем, для `CancelJob`, ставит флаг отмены и
  **ждёт без таймаута**, пока задача сама дойдёт до границы файла
  (`Control::check`), освободит writer lock и запишет терминальное
  состояние в `jobs`. Операция `rename` и запись журнала не прерываются
  посередине; принудительного убийства потока нет. Затем — graceful
  остановка axum и закрытие соединений SQLite (WAL сводится при закрытии
  последнего соединения).
- Если процесс всё же убит (питание, диспетчер задач), действует текущее
  правило `AppState::new`: при следующем старте `queued`/`running`
  становятся `interrupted`, незавершённые записи журнала сверяются
  `journal-reconcile`. Дисковые операции **никогда не повторяются
  автоматически** после перезапуска.
- `state.network` для десктопа всегда `false` (loopback).

Проверка `Host` (el-55m): активна только когда `serve` реально забиндился
на loopback-адрес (`local.ip().is_loopback()` после `bind`, т.е. и для
явного `127.0.0.1:0`/desktop, и для дефолта CLI); при bind на не-loopback
(NAS) поведение не меняется — middleware туда не подключается. Допустимые
значения заголовка — фактический адрес/порт после `bind` (порт `:0`
резолвится в реальный слушаемый порт до навешивания проверки):
`127.0.0.1:<порт>` или `localhost:<порт>` для IPv4-бинда,
`[::1]:<порт>` (localhost тоже принимается) для IPv6-бинда. Отсутствующий
или чужой `Host`, чужое имя хоста и неверный порт — отказ `421 Misdirected
Request`. `X-Forwarded-Host` не учитывается — заголовку доверия нет, так
как его может подставить сама rebinding-страница. Проверка живёт в
`serve()` (`crates/pc-api/src/lib.rs`), не в `router()` — при рефакторинге
запуска pc-api (el-39i) её нужно перенести вместе с сервером, не потеряв.
Код и тесты — `crates/pc-api/src/security.rs`. Для dev-прокси (`npm run
dev`, `crates/pc-api/web/vite.config.ts`) обязателен `changeOrigin: true`
у `/api`: иначе Vite пересылает исходный `Host: localhost:5173` и loopback
pc-api отвечает 421 на каждый запрос. JSON-запросы из чужого origin и без
rebinding уже упираются в CORS preflight, но rebinding его обходит —
поэтому проверка нужна отдельно.

## Где лежат данные

### Раскладка каталога данных

Каталог данных (data-dir) содержит ровно то, что сейчас кладут рядом с
базой CLI и батник:

```
<data-dir>/
  photo-cleanup.db          (+ -wal, -shm во время работы)
  photo-cleanup.db.writer-lock
  thumbs/
```

Карантин в data-dir не входит: по умолчанию он в корне файловой системы
каждого файла (иначе перенос перестал бы быть `rename`).

### Режимы и bootstrap-конфиг

Путь к базе нельзя хранить в самой базе, поэтому выбор режима лежит в
маленьком файле **вне** data-dir и **вне** каталога программы:

- идентификатор приложения (он же имя каталога Tauri):
  `io.github.imcitius.photo-cleanup`;
- `LOCAL` = `app_local_data_dir()` Tauri: `%LOCALAPPDATA%\<id>` на
  Windows, `~/Library/Application Support/<id>` на macOS
  ([PathResolver](https://docs.rs/tauri/latest/tauri/path/struct.PathResolver.html)).
  Roaming-профиль Windows не используется: путь к локальному диску с
  другой машины был бы ложью;
- bootstrap: `LOCAL/desktop.json`, пишется атомарно (временный файл +
  rename):

```json
{ "version": 1,
  "mode": "system",          // "system" | "custom"
  "data_dir": null,          // абсолютный путь для custom
  "previous": null }         // прежний выбор, пока новый не подтверждён запуском
```

Три режима:

1. **system** (по умолчанию) — `LOCAL/data/`.
2. **portable** — только Windows и только явно: рядом с exe лежит файл
   `photo-cleanup.portable`, данные в `<каталог exe>\data\`. Портабельный
   режим не угадывается по доступности каталога на запись. На macOS не
   поддерживается: скачанный браузером `.app` запускается через App
   Translocation из случайного read-only пути, «рядом с программой» там
   нет, а писать внутрь `.app` нельзя.
3. **custom** — каталог, выбранный пользователем (например, большой диск
   рядом с архивом).

### Порядок разрешения при запуске

1. Аргумент `--data-dir <путь>` (тесты, продвинутое использование) — на
   этот запуск, в bootstrap не записывается.
2. Windows: есть `photo-cleanup.portable` рядом с exe → portable. Каталог
   недоступен на запись → экран ошибки; тихого отката в системный каталог
   нет (прежняя редакция предлагала откат — отменено).
3. Есть `LOCAL/desktop.json` → его режим. Файл не читается или не
   разбирается → экран ошибки, файл не перезаписывается.
   Каталог `custom` отсутствует (отключён диск) или в нём нет
   `photo-cleanup.db` → экран «Данные недоступны: <путь>» с действиями
   «Повторить», «Выбрать другую папку», «Вернуться к прежней» (если есть
   `previous`). **Пустая база на месте недоступной не создаётся.**
4. Bootstrap нет → первый запуск: создаётся `LOCAL/data/`, открывается или
   создаётся база, и только после успешного открытия пишется bootstrap
   `system`. Если рядом с exe лежит `photo-cleanup.db` от батника,
   первый экран предлагает использовать её (как custom, без копирования)
   или начать в системном каталоге — молча не подхватывается.

Новая база создаётся только в шаге 4 или по явному действию пользователя
(«создать новую базу в этой папке»). Каталог программы ни в одном режиме,
кроме явного portable, не записывается, поэтому запуск из read-only места
(Program Files, смонтированный образ, translocated `.app`) работает.

Пути с пробелами и кириллицей — обязательный тестовый случай resolver'а и
переноса (el-2be, el-646).

Уточнения, принятые при реализации (el-2be):

- Правило «пустая база не создаётся» действует и для `system`: bootstrap
  есть, а `LOCAL/data/photo-cleanup.db` нет → тот же экран «Данные
  недоступны», а не новая база. Bootstrap существует только после
  успешного открытия базы, значит, данные там были.
- `--data-dir` может создать базу: это явное указание на этот запуск.
  Относительный путь отвергается — и там, и в bootstrap, и при выборе папки:
  текущий каталог приложения, запущенного из Finder/Explorer, случаен.
- Битый bootstrap при запуске не перезаписывается, но явный выбор папки
  пользователем с экрана ошибки его заменяет — это и есть выход. Bootstrap
  более новой версии (`version` > 1) не перезаписывается ничем.
- Каталог проверяется на запись пробным файлом, а не по битам прав (ACL,
  read-only тома); существующая база открывается без флага CREATE и
  проверяется, что SQLite не открыл её молча только на чтение.

### Контракт для оболочки

Крейт `pc-desktop`, `src/lib.rs` и модули `bootstrap`, `resolve`, `error`.
Тесты — `crates/pc-desktop/tests/data_dir.rs`, на временных каталогах;
readonly-случаи — только unix (`chmod 555`; под root пропускаются явно).

```rust
let dirs = SystemDirs::new(app.path().app_local_data_dir()?, exe_dir);
let r = pc_desktop::resolve(&dirs, cli_data_dir)?;   // только чтение
// r.legacy_dir == Some(..) → спросить: choose_data_dir(.., UseExisting) или продолжить с r
let p = pc_desktop::prepare(&dirs, &r)?;             // открыть/создать базу, затем bootstrap
// pc_api::start(p.layout.db, p.layout.thumbs, ..)
pc_desktop::confirm_started(&dirs, &p)?;             // снять `previous`
```

- `SystemDirs { app_local_data, exe_dir, portable_supported }` —
  `SystemDirs::new` ставит `portable_supported = cfg!(windows)`.
- `DataLayout { dir, db, thumbs }` — `photo-cleanup.db` и `thumbs/`.
- `StartupError` сериализуется с тегом `kind`
  (`data_unavailable` с `source`, `dir`, `why.what` ∈ `missing`,
  `not_a_directory`, `no_database`, `not_a_database`, `not_writable`, и
  `previous`; `bootstrap_unreadable`, `bootstrap_unsupported`,
  `bootstrap_write`, `database_exists`, `relative_path`,
  `portable_active`, `no_previous`, `create_failed`) — по нему экран
  ошибки выбирает действия; `Display` двуязычный через `pc_core::tf!`.
- Действия экрана ошибки: «Повторить» — снова `resolve`; «Выбрать другую
  папку» — `choose_data_dir(dir, UseExisting | CreateNew)` →
  `prepare`; «Вернуться к прежней» — `revert_to_previous` → `prepare`.
  В portable-режиме выбор и возврат отвергаются (`portable_active`).

Контракт для переноса (el-646): перенос копирует базу и миниатюры сам,
а завершает его запись `Bootstrap::new(Choice::custom(new), Some(old))`
через `write_bootstrap` (атомарно) и перезапуск. Дальше обычный путь:
новый каталог поднялся → `confirm_started` снимает `previous`; не поднялся
→ `data_unavailable` с `previous` и `revert_to_previous`. Своего API
настроек у переноса нет, «текущий выбор» — только bootstrap.

### Смена каталога данных

Это перенос **данных приложения** (база и миниатюры), не фотографий.
Выполняет нативная оболочка, потому что серверу нужно остановиться.

1. **Предпросмотр** (ничего не меняет): текущий и новый путь, размер базы
   вместе с WAL и миниатюр, свободное место в цели, конфликты. «Отмена» на
   любом шаге до записи bootstrap оставляет всё как было.
2. **Конфликт**: в цели уже есть `photo-cleanup.db` → копирование
   запрещено, чужая база не перезаписывается. Отдельное явное действие —
   «переключиться на существующую базу» без копирования.
3. **Остановка записей**: идущая задача → то же подтверждение, что при
   выходе (см. ниже); затем `Server::shutdown`; на всё время переноса
   берётся writer lock, чтобы CLI или второй сервер не писали в исходную
   базу.
4. **Копия базы** — `VACUUM INTO '<цель>/photo-cleanup.db.partial'` (или
   SQLite online backup): получается согласованный снимок с содержимым
   WAL. Файлы `-wal`/`-shm` побайтно не копируются.
5. **Проверка копии**: `PRAGMA integrity_check` = `ok`, совпадает
   `MAX(version)` в `schema_version` и число строк ключевых таблиц
   (`files`, `families`, `journal`, `jobs`). Затем `photo-cleanup.db.partial` → `photo-cleanup.db`
   переименованием.
6. **Миниатюры** — в `thumbs.partial/`, сверка числа и суммарного размера
   файлов, затем переименование. Ошибка здесь отменяет весь перенос, как и
   ошибка базы: полуперенесённого состояния нет.
7. **Bootstrap** пишется атомарно с новым режимом и `previous` = старый,
   затем перезапуск приложения. Успешный старт на новом месте очищает
   `previous`; неуспешный показывает экран ошибки с «Вернуться к прежней».
8. **Исходные данные не удаляются никогда** — ни при успехе, ни при
   ошибке. Экран настроек показывает, где осталась старая копия; удалить её
   пользователь может сам.

Любая ошибка (нет места, ошибка копирования, проверка не сошлась,
перезапуск не удался) оставляет исходный каталог рабочим и выбранным;
временные `.partial` в цели удаляются, только если созданы этим переносом.

## Окно и безопасность

- Окно создаётся в `setup()` после `start()` с
  `WebviewUrl::External("http://127.0.0.1:<порт>/")`. Ошибка запуска
  показывается в окне (локальная страница ошибки из ресурсов), не в
  консоли; на Windows приложение собирается как GUI subsystem.
- **Capability** одна, `windows: ["main"]`, добавляется в рантайме через
  `Manager::add_capability` (фича `dynamic-acl`, в Tauri 2 включена по
  умолчанию), когда порт уже известен:
  `remote.urls: ["http://127.0.0.1:<порт>"]` — точный порт, без `*` и
  без `localhost`. Статического wildcard на `http://127.0.0.1:*` нет: он
  дал бы IPC любой странице любого локального сервера.
  См. [capabilities](https://v2.tauri.app/security/capabilities/) и
  [справочник полей](https://v2.tauri.app/reference/acl/capability/).
- Права — только собственные команды оболочки: `desktop_info` (режим,
  пути, размеры), `pick_folder` (нативный диалог, возвращает путь или
  отмену), `reveal_data_dir` (без аргументов, открывает data-dir в
  Finder/Explorer), `preview_data_dir_change`, `change_data_dir`,
  `quit`. Никаких `fs:*`, `shell:*`, `opener:*` с произвольными путями,
  `core:default` — только если окажется нужен, и тогда перечислить.
- **Навигация**: `on_navigation` разрешает только origin своего сервера.
  Внешние ссылки открываются в системном браузере только по явному клику и
  никогда внутри окна; новые окна не создаются. Предупреждение Tauri о
  неотличимости iframe от окна касается Linux и Android — их мы не
  собираем; интерфейс iframe не использует.
- Сервер слушает только `127.0.0.1:0`.
- Веб-UI распознаёт десктоп по наличию Tauri IPC и только тогда
  показывает нативный выбор папок и настройки data-dir; в браузере и на NAS
  остаётся серверный браузер папок (`/api/fs`). Зависимость
  `@tauri-apps/api` допустима, если укладывается в лимит 400 КиБ gzip и
  `check:unused`.

## Жизненный цикл

- **Один экземпляр** (`tauri-plugin-single-instance`, регистрируется
  первым): второй запуск передаёт управление первому, тот показывает и
  фокусирует окно; второй процесс завершается до разрешения data-dir и до
  `bind`. Второй сервер на той же базе не поднимается.
- **Закрытие окна** не останавливает сервер и задачи. Windows: окно
  скрывается, в трее меню «Открыть», «Остановить работу» (отмена текущей
  задачи, как кнопка в UI), «Выйти». macOS: приложение остаётся в Dock,
  клик по значку (`RunEvent::Reopen`) возвращает окно.
- **Геометрия** — `tauri-plugin-window-state`; окно за пределами
  подключённых мониторов возвращается на основной.
- **Явный выход** (трей, Cmd+Q, «Завершить» в Dock): задачи нет →
  `shutdown(IfIdle)` и выход. Задача идёт → диалог «Идёт <вид задачи>.
  Остановить на границе файла и выйти / Продолжить работу». «Продолжить» не
  меняет ничего; «Остановить» → `shutdown(CancelJob)` с индикатором
  ожидания, выход только после возврата. Завершение сеанса ОС —
  best-effort отмена; дальше действует правило `interrupted` +
  `journal-reconcile`.

## Платформы и CI

Целевые: Windows x64 (`windows-latest`) и macOS arm64 (`macos-14`).
Linux — только CLI и Docker, как сейчас.

| проверка | ubuntu | windows | macos-14 |
|---|---|---|---|
| `cargo fmt --all --check` | есть | — | — |
| `cargo clippy --all-targets -- -D warnings` | есть (lib + заглушка) | **добавить** (оболочка) | **добавить** |
| `cargo test --workspace --locked` | есть | есть | **добавить** |
| web: `npm run build`, сверка `dist`, `check:unused`, `npm test` | есть | — | — |
| `cargo build --release -p pc-cli` + `--version` | есть | есть | в release |
| сборка десктопа | — | **добавить**: exe → `photo-cleanup-desktop-windows-x64.zip` | **добавить**: `.app` → `photo-cleanup-desktop-macos-arm64.zip` |
| smoke десктопа (временный data-dir, старт → HTTP → остановка) | — | **добавить** | **добавить** |
| Docker/Linux-бинари (release) | без изменений, без webkit2gtk | — | — |

Существующие артефакты релиза (CLI zip для Windows, CLI arm64 для macOS,
Linux-бинари, образ GHCR) сохраняются. Всё, что CI не может проверить
(реальное окно, трей, диалог папок, close/reopen во время индексации,
запуск скачанного `.app` под Gatekeeper, отсутствие WebView2), проверяется
вручную на обеих ОС, и **непроверенное явно отмечается в отчёте как
непроверенное**, а не как пройденное.

Подпись: MVP не подписан. На macOS arm64 бинарь получает ad-hoc подпись
линковщика, но скачанный `.app` Gatekeeper не откроет без явного
разрешения пользователя — инструкция в README. На Windows SmartScreen
предупреждает, как и с нынешним zip. WebView2 есть на Windows 11 и
обновлённой Windows 10; при отсутствии — понятное сообщение, загрузчик в
архив не кладётся.

## Приёмка MVP

Проверки на временных данных, никаких записей в настоящий архив и `purge`:

1. Первый и повторный запуск: создаётся и затем находится та же база в
   `LOCAL/data`.
2. Запуск из read-only каталога программы; portable на Windows; custom на
   отключённом диске даёт экран ошибки, а не пустую базу.
3. Пути с пробелами и кириллицей в data-dir и в корнях архива.
4. База занята другим процессом (writer lock) — понятная ошибка.
5. Выбор и отмена нативного диалога папок.
6. Закрытие и открытие окна во время индексации — прогресс сохраняется.
7. Выход при идущей задаче: отмена выхода оставляет задачу работать;
   подтверждение останавливает на границе файла; повторный старт ничего
   не повторяет сам.
8. Смена data-dir: успех, отмена, конфликт с существующей базой, нехватка
   места, ошибка копирования, неудачный перезапуск — исходные данные целы.
9. Полный путь в окне: опись → индекс → план → карантин → откат; защиты
   устаревшего плана (preview token) и writer lock работают как в браузере.
10. Посторонняя страница (внешняя ссылка, другой порт) не получает IPC.

Обязательные проверки кода: `cargo fmt --all --check`,
`cargo clippy --all-targets -- -D warnings`,
`cargo test --workspace --locked`; при изменении веба — `npm run build`,
`npm run check:unused`, `npm test`, закоммиченный `dist`.

## Следующий этап

Не входит в локальный MVP и планируется отдельно:

- автообновление (`tauri signer`, манифест, явное согласие и отключение) —
  единственный сетевой запрос, только по согласию;
- подпись и нотаризация macOS (Apple Developer Program), подпись Windows;
- установщики (`nsis`/`msi`, `dmg`), `scoop`/`winget`;
- Linux-десктоп.

Оценки сроков из первой редакции («полтора-два дня» и т. п.) не
подтверждены и сняты.
