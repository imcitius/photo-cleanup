# photo-cleanup — проектный документ

Статус: реализовано. Документ описывает, почему конвейер устроен именно так;
что работает сегодня — в [README.ru.md](README.ru.md).
Дата замеров архива: 2026-09-19.

---

## 1. Задача

Разобрать фотоархив, накопленный за много лет: найти дубликаты (включая копии в
другом формате и разрешении), выбрать лучший вариант, безопасно убрать остальное.
Дополнительно: разбор серий с выбором лучшего кадра, категоризация (сканы,
документы, счётчики, скриншоты), опциональная реорганизация структуры папок.

Что инструмент **не** делает:
- не удаляет файлы (только перенос в карантин + журнал отката);
- не распознаёт лица (детекция без идентификации — да, см. §9.3);
- не трогает видео в v1 (см. §14);
- не пишет внутрь библиотек Apple Photos.

## 2. Фактическое состояние архива

Целевое дерево: `/mnt/disk{1,2,3}/data/media/foto/`, кроме `Video/`.

### 2.1 Изображения — цель работы

| формат | файлов | GiB |
|---|---:|---:|
| jpg | 39 384 | 116.7 |
| arw (Sony RAW) | 4 290 | 88.8 |
| dng | 4 955 | 59.5 |
| tif/tiff | 1 473 | 16.2 |
| bmp | 140 | 3.8 |
| cr2 | 102 | 0.7 |
| png/psd/webp/xcf | 54 | 0.2 |
| **итого** | **50 398** | **286** |

Плюс неопределённое число фотографий без расширения (см. 2.3).

### 2.2 Прочее содержимое `foto/`

- **Видео россыпью внутри D/E/F: 366 GiB** (mp4 188, avi 104, mov 50, mpg 16,
  wmv 4, vob 3, mts 1). Отдельно папка `Video/` — 389 GiB.
- **Регенерируемые превью Lightroom: ≥92 GiB** — 24 520 JPEG без расширения
  внутри `*.lrdata`, плюс `.lrprev` 10 755 файлов / 2.9 GiB.
- Каталоги Lightroom: 18 шт., `.lrcat` суммарно 0.2 GiB.
- Архивы: 4 zip на 40 MiB, все — бэкапы `.lrcat`. Работа с архивами не нужна.

### 2.3 Открытый вопрос

~11 800 файлов без расширения (~81 GiB, средний размер 7 MiB) не попали в
учтённые `.lrdata`. Это либо превью более глубоко вложенных библиотек в `D/`
и `E/`, либо настоящие фотографии, потерявшие расширение. На архитектуру не
влияет — покрыто определением типа по magic bytes.

### 2.4 Особенности источника

- `D/`, `E/`, `F/` — дампы старых винчестеров. Фото перемешаны с системным
  мусором (dll, so, базы, бэкапы). Нужны фильтры сверх скоупа по каталогам.
- `Lightroom_lib/` — живой рабочий каталог (изменён недавно), в отличие от
  архивных дампов. Даёт приоритет путей по умолчанию.
- По всему массиву 122 417 JPG, внутри `foto/` — 39 384. Скоуп по каталогам
  отсекает 83 тысячи иконок и ассетов бесплатно.
- В архиве **нет HEIC**. libheif — за feature-флагом, не в v1.
- В корне есть `.DS_Store` → будут AppleDouble `._*`.

### 2.5 Железо

- Unraid, Ryzen 5 7600X (6c/12t, Zen 4, AVX-512 + VNNI), 16 GB RAM, Docker.
- disk1 WD40EFPX 3.7T (2.5T free), disk2 WD40EFPX 3.7T (2.7T free),
  disk3 Toshiba MG08 7.3T (4.3T free). Фото — преимущественно на disk2 и disk3.
- Кэш NVMe 477G, свободно 101G.
- **Паритета нет.** Оба слота `DISK_NP_DSBL`, `sbSynced=0`. Массив без
  избыточности — см. §12.1.
- Mac M3 Pro 36 GB есть, но для этой задачи не нужен (§3.2).

## 3. Ключевые решения

### 3.1 Всё считается на Unraid, локально

7600X — десктопный Zen 4, не слабый NAS-процессор. При корпусе в 50 тысяч
изображений полный проход занимает ~15 минут (§11). Сеть 2.5 GbE не
задействуется: инструмент работает в Docker на самой машине.

### 3.2 Apple Neural Engine не используется

Задача упирается в IO и JPEG-декод, а не в матричные умножения. Единственная
стадия, где помог бы ANE — эмбеддинги — на 7600X с INT8/VNNI занимает ~6 минут.
Разделение конвейера между NAS и Mac не окупается.

Путь на Mac сохраняется как опция: thumbnail-кэш (~1.5 GiB) переносится куда
угодно, инференс идёт через ONNX Runtime с выбором execution provider
(`cpu` / `coreml` / `cuda` / `directml`), модель одна и та же.

### 3.3 Никаких ANN-индексов — точный полный перебор

На 75 тысячах векторов приближённый поиск медленнее и сложнее точного.

- **Эмбеддинги.** Матрица 75k × 512 f32 = 154 MB. Все попарные косинусы — один
  GEMM: 5.8 TFLOP. Zen4 на 6 ядрах даёт ~670 GFLOPS на GEMM → **~9 секунд**.
  Блочно, полную матрицу не материализуем, храним top-K по строке.
- **pHash.** 2.8 млрд пар, XOR + `VPOPCNTDQ` → **меньше секунды**.

Убирает из проекта `usearch`/`hnsw_rs`, BK-дерево, их персистентность и
инвалидацию. Результат при этом точный, а не приближённый.

### 3.4 Тип файла — по magic bytes, никогда по расширению

24 520 файлов без расширения оказались JPEG. Обратное тоже встречается.
Расширение — подсказка для приоритета чтения, не более.

### 3.5 RAW читаем через встроенное превью

ARW/DNG/CR2 — контейнеры с индексом (TIFF/IFD). Полноразмерный или
крупный JPEG-превью извлекается без декодирования сенсорных данных.
149 GiB RAW → ~12 GiB фактического чтения.

Механика: первые 64 KiB дают заголовок и смещение превью, затем один seek.
Работу внутри диска сортируем по inode, чтобы головка шла вперёд.

JPEG так нельзя — энтропийный поток последовательный, файл читается целиком;
экономим только CPU через `scale_denom` библиотеки libjpeg-turbo.

### 3.6 Язык: Rust

Производительность больше не аргумент — корпус мал. Оправдание:
один статический бинарь под Docker, прямой FFI к libjpeg-turbo и libraw,
отсутствие GC на долгих проходах, задел на инкрементальный режим и видео
(755 GiB, там счёт другой).

## 4. Модель данных

### 4.1 Кадр, представление, роль

Единица смысла — **один спуск затвора** (`family`). У него несколько
**представлений** — файлов, каждый со своей **ролью**:

| роль | что это | удаляется по умолчанию |
|---|---|---|
| `original` | RAW или самый ранний/крупный член | нет |
| `camera-jpg` | JPEG из камеры рядом с RAW | нет |
| `converted` | DNG, сконвертированный из RAW | нет |
| `export` | экспорт из Lightroom/Photoshop | нет |
| `resize` | уменьшенная производная | по порогу разрешения |
| `copy` | побайтово или попиксельно идентичный близнец | **да** |
| `unknown` | роль не определена | нет, ручной разбор |

Дубликатом по умолчанию считается только `copy`. Всё остальное —
представления, они сохраняются, пока пользователь не решит иначе.

### 4.2 Провенанс берётся из метаданных, а не угадывается

| связь | источник | точность |
|---|---|---|
| DNG ← RAW | тег DNG `OriginalRawFileName` | точная |
| экспорт ← оригинал | XMP `xmpMM:DerivedFrom`, `DocumentID`, `OriginalDocumentID` | точная |
| один спуск затвора | `DateTimeOriginal` + `SerialNumber` тушки + `SonyImageNumber`/`ShutterCount` | точная |
| RAW ↔ камерный JPEG | общий basename + общий `DateTimeOriginal` + нетронутый EXIF камеры | точная |
| virtual copies, стеки | каталог Lightroom | точная |
| остальное | pHash → SSIM → ORB+RANSAC | эвристика |

Перцептивное сравнение работает только там, где точных связей нет.

### 4.3 Тиры совпадения

| тир | что | сигнал |
|---|---|---|
| T0 | байт-в-байт | blake3 |
| T1 | пиксели совпадают, отличается контейнер/EXIF | хеш декодированного RGB |
| T2 | тот же кадр, другое разрешение/качество | pHash → **SSIM обязательно** |
| T3 | кроп, поворот, редакт | эмбеддинг → **ORB+RANSAC обязательно** |
| T4 | та же сцена, другой кадр | эмбеддинг, низкий порог |

T4 — **не дубликат**, это серия (§9). Смешение T2 и T4 уничтожило бы серийную
съёмку.

Правило: из кандидата в T2 или T3 продвигаем только после геометрической
верификации. pHash и эмбеддинг — фильтры, не доказательства.

## 5. Конвейер

```
0  walk        обход /mnt/diskN напрямую, шардинг по физическим дискам,
               1-2 читателя на диск, сортировка по inode
               фильтры: magic bytes, размер >100 KiB, мин. сторона >512 px,
               стоп-лист путей
1  extract     RAW/контейнеры → seek к превью; JPEG → полное чтение
               EXIF, XMP, magic, размеры, ориентация
               blake3 файла, thumbnail 384px → blob-стор
2  lr-index    чтение .lrcat (read-only копия), слияние 18 каталогов
3  hash        pixel-hash после нормализации ориентации,
               pHash/dHash + pHash по центру и 4 квадрантам
4  embed       MobileCLIP-S0 INT8 через ONNX Runtime по thumbnail
5  provenance  точные связи (§4.2) → предварительные семейства и роли
6  match       брутфорс GEMM + popcount → кандидаты
               SSIM-верификация для T2, ORB+RANSAC для T3
               union-find → достройка семейств
7  series      группировка серий, скоринг кадров
8  classify    zero-shot категории
9  quality     скоринг keeper внутри семейства
10 plan        правила → план действий, счётчики
11 apply       перенос в карантин, верификация, журнал
```

Стадии 0-4 идемпотентны по ключу `(path, size, mtime, inode)` и
чекпоинтятся — многочасовой прогон можно прервать и продолжить.
Стадии 5-10 работают только по SSD-кэшу, перезапускаются за секунды с
любыми порогами.

## 6. Схема БД

SQLite + WAL на NVMe-кэше. Тамбнейлы — отдельный content-addressed стор
`thumbs/ab/cd/<blake3>.jpg` (≈1.5 GiB), не в базе: проще переносить.

```sql
CREATE TABLE runs(
  id INTEGER PRIMARY KEY, started_at INTEGER, finished_at INTEGER,
  roots TEXT, tool_version TEXT);

CREATE TABLE files(
  id INTEGER PRIMARY KEY,
  path TEXT NOT NULL UNIQUE,
  disk TEXT NOT NULL,              -- disk1/2/3: шардинг и per-disk карантин
  dev INTEGER, inode INTEGER, nlink INTEGER,
  size INTEGER NOT NULL, mtime INTEGER NOT NULL,
  kind TEXT,                       -- image/video/sidecar/catalog/derived/other
  format TEXT,                     -- по magic bytes
  width INTEGER, height INTEGER, bit_depth INTEGER, orientation INTEGER,
  blake3 BLOB, pixel_hash BLOB,
  phash INTEGER, dhash INTEGER, phash_crops BLOB,   -- 5 × u64
  thumb_key BLOB,
  excluded_reason TEXT,            -- lrdata/system/too-small/appledouble/...
  first_seen_run INTEGER, last_seen_run INTEGER);

CREATE TABLE meta(
  file_id INTEGER PRIMARY KEY REFERENCES files(id),
  taken_at INTEGER, taken_at_source TEXT,   -- exif/filename/path/mtime
  camera_make TEXT, camera_model TEXT, body_serial TEXT, lens TEXT,
  iso INTEGER, shutter TEXT, aperture REAL, focal REAL,
  shot_seq INTEGER,                -- SonyImageNumber / ShutterCount
  burst_id TEXT,                   -- BurstUUID / ContentIdentifier
  gps_lat REAL, gps_lon REAL,
  software TEXT,
  xmp_document_id TEXT, xmp_original_document_id TEXT, xmp_derived_from TEXT,
  dng_original_raw TEXT,
  jpeg_quality INTEGER);           -- оценка по таблицам квантования

CREATE TABLE lr_catalogs(
  id INTEGER PRIMARY KEY, path TEXT, name TEXT,
  schema_version TEXT, indexed_at INTEGER, is_backup INTEGER);

CREATE TABLE lr_refs(
  catalog_id INTEGER REFERENCES lr_catalogs(id),
  file_id INTEGER REFERENCES files(id),
  rating INTEGER, color_label TEXT, pick_flag INTEGER,
  has_develop_edits INTEGER, is_virtual_copy INTEGER, stack_id TEXT,
  collections TEXT,
  PRIMARY KEY(catalog_id, file_id));

CREATE TABLE embeddings(
  file_id INTEGER PRIMARY KEY REFERENCES files(id),
  model TEXT, vec BLOB);

CREATE TABLE families(
  id INTEGER PRIMARY KEY,
  key_kind TEXT,      -- shutter_id / xmp_chain / dng_link / perceptual
  confidence REAL, taken_at INTEGER, camera TEXT,
  representative_file INTEGER REFERENCES files(id));

CREATE TABLE family_members(
  family_id INTEGER REFERENCES families(id),
  file_id INTEGER REFERENCES files(id),
  role TEXT, parent_file INTEGER REFERENCES files(id),
  role_evidence TEXT,          -- json: на чём основана роль
  tier TEXT,                   -- T0..T4 относительно родителя
  quality REAL, quality_breakdown TEXT,
  PRIMARY KEY(family_id, file_id));

CREATE TABLE series(
  id INTEGER PRIMARY KEY,
  kind TEXT,                   -- burst / bracket / pixel-shift / timelapse
  started_at INTEGER, camera TEXT,
  best_family INTEGER REFERENCES families(id),
  protected INTEGER);          -- pixel-shift: запрет на удаление внутри

CREATE TABLE series_members(
  series_id INTEGER REFERENCES series(id),
  family_id INTEGER REFERENCES families(id),
  sharpness REAL, exposure REAL, eyes_open REAL, aesthetic REAL,
  rank INTEGER, locked INTEGER,
  PRIMARY KEY(series_id, family_id));

CREATE TABLE categories(
  id INTEGER PRIMARY KEY, name TEXT, prompt TEXT,
  threshold REAL, enabled INTEGER);

CREATE TABLE file_categories(
  file_id INTEGER REFERENCES files(id),
  category_id INTEGER REFERENCES categories(id),
  score REAL, PRIMARY KEY(file_id, category_id));

CREATE TABLE derived_bundles(
  id INTEGER PRIMARY KEY,
  path TEXT NOT NULL UNIQUE,
  disk TEXT NOT NULL,
  kind TEXT NOT NULL,          -- lr-previews / lr-smart-previews / lr-helper /
                               -- co-cache / on1-cache / thumbs-db / appledouble / ...
  owner_ref TEXT,              -- путь к .lrcat, если владелец определён
  file_count INTEGER, size INTEGER, newest_mtime INTEGER,
  regenerable INTEGER,         -- 0 = удалять запрещено
  blocked_reason TEXT,         -- catalog-open / originals-missing / not-regenerable
  rebuild_cost_hint TEXT,
  scanned_run INTEGER);

CREATE TABLE policy(
  id INTEGER PRIMARY KEY, kind TEXT, expr TEXT, weight REAL, enabled INTEGER);

CREATE TABLE plan(
  id INTEGER PRIMARY KEY, file_id INTEGER REFERENCES files(id),
  op TEXT,                     -- keep / quarantine / recategorize / reorganize
  dest TEXT, reason TEXT,
  decided_by TEXT,             -- policy / user
  decided_at INTEGER);

CREATE TABLE journal(
  id INTEGER PRIMARY KEY, plan_id INTEGER REFERENCES plan(id),
  op TEXT, src TEXT, dst TEXT, size INTEGER, blake3 BLOB,
  applied_at INTEGER, verified INTEGER, undone_at INTEGER);
```

В реализации таблицы `plan` нет: план дедупа и план раскладки считаются
заново из ролей и дат каждый раз — хранить решение, которое устарело вместе
с индексом, опаснее, чем пересчитать. Журнал остаётся единственной записью
о том, что было сделано, с операциями `quarantine`, `quarantine-file` и
`organize`; у последней `src` и `dst` — это и есть маппинг путей раскладки.

Индексы: `files(blake3)`, `files(pixel_hash)`, `files(size)`,
`files(dev,inode)`, `files(disk)`, `meta(taken_at)`,
`meta(body_serial, shot_seq)`, `meta(dng_original_raw)`,
`meta(xmp_document_id)`, `family_members(file_id)`.

## 7. Границы модулей

```
pc-core        типы, определение диска и точки монтирования, кэш тамбнейлов
pc-walk        обход, шардинг по дискам, фильтры, стоп-листы, бандлы
pc-image       magic-sniff, EXIF/XMP, разбор TIFF/IFD, превью, тамбнейлы
pc-hash        blake3, pixel-hash, pHash/dHash, crop-hashes, SSIM
pc-family      точные связи, перцептивные кандидаты, роли, скоринг keeper
pc-lightroom   чтение .lrcat только на чтение, проверка наличия мастеров
pc-organize    дата по лестнице источников, события, план раскладки
pc-apply       карантин, откат, purge, журнал, переносы раскладки
pc-db          SQLite, миграции, запросы
pc-work        общий скан/индекс для CLI и фоновых задач веба
pc-api         axum + встроенный фронтенд
pc-cli         команды
pc-desktop     окно Tauri (Windows, macOS) поверх pc-api; каталог данных

Ещё не написан: pc-embed (ONNX, эмбеддинги и категоризатор).

Серии, ранжирование кадров, виды и политика с планом вошли в pc-family
(модули `series`, `categories`, `plan`), метрики качества — в pc-image
(`metrics`).

Категоризация разделилась надвое против исходного плана: признаки, которые
измеряются по пикселям (сканы, документы, скриншоты, пустые кадры), не
требуют модели и уже работают; смысловые виды («фото счётчика») требуют
эмбеддингов и ждут pc-embed.

Отклонения от исходного плана, принятые при реализации:

* **libraw и mozjpeg-sys не нужны.** Разбор IFD на чистом Rust достаёт
  встроенное превью из любого TIFF-контейнера, а `scale_denom` не окупается
  при корпусе такого размера.
* **pc-provenance, pc-match и pc-quality объединены в pc-family** — они
  работают над одними данными и делят union-find.
* **pc-decode переименован в pc-image.**
```

CLI:

```
photo-cleanup scan    --root /mnt/disk2/data/media/foto --root /mnt/disk3/... \
                      --db /appdata/pc.db --exclude-from excludes.txt

photo-cleanup derived clean --kind lr-previews [--min-size 100M] [--dry-run]

photo-cleanup serve   --bind 0.0.0.0:8080
```

## 9. Интерфейс

Веб. Один бинарь со встроенной статикой, JSON API, SSE для прогресса.
На Windows и macOS тот же интерфейс открывается в окне Tauri
(`pc-desktop`, см. DESKTOP.md) — фронт тот же, сервер тот же.

### 9.1 Экран семейства — дерево, а не сетка

```
📷  DSC01234 · 14.07.2019 18:32:05 · A7 III · 24 МП        6 файлов, 61 МБ
│
├── ORIGINAL    DSC01234.ARW       24.1 MB  6000×4000  ★★★★☆  LR: Main library
│   └── sidecar DSC01234.xmp
├── CAMERA JPG  DSC01234.JPG        8.2 MB  6000×4000         из камеры
├── CONVERTED   DSC01234.dng       22.8 MB  6000×4000         OriginalRawFileName
├── EXPORT      DSC01234-Edit.jpg   4.1 MB  6000×4000         xmpMM:DerivedFrom
│   ├── COPY    DSC01234-Edit.jpg   4.1 MB  идентичен         /Backup/foto/2019/
│   └── RESIZE  DSC01234-Edit.jpg    380 KB 1200×800          /Web/
└── RESIZE      IMG_20190714.jpg     180 KB 1080×720          /Telegram/
```

Отступы показывают происхождение. За секунду видно, что ARW, JPG и DNG —
три разных объекта одного кадра, а не три копии.

### 9.2 Политика по ролям — одно решение вместо тысяч

```
Удалять:  COPY [x]   RESIZE <2 МП [x]   EXPORT [ ]   CAMERA-JPG [ ]   CONVERTED [ ]
→ 19 332 файла, 214 ГиБ
```

Счётчик пересчитывается мгновенно (всё на SSD). Руками разбирается только
то, где провенанс не определился.

Дефолт по решению пользователя: RAW и камерный JPEG держим оба,
экспорты храним отдельно и не удаляем.

### 9.3 Серии и лучший кадр

Группировка: `DateTimeOriginal` ± 3-10 с, та же камера, `BurstUUID`,
подтверждение эмбеддингом.

Скоринг:
- резкость — вариация лапласиана по области с верхним квантилем градиента,
  не по всему кадру (боке ломает глобальную метрику);
- различение смаза и расфокуса по анизотропии направленных градиентов;
- экспозиция — доля клиппинга в тенях и светах, энтропия гистограммы;
- эстетика — NIMA поверх уже посчитанного эмбеддинга (~50 MFLOP);
- **открытость глаз** — детекция лица (YuNet, ~1 мс) + eye aspect ratio по
  5 точкам. Идентификация не выполняется, эмбеддинги лиц не считаются и не
  хранятся. Отдельный флаг. Без этого моргнувший кадр не отличить.

### 9.4 Категоризатор — zero-shot, без разметки

Косинус эмбеддинга изображения к эмбеддингам текстовых промптов. Текстовая
часть считается один раз, классификация 50k файлов — секунды. Новая
категория добавляется вводом фразы, переиндексация не нужна.

Стартовый набор: сканы документов, счётчики, чеки, скриншоты, доски,
удостоверения, мемы с текстом, люди, пейзажи.

Для документов дополнительно дешёвый не-NN признак: доля текстовых регионов
(MSER / stroke width), почти бинарная гистограмма, соотношение сторон A4 —
часто точнее CLIP на сканах.

Действие для категорий — перенос, не удаление. Отдельная фаза от дедупа.

### 9.5 Остальные экраны

- **Дашборд**: возвращаемое место по тирам и ролям, разбивка по форматам, прогресс.
- **Регенерируемые данные**: превью Lightroom и кэши — победа без риска (§10).
- **Сравнение**: два кадра, синхронный зум, diff.
- **Правила**: приоритеты путей и форматов.
- **План и применение**: dry-run, дельта по месту, выполнение, откат.

Клавиатура обязательна везде: J/K навигация, Enter принять, Space сменить
keeper, X пропустить. Тысячи семейств мышкой не разобрать.

## 10. Очистка регенерируемых данных

Самостоятельная функция, не зависящая от дедупа. Не требует декодирования,
эмбеддингов и сравнения — только обход, сопоставление с правилами, перенос и
журнал. Задумывалась ради ≥92 GiB превью Lightroom; после решения
пользователя 2026-10-06 (§10.0) Lightroom она не трогает, а после двух
независимых проверок (el-wda81, el-2rpxq) не переносит и системные файлы.
Сейчас `derived clean` **не переносит ничего**: она показывает опись и для
каждого найденного — почему оно остаётся.

### 10.0 Lightroom не трогается вообще (el-126jk)

Решение пользователя 2026-10-06: «каталоги лайтрум не надо трогать вообще».
`scan`, `derived list`/`derived clean` и веб («Превью и кэши») не выбирают,
не планируют и не переносят **ничего из Lightroom**: `*.lrcat`,
`*.lrcat-data`, любые `*.lrdata` (Previews, Smart Previews, Helper, прочие),
`.lrprev`, резервные копии — и ничего внутри таких папок. Правило одно,
`pc_core::derived`, и спрашивают его все пути:

* **по пути целиком** — любая часть пути с расширением `.lr…` (то же
  правило, что у `purge`, `pc-apply::is_lightroom`), часть с «lightroom» в
  имени или папка `Backups`/`Backup`; регистр по `to_lowercase`, хвостовые
  точки и пробелы отбрасываются (`Backups. ` на SMB — это `Backups`).
  NFC/NFD отдельно не сворачиваются, и это не нужно: каноническая
  (де)композиция не порождает и не убирает ASCII-букв, а образцы — ASCII.
  Две последние приметы шире решения — мусор в `Backups` или «Lightroom …»
  тоже остаётся; лишний файл стоит одного решения. Тем же правилом (и тем же
  свёртыванием) держатся библиотеки, владеющие содержимым:
  `.photoslibrary`, `.photolibrary`, `.migratedphotolibrary`, `.aplibrary`,
  `.pvm`, `Photo Booth Library` (`pc_core::is_protected_bundle`,
  `blocked_code = protected-library`);
* **по виду** — все виды `lr-*` (`DerivedKind::is_lightroom`).

Обход распознаёт такие папки без учёта регистра (`PREVIEWS.LRDATA`,
`X.LRCAT-DATA`, `Old.lrlibrary`) и внутрь не заходит; опись показывает их
с причиной «Lightroom is never touched / данные Lightroom не трогаются
никогда» (`blocked_code = lightroom`). Причина вычисляется и из пути при
чтении, поэтому база, отсканированная до правила, где у превью блокировки
нет, тоже ничего не предлагает (`Bundle::refusal`). Переноса бандла в
коде нет вовсе (el-1bzcw): ни `Bundle::removable`, ни
`pc_apply::quarantine`/`quarantine_many`/`derived_gate` больше не
существует — отказ, стоящий перед работающим переносом, был бы переносом
на расстоянии одной правки.

**Системные файлы не переносятся** (el-126jk, суженный контракт после
el-2rpxq). Две проверки подряд находили файл, который проверка «это мусор?»
пропускала, а не должна была: спутник при кадре в другой форме Unicode
(NFC/NFD), битый `Thumbs.db` без мини-потока, `.DS_Store` с невозможным
корневым узлом. Вместо третьей узкой заплаты класс закрыт конструкцией:

* **спутник никогда не мусор** — `._X`, `X@SynoEAStream`, `X@SynoResource`
  (любое `@Syno…`) не выбираются и не переносятся ни при каком `X`: есть ли
  `X`, надёжно не решить (NFC/NFD, регистр, свёртка имён у каждой ФС своя).
  Поиск пары удалён; спутник едет только со своим кадром (инвариант 8),
  `blocked_code = companion`;
* **`.DS_Store`, `Thumbs.db`, `desktop.ini`, `@eaDir`, `.thumbnails`** —
  не мусор по виду. Строгая проверка `.DS_Store` осуществима (аллокатор
  Bud1, корневой блок, B-дерево), но ничего не доказывает: записи `blob` и
  свободные блоки несут произвольные байты, поэтому и безупречная структура
  не показывает, что в файле нет ничего вашего. `.DS_Store` убран вместе с
  остальными, `blocked_code = system-file`.

Обход такие файлы не записывает вовсе (`._*`, `.DS_Store`, `Thumbs.db`,
`desktop.ini` пропускаются, `@eaDir` и `.thumbnails` — как и раньше,
`is_pruned_dir_name`, внутрь не заходим и не индексируем). Строки вида
`system-junk`, записанные прежней версией, читаются и получают отказ по
виду и пути, без чтения диска (`pc_core::derived::refusal`):
переноса для них нет ни из плана, ни в обход него. Оставленный файл стоит одного
решения, перенесённая по ошибке фотография — фотографии.

**Уже лежащее в карантине** этим правилом не держится: `purge` бандлов и
Lightroom не удаляет (п. 5 §10.3), а откат возвращает их на место —
возврат это «положить обратно», правило переноса его не касается.

Командная строка и веб приходят к одному ответу из одной функции,
`pc_apply::select_derived`: `derived clean` (по умолчанию
`--kind system-junk`) печатает «Not moved: …» с причиной для каждой строки
описи и, если спрошен системный мусор, одну строку о том, почему его в
описи нет; веб показывает те же слова в отказах предпросмотра и у каждой
строки на экране; кнопка переноса при пустом плане недоступна. В `pc-api`
проверок нет. Синтетические образцы для тестов —
`crates/pc-core/src/derived/fixtures.rs` (подключается по пути, в сборку
не входит).

### 10.1 Классификация

Таблица описывает природу данных; **не переносится из неё ничего**
(§10.0). Строки Lightroom остаются как опись: они показываются с причиной и
не выбираются.

| вид | путь | регенерируемо | примечание |
|---|---|---|---|
| Превью Lightroom | `<Catalog> Previews.lrdata/` | да | основной объём; LR пересоберёт при просмотре |
| Smart Previews | `<Catalog> Smart Previews.lrdata/` | **условно** | см. 10.2 — нужны, когда оригиналы недоступны |

| Журнал/лок LR | `*.lrcat-journal`, `*.lrcat.lock` | — | транзиентное; наличие `.lock` означает открытый каталог |

### 10.2 Гейт для Smart Previews

*Исторически; после §10.0 Smart Previews не переносятся вовсе.*

Smart Previews — это lossy-DNG прокси, позволяющие редактировать при
отключённом диске с оригиналами. Пересоздаются только если оригиналы на месте.

Правило: удаление предлагается **лишь когда все оригиналы, на которые ссылается
каталог, найдены на диске**. Проверка — сверка `lr_refs` против `files`.
Хотя бы один недостающий оригинал → бандл помечается
`blocked_reason = originals-missing` и в план не попадает.

### 10.3 Правила безопасности

0. **Ничего из Lightroom** (§10.0) — раньше всех остальных пунктов, по виду
   и по каждой части пути. Пункты 1–2 ниже — исторические гейты превью,
   теперь недостижимые.
1. **Открытый каталог не трогаем.** Наличие `<Catalog>.lrcat.lock` означает,
   что Lightroom работает с ним прямо сейчас. Удаление превью на ходу может
   повредить каталог. Бандл блокируется с `blocked_reason = catalog-open`.
2. **`.lrcat-data` заблокирован на уровне кода**, а не политики. Его нельзя
   выбрать в интерфейсе и нельзя указать в `--kind`.
3. **Единица действия — бандл целиком**, а не отдельные файлы внутри.
   Переносим `X Previews.lrdata/` одним объектом.
4. **Карантин, а не удаление** — как и везде. На том же диске, поэтому
   перенос 92 GiB это серия `rename(2)`, мгновенно.
   **Место от бандла `purge` не возвращает** (п. 5): только человек, удалив
   его из карантина вручную, — командная строка говорит об этом прямо.
5. **Удержание по умолчанию 7 дней**, затем `purge` по явной команде.
   `purge` **не удаляет бандлов вовсе** и ничего из Lightroom (§11.3,
   el-3s9kp, решение пользователя 2026-10-06): бандл в карантине
   называется «оставлено — удалите вручную, если уверены», с путём и
   размером, и остаётся отменяемым. Место от бандла возвращает только
   человек, удалив его сам.
6. Прямого переноса бандла в коде нет (§10.0, el-1bzcw); откат и `purge`
   записей, оставленных прежними версиями, работают как раньше и покрыты
   тестами: такие записи тесты создают сами — строка журнала через
   публичный API базы и явный `rename` одноразовой заготовки
   (`pc-apply/src/legacy.rs`, только `#[cfg(test)]`).

### 10.4 Стоимость пересборки

Предупреждение показывается по каждому каталогу: Lightroom перестроит
стандартные превью при первом просмотре папки. Порядок величины —
десяток-другой минут на пару тысяч кадров, зависит от размера превью в
настройках каталога. Данные при этом не теряются, теряется только время.

Оценка `rebuild_cost_hint` считается из числа снимков в каталоге.

### 10.5 Обход

Каталоги-бандлы определяются по имени и **не раскрываются** (`prune`).
Вместо 24 520 строк в `files` появляется одна строка в `derived_bundles`
с агрегатами. Это ускоряет и сам обход, и все последующие стадии.

### 10.6 Интерфейс

Таблица, сгруппированная по видам (вывод `derived list`):

```
LIGHTROOM PREVIEWS  —  NEVER TOUCHED
  [—] Dogshow_15.02.2025 Previews.lrdata      2 582 files   2.3 GiB
      └─ Lightroom is never touched: Dogshow_15.02.2025 Previews.lrdata

```

`derived clean` при пустой описи системного мусора (обход его не
записывает) печатает одну строку о причине:

```
System junk (.DS_Store, ._*, Thumbs.db, desktop.ini, @eaDir, .thumbnails)
      └─ derived clean moves no system files: neither a name nor a structure proves …
```

Выбор целиком по виду одной кнопкой, бегущий итог сверху, заблокированные
показаны с причиной и не выбираются.

### 10.7 Команды

```
photo-cleanup derived list  [--kind system-junk]
photo-cleanup derived clean [--kind system-junk] [--min-size 100M] [--dry-run]
photo-cleanup derived purge --older-than 7d
```

`--kind lr-…` и `--kind system-junk` принимаются, но ничего не переносят:
каждый бандл назван в «Not moved» с причиной, системный мусор — одной
строкой о том, почему его нет в описи.

### 10.8 Почему это делается первым

Функция независима от всего остального конвейера и при этом прогоняет весь
рискованный слой сантехники — обход с шардингом по дискам, per-disk карантин,
журнал, откат, верификацию — на данных, где цена ошибки равна времени
пересборки превью, а не потере фотографии.

## 11. Бюджет производительности

| стадия | время |
|---|---|
| walk + stat | секунды |
| чтение: 137 GiB обычных + RAW через превью (149 GiB → ~12 GiB) | ~7 мин |
| декод + хеши, 12 потоков | ~1 мин, перекрывается с IO |
| MobileCLIP-S0 INT8, 50k файлов | ~6 мин |
| попарное сравнение (GEMM + popcount) | ~10 с |
| SSIM + ORB на кандидатах | ~2 мин |
| **полный проход** | **~15 мин** |

Память: целевой потолок 4-6 GiB, задаётся флагом. Эмбеддинги 154 MB,
буферы scaled-декода ~0.5 MB на поток. Единственный риск — полный декод RAW
(150-250 MB на кадр), поэтому RAW идёт через превью; файлы без превью — в
отдельную очередь с лимитом 1-2 параллельных декода.

## 12. Безопасность

### 11.1 Массив без избыточности

Паритета нет, отказ любого диска означает потерю данных. Перед фазой apply
нужно либо добавить паритетный диск, либо скопировать `foto/` вовне.
Карантин защищает от ошибок инструмента, но не от смерти диска.

Инструмент показывает это предупреждение на экране применения плана и
требует подтверждения.

### 11.2 Карантин на том же диске

Перенос внутри одного диска — `rename(2)`, мгновенно. Перенос между дисками
или через `/mnt/user/` — полное копирование. Поэтому карантин пишется как
`/mnt/diskN/.photo-quarantine/<зеркало пути>/` на том диске, где лежал файл.
Откат — тоже rename, тоже мгновенный.

**Rename без замены (el-usdqi).** Все переносы `pc-apply` — apply в карантин
(кадр, спутники `.xmp`/`.aae`/`._*`, каталоги-бандлы), откат в архив,
`organize` и его откат, уборка служебных файлов, сверка прерванной
операции, усыновление сироты — идут через одну границу: единица переноса
`unit::move_unit` → привязанный перенос `bound::rename_bound` →
`pc_core::disk::rename_no_replace`:
`renameatx_np(RENAME_EXCL)` на macOS, `renameat2(RENAME_NOREPLACE)` на
Linux, `MoveFileExW` без `MOVEFILE_REPLACE_EXISTING` и без
`MOVEFILE_COPY_ALLOWED` на Windows. Та же реализация (`rename_no_replace_at`)
обслуживает перенос данных в `pc-desktop`. Прежнее «`exists()`, затем
`rename`» молча заменяло файл, который Lightroom, синхронизация или импорт
успели создать между проверкой и переносом, и не видело висячую symlink.
Теперь занятая цель — отказ «цель уже существует и не будет заменена:
`<путь>`»: оба файла целы, запись журнала `failed` с этим текстом
(apply/organize). Спутник, чья цель занята, не даёт уехать и кадру: кадр со
спутниками — одна единица (ниже), она отказывается целиком, ничего не
переносится; прогон идёт дальше. Предварительные `exists()` в
`organize`/`adopt`/уборке остались только ранним ответом (через
`symlink_metadata`, видят и висячую ссылку).

**Предпроверка только читает (el-23goa).** `check_candidates`/
`check_organize` и предпросмотр веба вычисляют назначения и
спрашивают том, ничего не записывая: ни `.photo-cleanup-quarantine`, ни
заметки о раскладке. Назначение, которое не вычисляется (другой диск у
заданного карантина, нечитаемый путь), — отказ всего прогона до первого
переноса, а не пропуск; уже исчезнувший файл отказывается сам по себе.
Заметка о раскладке собранного карантина (`where-these-came-from.json`)
пишется только в `admit` — после проверки файла и хранителя и после ответа
тома, перед записью журнала. Она не идёт по символической ссылке
(`O_NOFOLLOW`), не пишет в файл с другим именем (жёсткая ссылка), в
содержимое, которое не разбирается как раскладка, и не перезаписывает метку
диска, уже записанную для другой точки монтирования: всё это — отказ с путём
и причиной, прогон останавливается, чужое не тронуто. Новая заметка
создаётся во временный файл (`O_EXCL|O_NOFOLLOW`) через удерживаемый
дескриптор каталога карантина и публикуется rename без замены; после
публикации опубликованное сравнивается с записанным (устройство:inode), и
подменённый временный файл своей заметкой не признаётся — отказ, оба файла
названы. Временный файл, который не удалось опубликовать (отказ публикации,
сбой записи или sync), **не удаляется никогда**: он остаётся на месте — или
остаётся чужой файл, оказавшийся под его именем, — и перечисляется в ошибке
и в `Refusal.retained` («Оставлено на месте, не удалялось: …»). Каталоги,
созданные под заметку, тоже не убираются и тоже перечисляются. Новая заметка
пишется в версионированном формате (`format`/`version`); существующая
дописывается, только если она в этом формате, обычный файл с одним именем,
принадлежит этому пользователю и всё ещё тот объект под именем. Заметка
прежнего формата без версии читается и принимается, если метка уже
записана, но не переписывается. Дописывание на месте не атомарно: сбой
посреди записи оставит неразбираемую заметку, и следующий прогон откажет с
её путём — данные не тронуты.

**Ничего не удаляется (решение пользователя 2026-10-04, el-1y8uo B1).** В
POSIX нет условного unlink: между любой проверкой «под именем тот же
объект» и `unlinkat` другая программа с правом записи в каталог может
подменить запись, и удаление заберёт чужое (обзор el-1y8uo воспроизвёл это
на macOS и Linux перехватом самого `unlinkat`). Поэтому apply, откат, сверка,
`organize`, уборка служебных файлов и публикация заметки о раскладке не
вызывают `unlink`/`unlinkat`/`rmdir` ни для чего: пустые каталоги после
`organize` и отката остаются на месте, собственный неопубликованный
временный файл остаётся и называется в отказе (`retained`). Удаляет только
`purge` — отдельная команда с подтверждением; он удаляет только доказанно
свои объекты и только через удерживаемую папку, а сирот (`abandon`) не
удаляет никто (§11.3). Команда
«убрать пустые каталоги» с подтверждением возможна позже отдельной задачей.

**Том без такого вызова — отказ закрыто, без fallback и без
переключателя.** На macOS том спрашивается заранее (`getattrlist`,
`VOL_CAP_INT_RENAME_EXCL`; exFAT его не объявляет, не объявленный считается
отсутствующим): предпроверка отказывает до первого переноса, и на томе не
пишется ничего (проверено на образе exFAT и с умолчательным карантином, и с
заданным несуществующим). На Linux и Windows запроса нет, пробной записи на
томе пользователя тоже нет: отвечает сам вызов (`EINVAL`/`ENOTSUP`), и
отказанный вызов ничего не переносит. Поэтому на Linux прогон может
остановиться не на первом файле, а на первом файле *этого* тома — после
того, как переносы на другие тома уже выполнены.

Остановка — где бы ни встретился отказ тома: основной файл, спутник,
служебный файл уборки, откат прогона `organize undo`, сверка. Тип
`NoExclusiveRename` не превращается в отказ одного файла, дальше ничего не
переносится. Кадр, уже уехавший к моменту, когда его спутник встретил отказ
тома, возвращается вместе со своей единицей: запись `failed` называет
спутник, файл остаётся `present`. Сообщение — про этот файл: что он не перенесён, что переносы
до него выполнены, записаны в журнал и отменяемы, итог прогона до остановки
(«2 объекта, 2 файла, …») и путь отката (страница «Карантин» или
`photo-cleanup derived undo --journal <id>`; для раскладки —
`photo-cleanup organize undo --run <id> --yes`). Остановка по ошибке базы
после физического переноса (запись журнала не создалась, не закрылась,
индекс не обновился) несёт тот же типизированный итог с фактически
перенесённым — кадры, спутники, служебные файлы, байты (el-1y8uo B3). Запись,
которую не удалось закрыть, остаётся `pending` и названа в остановке
(`Stopped.pending`, «Записи журнала #N не удалось завершить…»): то, что по
ней перенесено, возвращается сверкой, а не обычным откатом, и сообщение не
называет её отменяемой обычным путём. Откат, у которого файлы уже вернулись,
а журнал не принял итог, возвращает итог с вернувшимися файлами (`files_back`); запись
сохраняет прежнее состояние, повторный откат по тем же доказательствам её
закрывает. Командная строка печатает тот же итог, что задача веба. Итог — не текст, а
значение `pc_apply::Tally`: снимки, спутники, служебные файлы, объекты и
их файлы, перенесённые байты, записи отката (только целиком: частичного
отката больше нет) и вернувшиеся файлы. Остановка
несёт его типизированно (`Stopped`), и каждый уровень вложенности добавляет
свою долю ровно один раз (`stop_run`), ничего не обнуляя. Командная строка
печатает этот итог и отказы до выхода с ненулевым кодом; задача веба не
считает сама — она складывает итоги действий, которые вернул `pc-apply`, и
отдаёт тот же текст той же функцией. «Обработано» (`control.advance`) —
отдельная величина, не перенесённое.
Fallback на «проверить, затем rename», placeholder или link+unlink не
делается намеренно: каждый из них снова открывает окно или оставляет мусор.

**Unraid и сетевые тома.** Прямые диски массива `/mnt/diskN` (xfs, btrfs)
ядро Linux поддерживает с `RENAME_NOREPLACE` — ожидается, что перенос там
работает. Объединяющая `/mnt/user` (shfs, FUSE), NFS, CIFS/SMB и прочие FUSE
могут отказывать каждому переносу — тогда ни один файл не переедет, и это
закрытый отказ, а не повод обходить его: переключателя «разрешить небезопасно»
нет. Путь для Unraid тот же, что и прежде: `/mnt/diskN`, не `/mnt/user`. На
настоящем NAS это не проверялось — ни на Unraid, ни на сетевых томах;
проверены macOS (APFS, HFS+, exFAT на образах) и Linux в Docker на
локальной файловой системе контейнера.

**Файл признаётся своим только по доказательству (el-usdqi, диагноз
el-5vue3).** До первого переноса журнал записывает в манифест доказательство
каждого файла (`pc_core::proof`, версия 1): устройство, inode, вид, размер и
mtime, время рождения, где том его сообщает (APFS, ext4/xfs/btrfs через
statx); место под blake3 есть, сейчас не заполняется. Откат, его повтор,
сверка прерванной операции и предпросмотр веба читают запись одной функцией
`pc_apply::recovery::classify`: что лежит на каждом из двух мест, читается
без перехода по ссылкам, нечитаемое место — не пустое, найденное
сравнивается с доказательством. Переносится только файл, который лежит в
карантине, доказан своим, а дом свободен. Файл без доказательства на
исходном месте никогда не считается вернувшимся — ни по имени, ни по
старому списку: запись остаётся открытой, файл — в карантине, отказ
называет оба пути. Доказательство другой версии, сменившееся время
рождения или время рождения, которое том больше не сообщает, — отказ, как и
чужой объект. Записи прежних версий (без доказательства): файл, лежащий
ровно по записанному пути карантина, может вернуться — перед переносом с
него снимается доказательство, и повтор узнает его дома; файл дома в такой
записи своим не признаётся никогда. Что делать, когда исходное место занято, — выбор пользователя, для таких
записей и для новых одинаково («Откат на занятое место», ниже, el-14vx0).
Сверка прерванной записи прежних версий делает то же: доказательство
снимается с файлов по записанным путям карантина и **записывается до первого
переноса** (el-1y8uo B4), так что повтор узнаёт своё по доказательству, а
не по имени.

**Нечитаемое доказательство — отказ, а не «запись без доказательства»
(el-1y8uo B2).** Манифест и доказательство читаются строго: неизвестный ключ,
неизвестный вид объекта, повреждённый JSON — это доказательство, которое
эта версия не понимает, а не его отсутствие. Такая запись
(`JournalEntry::manifest_unreadable`, сырой текст как записан) не
откатывается, не сверяется, не удаляется `purge` и в предпросмотре веба
отказывается: ничего не перемещается, запись не переписывается, отказ
называет оба пути и сам записанный текст. Доказательство другой версии,
которое разбирается, по-прежнему отказывается при сравнении (`Unprovable`).
Пути такой записи по-прежнему считаются своими при поиске сирот в
карантине.

*Остатки:* устройство:inode может быть выдано заново после удаления файла;
размер, mtime и время рождения сужают это окно, но не закрывают его на томе
без времени рождения.

**Переносится проверенный объект, а не то, что носит имя (el-3wizg, D8
диагноза el-5vue3).** Раньше apply сравнивал пиксели кандидата и хранимого
файла по пути и затем переносил по пути же: подменённый под тем же именем
файл, подменённая папка выше или подменённый хранимый файл уезжали
непроверенными. Теперь (`pc_apply::bound`, macOS и Linux):

- кадр открывается **до** проверки — через дескриптор своей папки, без
  перехода по ссылке на имени (`openat(O_NOFOLLOW)`); пиксели кадра и
  хранимого файла читаются через эти открытые файлы, так что сравнено ровно
  то, к чему привязан перенос. Кандидат или хранимый файл, являющийся
  символической ссылкой, отказывается;
- дескриптор папки держится от проверки до переноса, и перенос —
  `renameat` относительно него (и относительно открытой папки назначения),
  без замены: подмена папки выше не перенаправляет перенос;
- **непосредственно перед** `renameat` имя перечитывается через
  удерживаемую папку и сравнивается с доказательством проверенного объекта
  (`pc_core::proof`: устройство, inode, вид, размер, mtime, время рождения),
  открытый файл — тоже; путь к папке обязан по-прежнему вести к
  удерживаемой папке (иначе журнал назвал бы не то место); хранимый файл
  перепроверяется так же (заменён, переписан, исчез). Любое расхождение —
  отказ: ничего не перенесено, запись журнала `failed` с причиной и путём
  (кадра или хранимого файла), файл остаётся `present`;
- **папка назначения удерживается от открытия до конца переноса** (B1
  обзора el-4z6z9). Она не создаётся по пути (`create_dir_all`) и не
  открывается по пути заново: от якоря каждая следующая папка открывается
  или создаётся через дескриптор предыдущей (`openat`/`mkdirat`,
  `O_NOFOLLOW`), и `renameat` идёт в этот дескриптор. Якорь — папка, в
  которой лежит `.photo-cleanup-quarantine` (папка кадра для карантина
  рядом, заданный корень для собранного): сама папка карантина и всё под
  ней — наши и ссылкой быть не могут, ссылка или файл на месте любого
  такого компонента — отказ, ничего не перенесено. Для назначений вне
  карантина (откат домой, `organize`, усыновление) якорь — ближайшая
  существующая папка (её путь может идти через ссылки системы или
  пользователя, `/var` на macOS), всё ниже создаётся через дескрипторы, как
  папки заметки о раскладке (el-usdqi). Непосредственно перед `renameat` и
  после него записанный путь папки спрашивается заново и обязан вести в
  удерживаемую папку;
- **после** `renameat` то, что прибыло, сравнивается с **полным**
  доказательством через удерживаемую папку назначения (B2 обзора
  el-4z6z9) — тем же вопросом `Proof::check_file`, что и перед вызовом:
  устройство, inode, вид, размер, mtime, время рождения, где том его
  сообщает, и blake3 через открытый файл, если доказательство его несёт
  (сейчас не заполняется). В POSIX нет rename, условного по объекту
  источника: между последней проверкой и вызовом имя ещё можно подменить, а
  тот же inode — переписать. Успех требует трёх ответов сразу (el-lvtmk
  R2): прибыл проверенный объект без изменений, записанный путь назначения
  ведёт в удерживаемую папку назначения **и** записанный путь источника
  по-прежнему ведёт в удерживаемую папку источника. Всё прочее
  возвращается в папку, откуда пришло, — без замены, через удерживаемые
  папки — и перенос отказывается: чужой объект, тот же файл, переписанный
  обычной записью (отказ называет причину и доказательства «проверено:
  …; найдено: …»), или проверенный файл, у которого во время переноса
  переместили папку назначения или папку источника. Запись журнала
  `failed`, манифест не переписывается в «перенесено», итог прогона его не
  считает. Где после этого лежит каждый объект, говорится только так, как
  описано ниже («Где объект — только доказанное»).

Привязка общая для всех переносов `pc-apply` (каждый член единицы
привязывается `Held::bind` к своему доказательству до первого переноса
единицы): спутники — каждый к доказательству, снятому при планировании
(подменённый спутник останавливает всю единицу: кадр возвращается и
называется вместе со спутником); бандлы; откат и его повтор — к доказательству из
манифеста; сверка — к доказательству из манифеста или снятому с файла в
карантине перед первым переносом; `organize`, уборка служебных файлов,
усыновление сироты — к доказательству, записанному в манифест до переноса.
Без доказательства (только на Windows, где ничего не переносится) перенос
привязывается к объекту, найденному в начале вызова.

**Где объект — только доказанное (el-3wizg, диагноз el-lvtmk).** Дважды
перенос сообщал «возвращён на место» по пути, который ему *передали*, хотя
папку к тому времени переместила другая программа (B1 обзора el-4z6z9,
B1-R2 обзора el-57qpk): фото лежало в переехавшей папке, а превью отката
говорило «нигде». Правило теперь одно (R1): любое «X лежит в P» — в
отказе, в итоге прогона, в журнале — строится из
`pc_core::whereabouts::Whereabouts`, вычисленного `anchored::locate`
**после последнего переименования объекта в операции и непосредственно
перед тем, как сказать или записать**. Переданные пути появляются только
как «записанный путь», не как место. Три исхода:

- `Verified(P)` — проверено: имя в удерживаемой папке несёт этот объект
  (устройство:inode при удерживаемом открытом файле, так что inode не
  может быть выдан другому), путь к папке — записанный, либо названный
  системой по дескриптору (`F_GETPATH` на macOS, `/proc/self/fd` на
  Linux) — ведёт именно в удерживаемую папку, и `P` целиком несёт объект.
  Слова: «проверено: лежит в P» / «verified at P»;
- `Uncertain { last_known, why }` — доказать не удалось: сказано почему и
  где видели последний раз, с пометкой «не проверено». Где система не
  называет путь по дескриптору (Unix кроме macOS и Linux), подтверждается
  только записанный путь, иначе — `Uncertain`; место не выдумывается;
- `Unlinked` — у удерживаемого файла не осталось ни одного имени: другая
  программа его удалила.

Итог перенос отдаёт типом (`Unmoved`: роль каждого объекта — `checked`,
`changed` или `stranger`, его `Whereabouts` и сторона переноса). Чужой
объект называется там, где доказан; о проверенном файле говорится, где он
по удерживаемому дескриптору, — «проверенный файл не тронут» без
доказательства больше не утверждается (сторонняя программа могла забрать
его уже из карантина). Командная строка и веб показывают одно значение
`pc_apply::Placed` («где: путь — проверено: лежит в …»), веб — в отказах
задачи.

Перед записью в журнал (R4) каждый перенесённый объект — кадр и спутники,
бандл, служебный файл, усыновлённая сирота, вернувшиеся при откате и
сверке — спрашивается **снова**, после всех переименований операции: ход
спутника или другая программа могли переместить папку уже после проверки
кадра. Не подтверждённый там, куда перенесён, или с переместившейся папкой
происхождения объект возвращает назад всю свою единицу (ниже) — «done» с
сомнением в месте не записывается. Это вопрос о месте (устройство:inode
через удерживаемые папки), а не полная сверка доказательства: переписывание
кадра ровно между его проверкой после переноса и переносом спутника им не
ловится — остаток (ж) ниже. Места объектов пишутся дописываемым
событием `located` (R5: роль, записанные `src`/`dst`, `held` — у операции
ли он, его `Whereabouts`, доказательство). Манифест не переписывается,
статусов и миграций не добавлено: `located` лежит в `journal_events.data`
и читается в `JournalEntry::located`. Откат, его превью и сверка смотрят
по последнему `located` объекта, находящегося у операции (`held`), вместо
записанного `dst` — и решают по-прежнему только по доказательству
(`classify`); путь из `located` — место, где искать, не основание. Чужие
объекты не переносятся никогда. Запись `done` с `located` (решение D5)
теперь возникает только из отката, который не смог ни закончиться, ни
вернуть единицу целиком (например, папку переместили во время отката);
запись `failed` ничего своего у операции не держит и к откату не
предлагается (`undo_offered` — только `done`).

**Кадр со спутниками — одно целое (решение пользователя (c) от
2026-10-05; обзор el-4pk1q B1-R3..B4-R3).** Три раунда обзора находили
половину, которую пропустил один из шагов: правку `.xmp`, оставшуюся в
карантине за записью, закрытой как «отменено»; отказанный спутник,
записанный по уже несуществующему пути; сверку, вернувшую кадр и
потерявшую его из виду. Вместо ещё одного слоя учёта половин половин больше
нет. Кадр и все его спутники (`.xmp`, `.aae`, `._*`) — неделимая единица
для каждой операции: apply, откат, сверка, `organize`, уборка
(`pc_apply::unit`):

1. До первого переноса каждый член единицы открывается и удерживается
   через свою папку и сверяется со своим доказательством, место каждого
   спутника в цели свободно. Любое сомнение — отказ всей единицы, ничего не
   переносится.
2. Если перенос любого члена отказан или перед записью любой член не
   доказан там, куда перенесён, все уже перенесённые члены возвращаются,
   новейший первым, в удерживаемые папки, откуда взяты, без замены
   (`Arrived::give_back`; окно между его сверкой и `renameat` — остаток (з)
   ниже). Запись — отказ (`failed`), не «done». Если
   вернуть не удалось и объект единицы остался у операции, прогон
   останавливается, запись остаётся открытой (`pending` для переноса
   вперёд и сверки, `done` для отката), место **каждого** члена — доказанное
   или последнее известное — дописывается событием `located` (вид `kept`)
   и показывается (`Stopped.placed`, `Stopped.pending`); ничего не
   удаляется. Чужой объект, который не удалось вернуть, тоже
   останавливает прогон.
3. Откат и сверка — только целиком: только когда **каждый** член доказан —
   дома или у операции со свободным домом. Иначе отказ всей записи, запись
   остаётся открытой, отказ перечисляет каждый член с его местом. Нет
   частичного отката, частичной сверки, «уже вернулось» для одного члена,
   пока другой под сомнением; предпросмотр веба отказывает так же. Член,
   уже доказанный дома, не переносится и во время возврата остальных не
   удерживается — его подмена ровно в этот момент не ловится, остаток (е)
   ниже.
4. Объект, изменившийся после проверки (`changed`) и оставшийся у
   инструмента, автоматически не восстанавливается: превью, откат и сверка
   отказывают и называют его путь — «верните его вручную»; запись остаётся
   открытой. `status` показывает такие объекты с той же пометкой.
5. Цена: при вмешательстве другой программы кадры отказываются чаще —
   спутник, который не может поехать, оставляет на месте и кадр. Это
   намеренно: лишний файл стоит одного решения, недостающий — фотографии.

Все переносы держат сам файл (R7): и кадр apply, и источник отката,
сверки, `organize`, уборки, спутников, бандлов и усыновления открывается
через удерживаемую папку (`O_NOFOLLOW`) до проверки и держится до записи —
символическая ссылка не открывается и проверяется по метаданным, как
прежде.

Папка прогона, переставшая вести к своей удерживаемой папке, останавливает
прогон (решение D2): после своего файла (возвращённого или названного),
остальные — «не перенесён: прогон остановлен, папку прогона переместили».
Корни прогона удерживаются с его начала (`RunRoots`) в `apply`,
`organize` и задаче веба; перенос, заметивший перемещение своей папки,
останавливает так же (`FolderMoved`; откат прогона `organize` и задачи веба
— тоже). `purge` отказывает записи с любым `located` (решение D6b):
удаление по записанным путям, которые больше не доказаны, не делается, и
поиск объекта по доказательству для удаления тоже не делается (el-3s9kp,
§11.3).

**Модель угроз (решение пользователя (a) от 2026-10-05, el-3wizg).**
Код, перемещающий фото, защищает от обычных одновременных изменений —
Lightroom, клиенты синхронизации, Finder, другие обычные программы — и
правдиво сообщает о каждом сомнении. Нарочное чередование ровно между двумя
системными вызовами инструмента (подстроенное по времени вмешательство
процесса того же пользователя) — вне модели: то же исключение, что принято
для хранилища десктопа в el-2xri («намеренно вредоносный процесс того же
UID»). В POSIX нет атомарных операций над несколькими файлами, так что
такие окна как класс закрыть нельзя; перечисленные ниже — сужены, не
закрыты. Ни в одном из остатков ниже файл не удаляется и не
перезаписывается: перенос всегда без замены, удаления нет.

*Остаток окна, честно:* (1) хранимый файл может измениться после последней
проверки и до `renameat` — микросекундное окно, и изменение хранимого после
переноса тем более вне этой проверки; кадр при этом остаётся в карантине и
откатывается. (2) Подмена кадра ровно между проверкой и вызовом не
предотвращается, а обнаруживается после: чужой объект на мгновение
проходит через карантин и возвращается; если сбой питания или убийство
процесса придётся ровно между `renameat` и проверкой после него, чужой
объект останется в карантине под записью `pending` — сверка сравнит его с
доказательством и своим не признает. (3) Переписывание на месте того же
inode до того же размера с подделанным mtime — остаток доказательства
(выше): обычная перезапись — другого размера или того же размера с
обычным новым mtime — ловится и до, и после вызова; не ловится только
подделанный назад mtime при том же размере и времени рождения, пока
доказательство не несёт blake3. (4) Вне модели (выше): нарочное
вмешательство того же пользователя ровно между системными вызовами, а
также другой пользователь или root, способный менять владельца,
монтировать поверх или писать в удерживаемый файл в обход. (5) Пространства имён: подмена или перемещение
папки назначения, папки источника или их предков во время переноса — до
вызова отказ, после — возврат, место каждого объекта доказано или сказано
как недоказанное. Не закрыто: (а) ссылка выше якоря или на месте ближайшей
существующей папки назначения вне карантина, поставленная *до* начала
переноса, неотличима от собственной ссылки пользователя и проходится —
записанный путь тогда ведёт к файлу через неё; (б) перемещение папки
**после** того, как операция записана (el-lvtmk #20, решение D3): например,
пользователь переименовал папку архива вместе с карантином рядом с фото —
откат отказывает, называя оба пути, ничего не переносит; поиск по
доказательству — задача el-6byp2; (в) прерывание (сбой питания, убийство
процесса) после переноса и одновременное перемещение папки карантина
(el-lvtmk #15) или прерывание после компенсирующего возврата в
переместившуюся папку (#16): запись остаётся `pending`, сверка отказывает с
причиной, ничего не двигается; поиск — el-6byp2 (решение D1); (г) сторонняя
программа, забравшая прибывший файл (решение D4): не предотвращается, но
говорится правдиво — проверено, где он (по удерживаемому файлу), или
`Unlinked`, или «место не подтверждено»; (д) между последним `locate` и
фиксацией записи журнала проходят микросекунды — перемещение папки ровно
там записано не будет и останется в (б); (е) спутник, уже доказанный
дома, подменён у себя дома ровно во время возврата кадра откатом или
сверкой (el-6anwy B1-R4): домашний член в возврате не удерживается и
после него не перепроверяется, поэтому запись может закрыться «отменено»
(`undone`), хотя на имени спутника лежит чужой файл, а исходный спутник
припаркован под другим именем; ни одно событие не называет его место.
Ничего не удалено и не перезаписано: кадр дома, чужой файл и исходный
спутник целы; (ж) кадр, переписанный в карантине ровно между его проверкой
после переноса и переносом спутника (el-6anwy B2-R4): последний вопрос
перед записью спрашивает место (устройство:inode), не полное
доказательство, — запись закрывается «done» с устаревшим доказательством
и размером. Ничего не удалено и не перезаписано; следующий же предпросмотр
отката говорит «размер изменился», откат отказывает всей записи —
вернуть кадр и спутник вручную по пути; (з) `Arrived::give_back` сверяет
прибывший объект и затем вызывает `renameat` без замены в удерживаемую
папку источника — между сверкой и вызовом имя можно подменить
(el-49zg0, оценка el-6anwy, статически, без шва в самом окне). Вызов не
заменяет занятое место и ничего не удаляет; последующий поиск по
удерживаемому дескриптору и итог единицы обнаруживают, что проверенный
объект не там, называют его место (или «не подтверждено») и
останавливают прогон. Пустые папки, созданные под
перенос, как и прежде, не удаляются. (и) `purge` — единственное место, где
файл удаляется, и единственный остаток модели, где страдает чужой объект:
в POSIX нет условного unlink, и объект, подставленный под имя ровно между
последней сверкой и `unlinkat` (через удерживаемую папку), удаляется
вместо проверенного. Это нарочное чередование того же пользователя — вне
модели; обычная программа, положившая файл под имя раньше, отказ получает
(§11.3). Случившуюся подмену видно после вызова по удерживаемому
дескриптору (у проверенного файла не убыло ссылок): запись остаётся
`pending`, событие `purge/partial` называет имя, проверенный файл остаётся
на месте.

**Журнал только растёт.** Каждая попытка отката или сверки, каждый отказ и
успех — отдельное событие в `journal_events` (миграция 020, только
добавление); `note` остаётся читаемым изложением и только дописывается,
прежняя note старой записи — начало её истории. Каждый исход операции —
перенос вперёд (`forward`: `done`, `refused`, `kept`), откат (`undo`),
сверка (`reconcile`), усыновление (`adopt`), начало `purge` — пишется
типизированным событием через `Db::journal_close` вместе со сменой
состояния, в одной транзакции, независимо от того, есть ли человеческая
note; в `data` — JSON с состоянием, перенесёнными парами, отказами и
ошибкой (el-1y8uo B6). `journal_finish` с общим `note/note` остался только
для фикстур. Успешный повтор дописывает
успех и сохраняет прежние отказы. Если записать отказ в журнал не удалось,
это сообщается вместе с самим отказом. Размер записи журнала — перенесённые
байты, а не запланированные; единица, отказанная целиком, в размер карантина
не входит вовсе.

**Спутник с занятым местом** останавливает и свой снимок — в командной
строке и в вебе одинаково: снимок остаётся на месте, отказ называет
спутник. Это правило живёт в `pc-apply` (`unit`); предпросмотр веба
кандидата из-за него не отказывает — отказывает сам перенос.

**Откат на занятое место: выбор пользователя (el-14vx0, решение
2026-10-03).** Откат возвращает единицу только на свободное место. Если
исходное место занято другим файлом или не доказано, что там лежит наш
(запись прежних версий без доказательства — своим файл дома не признаётся
никогда), это **конфликт**: каждый член единицы лежит у операции и доказан
(или лежит ровно по записанному пути карантина в записи без
доказательства), и хоть одно его место занято чем-то недоказанным. Всё
прочее — член изменился, исчез, в карантине чужой, место не читается,
возврат под свободными именами уже начат — не конфликт, а прежний отказ.
Вся логика — `pc_apply::conflict`, одна для командной строки и веба;
`pc-api` только передаёт ответ. То же — для **сверки** незавершённой
записи (`pending`, прежней и новой): если все её файлы лежат в карантине и
единственное препятствие — занятое место, сверка предлагает те же выборы
той же функцией (`reconcile_conflict`, `reconcile_undo_with`,
`reconcile_reviewed`), события пишутся под фазой `reconcile`, запись при
«оставить» остаётся `pending` (el-4cmzu B3).

Конфликт (`Conflict`) называет возвращающуюся единицу (кадр первым, затем
спутники: где лежит, куда возвращается) и **существующую единицу** —
занимающие места объекты, а если занято место кадра, то и собственные
спутники лежащего там кадра (`.xmp`, `.aae`, `._*`): они идут со своим
кадром, сиротами не остаются. Каждый занимающий объект записывается с
доказательством, снятым в момент показа выбора. Выборы, по конфликту и
«для всех остальных»:

1. **keep — оставить в карантине** (по умолчанию). Ничего не переносится,
   запись остаётся `done`, отказ (`ConflictKept`) называет точный путь в
   карантине и место, куда возвращать.
2. **replace — заменить существующий.** Существующая единица сначала
   уходит в карантин рядом со своей папкой отдельной записью
   `quarantine-file` того же прогона — с манифестом и доказательствами, то
   есть сама откатывается и удаляется только `purge`, как любой карантин.
   Её имя в карантине — своё, а если занято (обычно там и лежит
   возвращающийся файл) — `_1`, `_2`… Затем обычный откат по
   доказательству. Ничего не удаляется (инвариант 1).
3. **rename-existing — переименовать существующий** в свободное имя рядом
   (`IMG_1.CR2` со `IMG_1.xmp`; `_2`, если занято), записью `set-aside`,
   которая сама откатывается; затем обычный откат.
4. **rename-returning — вернуть под свободным именем**, существующее не
   трогать. Индекс следует за файлом, если под новым именем строки нет.

Спутники переименовываются вместе с кадром по одному правилу
(`IMG.xmp` → `IMG_1.xmp`, `IMG.CR2.xmp` → `IMG_1.CR2.xmp`,
`._IMG.CR2` → `._IMG_1.CR2`); имя, которое правило не меняет, делает
переименование недоступным. **Свободное имя не ищется взглядом**: каждый
перенос — тот же `move_unit` → `rename_no_replace`, и имя, оказавшееся
занятым в момент переименования (`Taken`, в том числе созданное другой
программой между выбором и переносом), ничего не переносит — единица
возвращается целиком, берётся следующее имя. Предварительный взгляд только
пропускает уже занятые имена. Предел — `_999`, дальше отказ с путями.

**Перечитать всё непосредственно перед первым переносом (el-4cmzu B1,
B2).** Выбор мог занять у человека минуты. Перед первым переносом весь
конфликт читается заново — запись, её список, возвращающаяся единица по
доказательству, существующий кадр со **всеми** спутниками, какие у него
есть сейчас, — и любое отличие от того, на чём делался выбор (появился
`IMG.aae`, изменён возвращающийся `.xmp`, исчез занимающий), — отказ,
событие `refused`, ничего не перенесено. Для replace/rename-existing
возвращающаяся единица доказывается целиком **до** того, как тронута
существующая: единица, которая не сможет вернуться, ничего не вытесняет.
В записи без доказательства мерой служит то, что лежало по записанному
пути карантина в момент показа выбора (`Returning::seen`); оно же
записывается в манифест перед переносом. Наконец, перенос существующей
единицы после последнего `rename` ещё раз смотрит на её место: новый
спутник её кадра, появившийся *во время* переноса, возвращает всю единицу
обратно — единица не делится, успех не объявляется.

**Связь с доказательством.** Занимающие объекты переносятся привязанными к
доказательству из конфликта (`Held::bind`): подменённый или изменённый
после показа выбора — отказ всей единицы, запись `set-aside`/
`quarantine-file` закрывается `failed`, ничего не перенесено. Выбор из веба
(`Reviewed`) действует, только пока конфликт, прочитанный сейчас, равен
просмотренному (те же файлы и те же объекты по доказательству); иначе —
отказ «на исходном месте что-то изменилось с предпросмотра». Конфликт,
которого при предпросмотре не было (место занял чужой файл уже после),
получает умолчание keep — никогда не замену. Доказательства занимающих
объектов входят в предпросмотр, поэтому их смена меняет и токен плана.

**Lightroom не трогается (решение 2026-10-06, инвариант 7).** Если любой
путь конфликта — возвращающийся, место в карантине или занимающий —
есть в живом каталоге (полный путь или хвост, как везде) или содержит
часть `.lr…`, предлагаются только keep и rename-returning. Занимающее
место не обычный файл (папка, ссылка) — тоже только эти два. Бандл
(запись `quarantine`) возвращается только на своё место: только keep.
Выбор, которого конфликт не предлагает, — отказ с причиной, ничего не
перенесено.

**Журнал и повтор.** Каждое решение и его итог дописываются событием
`undo` (`reconcile` — для сверки) с `ConflictNote` в `data` (выбор, возвращающиеся и занимающие с
доказательствами, куда отложено, номер записи отложенного): `kept`,
`refused`, `set-aside`, `attempt`. Попытка вернуть под свободными именами
записывается **до** переименования (`returned_as`, читается в
`JournalEntry::returned_as`); повтор после прерывания (кадр уже под `_1`,
спутник ещё в карантине) находит вернувшееся по доказательству — не по
имени — и доводит единицу под теми же именами; чужой файл под записанным
свободным именем своим не признаётся. Остановка после того, как
существующая единица отложена, но до возврата нашей, — типизированный
итог (`Stopped`, `Tally.set_aside`): отложенное остаётся отложенным под
своей откатываемой записью, повторный откат находит место свободным и
идёт обычным путём.

Явное «оставить» — тоже решение и пишется так же, откуда бы ни пришло
(el-4cmzu B4): в вебе оно не элемент плана (ничего не переносит), но идёт
с подтверждённой задачей, и `pc-apply` записывает `kept` и возвращает
`ConflictKept` — отказ в итоге задачи с путём в карантине. Ничего не
переносится, даже если место к моменту подтверждения освободилось; если
конфликт изменился, слова говорят об этом. Предпросмотр по-прежнему
только читает.

**Командная строка и веб.** `derived undo --journal <id>` и
`organize undo --run <id> --yes` принимают `--on-conflict
keep|replace|rename-existing|rename-returning` (ответ на первый конфликт)
и `--all` (на все). На терминале остальные конфликты спрашиваются
(`2a` — этот выбор и все следующие); без терминала — keep. **Все
конфликты показываются и все ответы собираются до первого переноса**
(el-4cmzu B5): `run_conflicts` читает конфликты прогона, команда печатает
их с доступными выборами — и в предпросмотре без `--yes`, и перед
действием, — затем задаёт вопросы и только потом исполняет
`undo_run_reviewed`/`undo_reviewed`; каждый ответ держится, пока конфликт
тот же (`Reviewed`), как в вебе. Веб: в
предпросмотре отката (`journal-undo`, `organize-undo`) и сверки
(`journal-reconcile`) — список
`conflicts` с выборами и словами `pc-apply`; диалог — карточка на
конфликт и «применить ко всем остальным», ответ уходит параметром
`choices` (`{"<id записи>": "<выбор>"}`), предпросмотр пересчитывается.

*Остатки, честно.* (1) Между последней сверкой занимающего объекта и
`renameat` — то же окно, что у любого переноса (§11.2, остаток (2)):
обнаруживается после, объект возвращается. (2) Отложенная единица — не
наша: её доказательство снято в момент выбора, а не при переносе
инструментом, и откат отложенного возвращает её на её имя, только если
оно свободно — иначе тот же выбор. (3) Индекс не узнаёт о переименованном
или отложенном существующем файле до следующей индексации. (4) Свободное
имя может быть «съедено» одновременно созданными файлами до `_999` — тогда
отказ, ничего не перенесено.

**Пустые каталоги** после `organize` и его отката остаются на месте (выше:
ничего не удаляется). Служебные файлы опустевшего каталога по-прежнему
уезжают в карантин той же записью прогона и возвращаются откатом.

**Windows.** Перенос, откат, сверка и запись заметки о раскладке на Windows
отказываются с причиной: идентичность файлов, неследование по ссылкам и
создание через удерживаемый каталог там на настоящей системе не проверены.

**Тестовые швы не попадают в выпуск (el-1y8uo B5).** Возможность `test-seams`
крейта `pc-apply` (крючок перед каждым переносом, для тестов `pc-api`;
крючки вокруг самого `renameat` — только в собственных тестах `pc-apply`)
включается только как dev-зависимость; сборка без отладочных проверок с
этой возможностью — ошибка компиляции (`compile_error!`), так что
`cargo check --release -p pc-apply --features test-seams` не проходит, а
`cargo test --release` для `pc-api` не собирается.
Кросс-компиляция и чтение кода проверкой не считаются.

### 11.3 Журнал и откат

Каждое действие пишется в `journal` до выполнения: src, dst, размер, blake3.
`undo` проигрывает записи в обратном порядке. Полный хеш проверяется
непосредственно перед переносом — в тот момент, когда корректность важна.
Настоящее удаление — отдельная команда после срока хранения.

**Окончательное удаление — только доказанно своего, и никогда — бандлов и
Lightroom (el-3s9kp).** `purge` (`derived purge --older-than … --yes` и
задача веба `derived-purge` с подтверждением «УДАЛИТЬ») — единственная
операция, которая удаляет, после срока удержания и только записи в
состоянии `done`. Раньше она удаляла записанный путь рекурсивно и по пути:
чужой файл под этим именем, папка на месте файла со всем содержимым, папка
карантина, заменённая ссылкой на другую папку, — всё уходило безвозвратно
(el-lvtmk D6/S2). Теперь (`pc-apply::purge`, одно и то же для командной
строки и веба; в `pc-api` проверок нет):

0. *Что не удаляется никогда.* Решение пользователя 2026-10-06: «каталоги
   Лайтрум не надо трогать вообще». `purge` не удаляет **ни одного бандла**
   — папки или файла, перенесённого `derived clean` целиком (превью,
   смарт-превью, helper, прочие `.lrdata`, `@eaDir`, `.thumbnails`,
   системный мусор одним файлом), — и **ничего из Lightroom**, даже одним
   файлом с полностью совпавшим доказательством, хэш включительно: запись,
   у которой хоть один записанный путь — откуда или куда, её собственный
   или любого члена — содержит часть с расширением `.lr…` (`.lrcat`,
   `.lrcat-data`, `.lrcat-wal`, `.lrdata`, `.lrprev`, `.lrlibrary`,
   резервные `.lrcat.zip` и т. п.; `pc-apply::is_lightroom`, регистр по
   `to_lowercase`). Решение принимается по записи журнала, до любого
   обращения к диску (`purge_keeps`). Исход — типизированный `PurgeKept`
   (`KeptWhy::Bundle` или `KeptWhy::Lightroom`): ничего не удалено, запись
   остаётся `done`, в карантине и отменяемой; в историю пишется событие
   `purge/kept` со списком «путь — почему»; в словах — пути в карантине и
   размеры, записанные при переносе, число файлов и «удалите вручную, если
   уверены». Командная строка печатает это в предпросмотре («Kept, not
   deleted …») и в итоге; веб показывает те же слова pc-apply среди отказов
   предпросмотра, в сумму к удалению их не включает, а при выполнении
   проводит запись через тот же `purge_entry_controlled`, так что событие
   пишется и там. Каждый запуск `purge` пишет событие заново — история
   только растёт.

   Почему так. Удаление бандла по списку содержимого и по первым байтам
   каждого файла трижды подряд пропустило необратимое: снимок того же
   размера на месте превью (el-8s63g), подмену с теми же именем, размером и
   форматом (el-wffu8), каталог Lightroom и базу самого инструмента под
   именем `.db`, SQLite под именем `Thumbs.db` и 24-байтный обрывок
   (el-5gr1y): несколько байтов не доказывают, что содержимое можно
   пересобрать. Путь удаления бандла и его список допуска (`contents.rs`,
   список содержимого бандла в журнале) убраны целиком, а не оставлены
   спящими. Освободить место от бандла может человек, удалив его вручную;
   выбор бандлов Lightroom при `derived clean` и `scan` закрыт el-126jk
   (§10.0): ничего из Lightroom больше не переносится.

Остальное — только для файловых записей (`quarantine-file`: снимок и его
спутники):

1. *Достижение.* Каждый объект записи достигается от первой папки
   `.photo-cleanup-quarantine` своего записанного пути вниз — по одной
   папке, `O_NOFOLLOW`, через удерживаемые дескрипторы. Ссылка внутри
   карантина не проходится никогда; ссылка выше него — путь пользователя к
   архиву, как везде (§11.2, остаток (5а)). Путь не в папке карантина —
   отказ.
2. *Доказательство.* Объект открывается через удерживаемую папку без
   следования по ссылке и сравнивается, через открытый дескриптор, с
   доказательством, записанным до первого переноса: устройство, inode, вид,
   размер, mtime до наносекунды, время рождения, blake3 — где он записан
   (сегодня не пишется; записанный пересчитывается целиком через
   дескриптор). Сравнение одно на всех — `Proof::verify`: перенос, откат,
   восстановление и `purge` сравнивают все записанные поля; поле, которое
   нельзя прочитать заново (время рождения, хэш без открытого файла), — не
   совпадение (el-wffu8). Имя в папке обязано вести к открытому объекту.
   Удаляется только обычный файл; папка — никогда (ни записанная, ни
   оказавшаяся на месте файла).
3. *Всё или ничего.* Кадр и спутники — одна единица: хоть один член не
   доказан (чужой, ссылка, папка, устройство, изменился, не читается,
   доказательства нет) — отказ всей записи до первого удаления. Отказ
   пишется событием `purge/refused` со списком «путь — почему»; запись
   остаётся `done`, в карантине и отменяемой. Записи без списка
   перенесённого или без доказательства (сделанные до el-usdqi), с
   нечитаемым списком и с любым `located` отказываются целиком: удалять их
   по путям нечем доказать — их удаляет человек вручную, проверив. Отказ
   по нечитаемому списку пишется тем же событием `purge/refused`, как
   любой другой; сам список не переписывается (el-8s63g B3).
4. *Удаление.* Перед удалением запись становится `pending` (событие
   `purge/begun`). Каждый файл непосредственно перед `unlinkat` сверяется
   снова тем же полным сравнением (через удерживаемый дескриптор, хэш —
   заново, где записан; имя → тот же объект) и
   удаляется через удерживаемую папку, никогда по пути. После вызова
   удерживаемый дескриптор говорит, что ушло: у нашего объекта убыло ссылок
   — удалён он; не убыло — под имя подставили другой (остаток (и) §11.2),
   и запись остаётся `pending` с событием `purge/partial`. Сначала спутники,
   кадр последним. Успех — `purged`, событие `purge/done`.
5. *Итог* — то, что действительно удалено: записи, файлы и байты
   (`Tally.purged_*`; байты — только файлов, у которых ушла последняя
   ссылка, жёсткая ссылка места не возвращает). Командная строка и веб
   показывают одно и то же; отказ записи — отказ этого пункта, прогон идёт
   дальше; остановка на полпути (`PurgeStopped`) несёт удалённое до неё.
   Ошибка *после* удаления — журнал не принял `purged` или индекс не
   обновился — тоже `PurgeStopped` (стадия `Recording` или `Indexing`) с
   тем, что действительно удалено, и событием `purge/unfinished`; запись
   остаётся `pending`, если журнал не принял завершение, и `purged`, если
   принял (el-8s63g B2). Никто из вызывающих не принимает такую ошибку за
   «ничего не удалено»: веб кладёт удалённое в итог задачи, командная
   строка печатает квитанцию («Deleted: …», затем «stopped after
   deleting: …») и завершается ненулевым кодом.
   Отмена в вебе принимается до начала удаления записи (ничего не удалено,
   запись цела); кадр и спутники после первого удалённого уходят вместе.

**Папки.** `purge` не удаляет ни одной папки: ни рекурсивно, ни по пути,
ни пустой. Папки карантина (`.photo-cleanup-quarantine` и зеркало пути в
собранном карантине), созданные инструментом, остаются на месте.

**Windows** — отказ для файловых записей: удаление через удерживаемую
папку и личность объектов там на настоящей системе не проверены. Бандлы и
Lightroom оставляются тем же `PurgeKept`, что и везде.

**Остатки, честно.** (1) Окно между последней сверкой и `unlinkat` (выше и
§11.2 (и)): обнаруживается после, не предотвращается. (2) Остатки самого
доказательства (§11.2): файл, переписанный *на месте* (тот же inode) до
того же размера с подделанным mtime, пока blake3 не пишется; записанный
blake3 проверяется всегда. (3) Ссылка или подмена *выше* папки карантина
ведёт туда, куда ведёт; удаляется там только объект, доказанный своим.
(4) Записи прежних версий без доказательства не удаляются вовсе. (5)
Lightroom узнаётся по именам путей, записанных в журнале: файл Lightroom,
переименованный без `.lr…` и лежащий вне `.lrdata`/`.lrcat-data`, как
файловая запись (дубликат снимка) удаляется по обычному доказательству —
так же, как любой другой подтверждённый дубликат. Ошибка в обратную
сторону (чужой файл с расширением `.lr…`, например `.lrv` камеры)
оставляет файл, а не удаляет. (6) Бандлы, уже лежащие в карантине,
освобождают место только руками человека; `purge` их называет, но не
трогает. (7) Сироты освобождают место тоже только руками человека — см.
ниже.

**Сироты (`abandon`, задача веба `quarantine-purge`) не удаляются вовсе**
(el-63ph1). Сирота — то, что лежит в папке карантина и не принадлежит ни
одной записи журнала `done`/`pending`: по определению для неё нет
записанного доказательства, и сверить то, что лежит по её пути, не с чем.
Раньше `abandon` удалял по пути и рекурсивно всё, что там лежало: чужой
файл, ссылку, папку со всем содержимым, каталог Lightroom. Более слабое
«доказательство» для сирот (имя, размер и время, которые видел обход)
не вводится: ровно его проходит и чужой файл под тем же именем. Поэтому
просмотренная и подтверждённая (`УДАЛИТЬ`) задача по каждой сироте
пишет в журнал строку `abandon` со статусом `failed` (она ничего не
присваивает) и событием `abandon/kept` — путь и причина — и возвращает
типизированный итог `OrphanKept`: путь, размер сейчас (без перехода по
ссылке; у папки — 0, содержимое не обходится), причина — Lightroom (по
любой части пути, `is_lightroom`), папка или «нет доказательства».
Удалённого — ноль; в итоге задачи каждая сирота — отказ этого пункта с
этими словами, «удалите вручную, если уверены», и остаётся в списке
найденного, потому что лежит на месте. Остановка, запрошенная до пункта,
не пишет ничего. Отдельного пути удаления для сирот больше нет: удаляет
только `purge` по доказательству (выше), на Windows — тоже ничего.

### 11.4 Контейнеры

На фазе сканирования `/mnt/disk*` монтируются в Docker read-only.
Запись разрешается только на фазе применения.

### 11.5 Защищённые объекты

- Файлы, упомянутые в живых каталогах Lightroom: могут быть keeper'ом,
  не могут быть кандидатом на удаление без явного снятия защиты.
- Наборы pixel-shift (Sony, 4 кадра со сдвигом сенсора): визуально идентичны,
  SSIM ~0.99. Жёсткий запрет на удаление внутри набора. Детект по
  `SequenceImageNumber` / интервалу в доли секунды.
- `.photoslibrary`: индексируется read-only, внутрь не пишем никогда.
- Companion-группы (RAW + JPEG + xmp + AAE): двигаются только вместе.
- Hardlink / APFS clone: `(dev, inode, nlink)` — удаление не вернёт место.

### 11.6 Ложные срабатывания, требующие защиты

- Однородные кадры (чёрные, белые, засветки) — pHash у всех одинаков.
  Низкая дисперсия → отдельный бакет, автогруппировка запрещена.
- Скриншоты и сканы документов — одинаковая раскладка, разный контент.
  Повышенный порог, обязательная SSIM-верификация.
- EXIF orientation: нормализуем перед хешированием, плюс хешируем 4 поворота.

`.Spotlight-V100`, `.fseventsd`, `.TemporaryItems`, `Thumbs.db`,

| Ф0 | **сделано** — инвентаризация и очистка регенерируемых данных (§10), заодно обкатка обхода, карантина, журнала и отката; окончательное удаление — только доказанно своих файлов, бандлов и Lightroom — никогда (§11.3, el-3s9kp) |
| Ф1 | **сделано** — индекс, провенанс, семейства, роли, политика и план |
| Ф2 | pHash + SSIM (T2) **сделано**; эмбеддинги и ORB для T3 — нет |
| Ф3 | серии и выбор лучшего кадра — **сделано**, кроме детекции лиц |
| Ф4 | виды по измеримым признакам **сделано**; zero-shot на эмбеддингах — нет |
| Ф5 | реорганизация структуры — **сделано** |
| Ф6 | инкрементальный режим и ingest |
| Ф7 | видео (755 GiB — крупнейший потенциал по месту) |

Реорганизация выполняется строго после дедупа: команда отказывается
работать, пока план дедупа не пуст (`--allow-duplicates` снимает запрет).
Схема `YYYY/YYYY-MM-DD_<событие>/`, событие — временной кластер с разрывом
более 6 часов. Полный маппинг путей в журнале, операция `organize`.

Определение даты, по убыванию доверия: `DateTimeOriginal` → `CreateDate` →
`DateTime` → дата из имени файла → дата из пути → `mtime`. Источник
показывается пользователю, неуверенные выделяются. Неправдоподобные
значения (до 1990 года — мёртвая батарейка камеры, или будущее) уступают
следующему источнику.

Принято при реализации:

* **Второе и последующие события дня** получают время начала:
  `2019-07-14`, затем `2019-07-14_2000`. Первое остаётся просто датой, и
  архив, где на день приходится одна съёмка, читается как список дат.
* **Собственная схема читается обратно.** На повторном проходе дерево само
  становится входом: `_HHMM` разбирается назад, иначе кадр, у которого
  дата была только из `mtime`, вернулся бы к полуночи и переехал в другое
  событие. Повторный `organize plan` после применения — пустой.
* **Точность даты не выдумывается.** Путь, знающий только месяц или год,
  даёт `2021/2021-06_без-точной-даты/`, а не первое число месяца.
* **GPS и метка CLIP в имя события не вошли.** Без обратного геокодинга
  координаты дают `55.76N-37.62E` — это не название места; метка CLIP ждёт
  pc-embed.
* **Перенос — только `rename(2)` в пределах диска, без замены.** Файлы с
  других дисков попадают в отказы: копирование 149 GiB не является
  переносом. Цель, занятая в последний момент, не заменяется, а переносится
  тот файл, что был запланирован, — не подменённый под его именем обычной
  программой; подмена, нарочно попавшая ровно между двумя системными
  вызовами инструмента, вне модели угроз и названа в остатках (§11.2
  «Модель угроз», el-3wizg). Том,
  который не умеет переименовывать без замены (exFAT, возможно
  `/mnt/user`, NFS, CIFS, FUSE), останавливает раскладку — и спутником, и
  уборкой служебных файлов, и откатом прогона; уже перенесённое остаётся в
  журнале и откатывается `organize undo --run`. На NAS не проверено.
* **Каталоги Lightroom защищены от переноса,** а не только от удаления:
  ссылка в каталоге ведёт по абсолютному пути и переезда не переживёт.
* **Опустевшие каталоги остаются на месте** — и после раскладки, и после
  её отката: ничего не удаляется (§11.2, решение пользователя el-1y8uo B1).
* **Итог раскладки один для командной строки и веба:** снимки, спутники,
  служебные файлы и байты — то, что перенесено, из `pc-apply`; остановка на
  служебном файле не обнуляет уже перенесённый снимок.

Sony нумерует файлы `DSC0xxxx` со сбросом на 9999 — за много лет и несколько
тушек имена массово повторяются у разных кадров. Дедуп по имени запрещён,
реорганизация разводит коллизии суффиксом `_2`, `_3`; суффикс выдаётся на
пару «исходный каталог + основа имени», поэтому RAW и лежащий рядом JPEG
остаются одним кадром, а спутники (`.xmp`, `.aae`, AppleDouble)
переименовываются следом.

## 14. Открытые вопросы

1. Природа ~11 800 файлов без расширения вне учтённых `.lrdata` (§2.3).
2. Размеры встроенных превью в ARW по моделям камер — определяет, хватает ли
   их для SSIM и ORB, или для части файлов нужен полный декод.
3. Политика для экспортов Lightroom при живом ARW и каталоге: хранить все
   или чистить по порогу разрешения.
4. Порог `RESIZE` по умолчанию (предложение: удалять производные менее 2 МП,
   если есть представление большего разрешения).
5. Добавление паритетного диска до фазы применения (§12.1).
