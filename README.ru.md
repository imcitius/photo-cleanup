# photo-cleanup

Разбор большого фотоархива: дубликаты, серии, регенерируемые данные.
Проект и обоснование решений — [DESIGN.md](DESIGN.md).

*[In English](README.md) · интерфейс говорит на обоих языках, переключатель в
настройках.*

Реализованы:

* **фаза 0** — опись и очистка регенерируемых данных: превью Lightroom,
  кэши, системный мусор;
* **фаза 1** — индекс изображений и разбор архива на семейства: один кадр,
  несколько представлений, у каждого своя роль;
* **фаза 3** — серии и выбор лучшего кадра;
* **фаза 4** — разбор по видам: документы, сканы, скриншоты, пустые кадры;
* **фаза 5** — раскладка по датам и событиям с откатом (см. «Раскладка по
  датам» ниже);
* **веб-интерфейс** поверх всего этого.

Дальше по плану — смысловые категории на эмбеддингах, инкрементальный режим
и видео (§13 дизайна).

## Что делает фаза 0

* обходит дерево, шардируя работу по физическим дискам;
* распознаёт бандлы производных данных по имени каталога и **не заходит
  внутрь** — вместо 24 тысяч файлов превью в описи одна строка;
* читает каталоги Lightroom только на чтение, по копии, и использует их для
  проверок безопасности;
* переносит выбранное в карантин на том же диске (`rename`, мгновенно);
* освобождает место отдельной командой после срока удержания.

## Правила безопасности

| | |
|---|---|
| `*.lrcat-data` | **никогда не удаляется** — ИИ-маски и Denoise, регенерации нет. Запрет на уровне кода, политикой не снимается |
| открытый каталог | есть `*.lrcat.lock` → Lightroom работает с каталогом → бандл заблокирован |
| Smart Previews | удаляются, только если **все** мастера каталога найдены на диске |
| изменился с момента сканирования | пропускается, не переносится |
| карантин на другом диске | отказ: перенос превратился бы в копирование |
| удаление | только `purge`, только явным `--yes`, только после срока удержания |

Пишет всегда кто-то один, каким бы способом вы ни пользовались: пока идёт
задача — или пишет команда — архив заперт на запись, а второму отказывают и
говорят, кто занял. Чтение идёт как обычно. Замок держит операционная
система, поэтому убитый процесс освобождает его сам.

**Чего не обещает командная строка.** Интерфейс возвращает просмотренный план
с токеном и отказывается исполнять что-либо другое. У `apply --yes` токена
нет: он считает план сейчас и исполняет именно его — тот, что напечатан выше.
Если индекс с прошлого раза изменился, уедет то, что говорит новый план.
Флаг `--yes` у `purge` — и есть всё подтверждение, тогда как интерфейс просит
набрать слово. Так задумано: командная строка для тех, кто отвечает за свои
слова, и для скриптов, которые не умеют набирать слова. Когда важно, чтобы
исполнился именно просмотренный план, — интерфейс.

Ничего не удаляется командой `clean` — данные лежат в карантине и
возвращаются одним `undo`. Карантин — это скрытая папка
`.photo-cleanup-quarantine` рядом с самим файлом, в его же каталоге: тот же
диск, перенос — `rename(2)`, ни один байт не копируется. Собрать всё
перенесённое в одном месте можно флагом `--quarantine <путь на том же диске>`
или полем «Папка карантина» в настройках. Место освобождается только на
`purge`.

## Быстрый старт

```bash
cargo build --release
```

Три шага: опись производных данных, индекс изображений, семейства.

```bash
./target/release/photo-cleanup --db pc.db scan --root ~/Pictures
```

```bash
photo-cleanup --db pc.db index --root ~/Pictures
```

Собирать **только релизом**: без оптимизации декодирование изображений идёт
примерно в пятьдесят раз медленнее, и двухминутный проход превращается в
двухчасовой. Для `cargo run` профиль `dev` в `Cargo.toml` уже собирает
пиксельные крейты оптимизированно.

Индексация читает и разбирает снимки в фоновом классе планировщика и
оставляет одно ядро свободным, так что машиной можно пользоваться. Число
потоков меняется флагом `--workers` и в настройках веб-интерфейса.

Остановка безопасна: прочитанное уже в базе, следующий запуск продолжает с
того же места, а не начинает заново.

```bash
photo-cleanup --db pc.db families build
```

```bash
photo-cleanup --db pc.db series build            # серии и лучший кадр
photo-cleanup --db pc.db categories build        # документы, скриншоты, пустые
```

```bash
photo-cleanup --db pc.db plan                    # что будет перенесено
photo-cleanup --db pc.db apply --yes             # перенести в карантин
```

```bash
photo-cleanup --db pc.db organize plan --root ~/Photo   # куда что поедет
photo-cleanup --db pc.db organize apply --root ~/Photo --yes
```

```bash
photo-cleanup --db pc.db serve --bind 0.0.0.0:8080
```

В вебе доступен весь путь: выбор папок, опись, индекс, семейства, серии,
виды, проверка плана, карантин, восстановление и раскладка по датам с откатом.
Долгие операции выполняются на сервере, показывают прогресс и продолжаются
после закрытия вкладки. Каждый перенос требует показанного плана с точными
путями; окончательное удаление — отдельного подтверждения словом «УДАЛИТЬ».

Кнопка «Сделать всё» на странице «Опись и индекс» проходит весь путь до
разбора одной задачей: опись → индекс → семейства → серии → виды. Ничего не
переносится и не удаляется — план переноса по-прежнему утверждается отдельно.
В верхней строке всегда видно, что выполняется и на какой стадии.

Сбросить всё прочитанное и начать заново можно в настройках веб-интерфейса:
«Сброс индекса» забывает файлы, семейства и кэш превью, не трогая ни сами
фотографии, ни журнал переносов.

## Docker и Unraid

Готовые образы собираются на каждый тег и лежат в GHCR, для `linux/amd64` и
`linux/arm64`:

```bash
docker pull ghcr.io/imcitius/photo-cleanup:latest
```

Запуск вручную — один диск массива на один `-v`:

```bash
docker run -d --name photo-cleanup --user 99:100 -p 8080:8080 \
  -v /mnt/user/appdata/photo-cleanup:/data \
  -v /mnt/disk1:/mnt/disk1 \
  -v /mnt/disk2:/mnt/disk2 \
  ghcr.io/imcitius/photo-cleanup:latest
```

Затем открыть `http://<адрес NAS>:8080` и указать корни — те самые
`/mnt/diskN/...`, что смонтированы внутрь.

В Unraid проще всего через Community Applications: найти **photo-cleanup**,
нажать Install и заполнить пути в форме. Если нужно вручную — скопировать
[`templates/photo-cleanup.xml`](templates/photo-cleanup.xml) в
`/boot/config/plugins/dockerMan/templates-user/` и добавить контейнер из
списка шаблонов.

Два требования к монтированию — не косметические:

* **`/mnt/diskN`, а не `/mnt/user`.** Объединяющая файловая система прячет,
  на каком физическом диске лежит файл, а перенос в карантин делается
  `rename(2)` и работает только внутри одной файловой системы. Через
  `/mnt/user` перенос либо превратится в копирование, либо не выполнится —
  инструмент это заметит и откажется.
* **Папки с фотографиями нужны на запись.** Карантин кладёт файл в скрытую
  `.photo-cleanup-quarantine` в его же каталоге. Без подтверждения ничего не
  удаляется, но в архив пишется.

`--user 99:100` — это `nobody:users` в Unraid: перенесённые файлы и кэш
превью останутся с обычными правами, а не root.

Кому Docker не нужен — на странице релиза лежат статические бинарники для
Linux (amd64, arm64) и для macOS на Apple Silicon. Зависимостей нет,
достаточно распаковать и запустить.

### На массиве Unraid

Корни задавать через `/mnt/diskN`, **не** через `/mnt/user` — FUSE-слой
скрывает, на каком диске лежит файл, и ломает и шардинг, и карантин. Массив
без паритета не переживёт отказ диска: карантин не заменяет резервную копию.

```bash
photo-cleanup --db /mnt/cache/appdata/photo-cleanup/pc.db \
  scan --root /mnt/disk1/data/media/foto \
       --root /mnt/disk2/data/media/foto
```


Интерфейс встроен в бинарь, работает без интернета и поддерживает светлую
и тёмную темы. Сборка фронтенда, тесты и контракт задач описаны в
[CONTRIBUTING.md](CONTRIBUTING.md).

Командами то же самое:

```bash
photo-cleanup derived list          # превью и кэши, что заблокировано
photo-cleanup families list -v      # дерево семейств с разбором оценок
photo-cleanup catalogs              # каталоги Lightroom
photo-cleanup status                # сводка и содержимое карантина
photo-cleanup organize runs         # прогоны, которые что-то раскладывали
photo-cleanup organize undo --yes   # вернуть последнюю раскладку назад
```

## Windows

Скачать `photo-cleanup-windows-x64.zip` из
[последнего релиза](https://github.com/imcitius/photo-cleanup/releases/latest),
распаковать куда угодно и запустить **Start photo-cleanup.bat**. Браузер
откроется сам.

Один `.exe`, ставить нечего: интерфейс вкомпилирован в бинарь. База и кэш
превью пишутся рядом с ним, так что папку можно перенести или удалить целиком.

Чего Windows сказать не может. В юниксе файловая система опознаётся номером
устройства; в Windows дешёвого стабильного аналога нет, поэтому вместо него
берётся буква диска. Для двух вещей, которые от этого зависят, — какие диски
читать параллельно и будет ли перенос переименованием — это верная точность.
Не покрыт случай папки, смонтированной в дерево другого тома; в домашнем
архиве он редок. Жёсткие ссылки там тоже не определяются: без inode два имени
одного файла считаются дважды, а не принимаются друг за друга.

## Как читаются результаты

Единица показа — **один спуск затвора**, а не файл. Внутри семейства у
каждого файла своя роль:

| роль | что это | удаляется по умолчанию |
|---|---|---|
| `ORIGINAL` | RAW или нетронутый кадр из камеры | нет |
| `CAMERA JPG` | JPEG, записанный камерой рядом с RAW | нет |
| `CONVERTED` | DNG, назвавший исходный RAW | нет |
| `EXPORT` | экспорт из Lightroom, Photoshop, Capture One | нет |
| `RESIZE` | уменьшенная производная | нет |
| `COPY` | побайтово или попиксельно идентичный близнец | **да** |

Дубликат по умолчанию — только `COPY`. Остальное это разные представления
одного снимка, и они сохраняются.

**Серии не считаются дубликатами.** Кадры со штатива различаются по SSIM
всего на 0.86–0.92, что попадает в любой порог, достаточно мягкий для
перекодировки. Поэтому сходства мало: пара объединяется только если один
файл мог быть сделан из другого — уменьшен, переконвертирован или
пересохранён из тех же пикселей. Два RAW не объединяются никогда.

## Папки с оригиналами

Десять тысяч групп — это десять тысяч нажатий, а человек, у которого архив,
обычно знает о нём одну вещь: снимки лежат вон там, а всё остальное — копии
оттуда. На экране **«Дерево архива»** эту фразу можно сказать один раз.

Дерево строится по индексу и раскрывается как в проводнике: папка, её размер
и число файлов во всём поддереве, а справа — сами кадры с миниатюрами. У
выбранной папки есть кнопка «Здесь оригиналы». Отметка распространяется на всю
подпапочную глубину: любой файл под ней считается оригиналом, и в каждой
группе, где такой файл есть, хранимым становится он.

**Массив — это одна структура, а не три.** На Unraid фотографии лежат на
`/mnt/disk1`, `/mnt/disk2`, `/mnt/disk3` — три файловые системы, потому что
перенос обязан оставаться на одном шпинделе, чтобы быть переименованием. Но
`D/разобрано/даня/театр` при этом одна папка, разложенная по дискам, и дерево
показывает её одним узлом: сколько файлов на каждом диске — написано рядом.
Отметка хранится **путём относительно корня**, поэтому накрывает эту папку
сразу на всех дисках. И на том, который вы добавите в массив завтра: правило
не придётся переставлять.

Когда оригиналы всё-таки на одном конкретном диске, а на остальных копии —
раскройте «Эта папка по дискам» и отметьте именно его. Такая отметка живёт
отдельно и дальше своего диска не идёт.

Отметка — это правило, а не нажатие. Она переживает пересборку семейств и
применяется заново, так что файлы, проиндексированные завтра в той же папке,
тоже станут оригиналами. Снять её можно там же: снимается и то, что она
решила, а выбор, сделанный руками на экране «Дубликаты и версии», остаётся.

Кнопка «Убрать дубликаты оригиналов» строит обычный план переноса, суженный до
групп, чей хранимый файл лежит в отмеченном дереве, — и уносит в карантин
**только точные копии**, где бы в архиве они ни лежали. Каждая уезжает в
карантин на своём же диске. Другие версии снимка (скан и сделанный из него
экспорт) остаются: их различает только человек. Правило и не пытается их
трогать — оно меняет хранимый файл лишь там, где пиксели совпадают, а
остальные группы честно считает и показывает числом.

## Серии — это не дубликаты

Несколько кадров одного момента: очередь на спуске, брекетинг, съёмка со
штатива. Инструмент их находит, ранжирует и отмечает лучший — и **ничего
не предлагает удалять**. Каждый кадр серии это отдельная фотография.

Ранжирование объяснимое и относительное: абсолютная резкость ничего не
значит между камерами и разрешениями, а «самый резкий из этих пяти» значит
всё.

| сигнал | как считается |
|---|---|
| резкость | средний градиент по самой резкой двадцатой части кадра — портрет на f/1.8 по площади в основном не в фокусе, и глобальная мера назвала бы резкий сюжет мыльным |
| потери | доля выбитых в белое и задавленных в чёрное пикселей, со штрафом: информация выброшена навсегда |
| детализация | энтропия гистограммы яркости |

**Наборы pixel-shift защищены от прореживания.** Четыре кадра со сдвигом
сенсора выглядят идентично, но это один снимок, хранящийся несколькими
файлами: потеря любого теряет снимок.

Ещё не реализовано: детекция закрытых глаз и резкости по лицу — для этого
нужна модель детекции лиц (без распознавания, §9.3 дизайна).

## Виды: что определяется без модели, а что нет

Сканы, документы и скриншоты имеют физические признаки, которые читаются
прямо с пикселей и ничего не стоят:

| вид | по чему опознаётся |
|---|---|
| документ, скан | текст идёт строками с промежутками между ними; бумага не насыщена; у скана вдобавок белый фон и бимодальная гистограмма |
| скриншот | нет камеры в EXIF плюс имя файла или точный размер экрана |
| пустой кадр | почти нулевая энтропия и контраст |
| чёрно-белое | насыщенность около нуля при живой энтропии |

Ключевой признак документа — **промежутки между строками**. Забор, кирпичная
кладка и листва тоже дают сотни перепадов контраста в строке, но равномерно
по всей высоте; текст — полосами. Без этого признака в «документы» попали бы
тысячи фотографий.

Документ, снятый камерой в комнате, распознаётся наравне со сканом: на
реальных файлах у него белизна 0.00 и бимодальность 0.04, но строчная
структура на месте. Требование белой бумаги нашло бы только выхлоп сканера.

**Чего этот способ не умеет.** «Фото счётчика», «чек», «документ такого-то
типа» — вопросы о смысле картинки, а не о её пикселях. Для них нужна модель
(MobileCLIP, zero-shot по текстовым описаниям, §9.4 дизайна). Инструмент
говорит об этом прямо, а не угадывает.

## Что делает индексация

Не декодирует RAW. ARW, CR2, NEF и DNG — это TIFF-контейнеры с собственным
оглавлением: читается заголовок, разбираются IFD, один seek достаёт
встроенный JPEG-превью. На 176 файлах Sony ARW это **99 МиБ чтения вместо
3.4 ГиБ**. Поэтому в зависимостях нет libraw.

Полный хеш при индексации не считается — он потребовал бы прочитать каждый
файл целиком и уничтожил бы эту экономию. Записывается размер и оба конца
файла, а полный хеш берётся перед самим действием.

```bash
photo-cleanup derived clean --kind lr-previews --dry-run
photo-cleanup derived clean --kind lr-previews --yes
photo-cleanup derived undo --journal 12
photo-cleanup derived purge --older-than 7d --yes
```

Виды: `lr-previews`, `lr-smart-previews`, `lr-helper`, `lr-lrdata-other`,
`system-junk`. Вид `lr-catalog-data` существует в описи, но недоступен для
удаления.

## Раскладка по датам

После дедупа архив можно разложить в `YYYY/YYYY-MM-DD_событие/`. Событие —
съёмка, отделённая от соседней разрывом больше шести часов (`--gap`); первое
событие дня называется просто датой, следующим приписывается время начала:
`2019/2019-07-14/` и `2019/2019-07-14_2000/`.

Дата берётся по убыванию доверия: `DateTimeOriginal` → `CreateDate` →
`DateTime` → дата из имени файла → дата из пути → `mtime`. Источник
показывается в плане, а неправдоподобные значения (мёртвая батарейка пишет
1980 год) отбрасываются в пользу следующего источника. Если путь знает
только месяц или год, файл кладётся в `2021/2021-06_без-точной-даты/` —
выдумывать день тул не станет. Исключить такие файлы целиком: `--skip-uncertain`.

Что при этом гарантируется:

- перенос — `rename(2)` в пределах одного диска, поэтому `--root` обязан
  быть на том же диске, что и файлы; файлы с других дисков перечисляются в
  отказах, для них нужен свой прогон;
- Sony годами пишет `DSC0xxxx` заново, поэтому коллизии имён разводятся
  суффиксом (`DSC01234_2.ARW`), а RAW и его JPEG сохраняют общее имя;
- `.xmp`, `.aae` и прочие спутники едут вместе с кадром и переименовываются
  следом за ним;
- каждый перенос записан в журнал обоими путями, индекс обновляется, а
  `organize undo` возвращает весь прогон назад;
- файлы из живых каталогов Lightroom не трогаются: перенос разорвал бы
  ссылку (`--allow-lightroom`, если это как раз и нужно);
- раскладка отказывается работать, пока не разобраны дубликаты, иначе по
  новому дереву разложатся и копии (`--allow-duplicates` снимает запрет);
- опустевшие каталоги убираются, кроме корней, с которых шёл обход.

## Запуск на NAS

Образ, собранный на Маке, живёт в демоне Мака — на NAS это другая машина
и другой Docker. Сборку надо доставить.

Самый простой путь: **собрать на самом NAS и получить статический бинарь**,
который запускается без контейнера вообще.

```bash
scripts/deploy-to-nas.sh root@tower /mnt/user/appdata/photo-cleanup
```

Скрипт копирует исходники по rsync, запускает сборку там (архитектура
совпадает, эмуляции нет) и оставляет `/mnt/user/appdata/photo-cleanup/photo-cleanup`.

Вручную то же самое:

```bash
rsync -az --delete --exclude target --exclude .git . root@tower:/mnt/user/appdata/photo-cleanup/src/
```

```bash
ssh root@tower "cd /mnt/user/appdata/photo-cleanup/src && docker build --target export --output type=local,dest=.. ."
```

Бинарь статический (musl, SQLite вкомпилирован), зависимостей нет — на Unraid
переживает обновления ОС.

### Если собирать всё-таки на Маке

Тогда образ нужно перенести целиком:

```bash
docker build --platform linux/amd64 -t photo-cleanup:dev .
```

```bash
docker save photo-cleanup:dev | gzip | ssh root@tower "gunzip | docker load"
```

Либо выгрузить один бинарь и скопировать его:

```bash
docker build --platform linux/amd64 --target export --output type=local,dest=./dist .
```

```bash
scp dist/photo-cleanup root@tower:/mnt/user/appdata/photo-cleanup/
```

### Запуск в контейнере

```bash
docker run --rm \
  -v /mnt/disk1:/mnt/disk1:ro -v /mnt/disk2:/mnt/disk2:ro -v /mnt/disk3:/mnt/disk3:ro \
  -v /mnt/cache/appdata/photo-cleanup:/db \
  photo-cleanup:dev --db /db/pc.db scan --root /mnt/disk3/data/media/foto
```

На фазе сканирования монтируйте диски read-only; запись нужна только для
`clean`, `undo` и `purge`.

## Структура

```
pc-core       типы, определение диска и точки монтирования, форматирование
pc-db         SQLite: схема, миграции, запросы
pc-walk       обход с шардингом по дискам, распознавание бандлов
pc-lightroom  чтение .lrcat только на чтение, проверка наличия мастеров
pc-organize   даты, события и куда переедет каждый файл
pc-apply      карантин, откат, purge, журнал, переносы раскладки
pc-cli        команды
```

## Разработка

```bash
cargo test && cargo clippy --all-targets && cargo fmt --all --check
```

реальный архив — живые каталоги, открытый каталог, smart previews с
потерянными мастерами, сирота, защищённые данные, настоящие фотографии — и
проверяют полный цикл вместе с тем, что защищённое осталось нетронутым.
