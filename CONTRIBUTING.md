# Веб-интерфейс

Интерфейс работает с локальным сервером axum: React, TypeScript, Vite.
Шрифты системные, внешних запросов, CDN и телеметрии нет. В бинарь через
`include_str!` / `include_bytes!` включается **`crates/pc-api/web/dist`**.
Этот каталог хранится в Git вместе с исходниками. На NAS Node.js не нужен;
существующая сборка Docker продолжает работать с готовой статикой.

## Разработка и проверки

Из `crates/pc-api/web`:

```sh
npm ci
npm run build
npx playwright install chromium webkit
```

Из корня репозитория:

```sh
cargo build -p pc-cli
cargo test --workspace --locked
cargo clippy --all-targets -- -D warnings
cargo fmt --all --check
```

Затем из `crates/pc-api/web`:

```sh
npm test
```

Playwright запускает два настоящих сервера на `127.0.0.1:18086` и `:18087`
с отдельными временными базами и архивами. Реальные пользовательские
фотографии не затрагиваются. Проверяются Chromium и WebKit, все экраны,
клавиатура, светлая и тёмная темы с axe, 50 000 виртуальных семейств,
пустые и ошибочные состояния, перезагрузка задачи, подтверждение удаления
и полный цикл с настоящими JPEG: опись → индекс → сборка → план → карантин
→ восстановление → раскладка → откат прогона.

`npm run dev` запускает Vite; `/api` проксируется на `127.0.0.1:8080`.
После изменения исходников выполните `npm run build`, затем пересоберите Rust:
сборка Cargo использует готовый `dist`, а не запускает npm.
После `npm ci` сборка фронтенда не требует сети. Лимит 400 КиБ gzip
проверяется автоматически. CI также проверяет соответствие `dist` исходникам.
Все русские строки клиента собраны в `src/ru.ts`.

## Фоновые задачи

`pc-work` содержит общую для CLI и веба оркестрацию описи и индексации.
`pc-core::work::Control` передаёт прогресс и проверяет отмену между файлами.
Сервер выполняет тяжёлые операции в `spawn_blocking` с отдельным соединением
SQLite/WAL. Одновременно разрешён один исполнитель; ручная правка во время
задачи возвращает 409 с её номером. Чтение API остаётся доступно.

Состояния и параметры хранятся в таблице `jobs`. Прогресс сохраняется
периодически, если SQLite не занят транзакцией, и обязательно при завершении.
Во время транзакции SSE отдаёт свежий снимок из памяти раз в секунду.
После перезапуска `queued` и `running` становятся `interrupted`:
дисковые операции **не повторяются автоматически**. Пользователь проверяет
журнал и запускает новый план. Индексация при повторном запуске пропускает
актуальные файлы. `build-all` — дополнительный серверный вид задачи,
выполняющий семейства, серии и виды последовательно без участия вкладки.

SSE `/api/jobs/{id}/events` передаёт целый объект задачи с полем `progress`,
чтобы клиент получал также конечное состояние и ошибку. Клиент переподключается
с паузой 1–30 секунд, восстанавливается через GET и обновляется при возврате
вкладки из фона. Обычный опрос списка служит резервным каналом.

## Предпросмотр и выполнение

В дополнение к существующим GET-предпросмотрам есть единый контракт:

```http
POST /api/preview
Content-Type: application/json

{"kind":"plan-apply","params":{"roles":["copy"],"allow_lightroom":false}}
```

Ответ: `kind`, `params`, `items`, `refusals`, `total_files`, `total_bytes`,
`token`. В элементах указаны точные исходные пути и назначения, спутники,
а для копий — остающийся файл и его превью. Для раскладки добавлены источник
даты, признак неуверенности, событие и переименование при коллизии.

```http
POST /api/jobs
Content-Type: application/json

{"kind":"plan-apply","params":{"roles":["copy"],"allow_lightroom":false},"plan_token":"<token из предпросмотра>"}
```

Перед первым переносом сервер снова строит план и сверяет его отпечаток.
Устаревший план завершает задачу с понятной ошибкой, ничего не перемещая.
Перед каждым файлом повторяются проверки ядра. Для `derived-purge` дополнительно
требуется `confirmation: "УДАЛИТЬ"`. В интерфейсе также есть отдельный флажок
понимания необратимости. Отсутствие паритета показано явно.

Старые POST `/api/plan/apply` и `/api/quarantine/{id}/undo` возвращают 409
с указанием нового контракта: ими нельзя обойти просмотр плана или очередь.
Откат отдельной записи и прогона тоже требует предпросмотра.

Если удаление из карантина прервано внутри каталога, запись остаётся `pending`:
часть файлов уже может быть удалена. Такая запись не предлагается как целая
обратимая операция. Нужно проверить оба пути и примечание журнала.

## Ручные решения и границы

Ручные даты (`source=manual`) переживают переиндексацию; ручные категории —
повторную классификацию. Выбор keeper, лучшего кадра и разъединение семейств
сохраняются отдельно и применяются при повторной сборке, в том числе из CLI.

`GET /api/fs` показывает только каталоги; компоненты `..` и символические
ссылки запрещены, переход вверх останавливается на точке монтирования.
Сервер по умолчанию слушает loopback; `--bind 0.0.0.0:8080` явно открывает LAN,
что отражается в шапке. Авторизация и многопользовательский режим в объём не входят.

База и кэш задаются при запуске и показаны только для чтения. Папку карантина,
пороги и оформление можно менять в настройках. Новый корень раскладки выбирается
среди существующих папок; дерево годов и событий создаёт операция переноса.

Нагрузочные гарантии на конкретном NAS и архиве 286 ГиБ нужно измерять на NAS:
локальные тесты проверяют ограниченный DOM при 50 000 семействах и реальную
логику задач на небольшом временном архиве.
