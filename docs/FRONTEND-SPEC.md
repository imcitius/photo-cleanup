# Техническое задание: веб-интерфейс photo-cleanup

Версия 1. Документ для разработчика фронтенда и серверной части, которая его
обслуживает. Пишется поверх готового ядра: обход, индекс, семейства, роли,
серии, виды, политика, карантин, журнал и раскладка по датам уже работают и
покрыты тестами. Не работает ровно одно: пользоваться этим из браузера.

---

## 1. Что это за инструмент

Разбор домашнего фотоархива на NAS. Инструмент находит дубликаты, серии,
регенерируемые превью Lightroom и раскладывает архив по датам. Он двигает
и удаляет чужие фотографии, поэтому цена ошибки несимметрична: лишний
вопрос пользователю стоит секунды, потерянный кадр — навсегда.

Архив, ради которого всё написано:

| что | объём |
|---|---|
| изображения | 50 398 файлов, 286 GiB (jpg 39 384, arw 4 290, dng 4 955, tif 1 473) |
| файлы без расширения | ~11 800, ~81 GiB — часть из них фотографии |
| превью Lightroom | ≥92 GiB регенерируемых данных |
| видео | 755 GiB (вне объёма первой версии) |
| каталоги Lightroom | 18 штук, один живой рабочий |

Железо: Unraid, Ryzen 5 7600X, 16 GB RAM, три HDD (disk1, disk2, disk3),
NVMe-кэш. **Паритета нет** — отказ диска означает потерю данных, и
интерфейс обязан об этом помнить (см. §9.4).

Пользователь один. Интерфейс открывается с ноутбука по локальной сети к
`http://nas:8080`. Интернета у страницы может не быть вовсе.

## 2. Что есть сегодня и почему этого мало

Сейчас фронтенд — три файла (`crates/pc-api/web/{index.html,app.js,app.css}`,
суммарно ~950 строк ванильного JS), вшитые в бинарь через `include_str!`.

Есть семь вкладок: обзор, семейства, виды, серии, план и перенос, раскладка,
производные данные.

### 2.1 Что уже отдаёт API

```
GET  /api/status                     счётчики индекса, роли, объёмы
GET  /api/families?limit=&offset=&all=
GET  /api/families/{id}
POST /api/families/{id}/keeper       {file_id}
GET  /api/series?limit=&offset=
GET  /api/categories
GET  /api/derived
GET  /api/plan?roles=&allow_lightroom=
POST /api/plan/apply?roles=&allow_lightroom=
GET  /api/organize?root=&gap_hours=&allow_lightroom=&skip_uncertain=
GET  /api/quarantine
POST /api/quarantine/{id}/undo
GET  /api/thumb/{key}
GET  /api/file/{id}
```

### 2.2 Что доступно только из командной строки

| действие | команда | почему это проблема |
|---|---|---|
| обход дисков | `scan --root ...` | без него интерфейс пуст, а запустить нельзя |
| индексация | `index --root ... --min-size --readers-per-disk --reindex` | часы работы, прогресса в вебе нет |
| сборка семейств | `families build --phash-max --ssim-min` | пороги не подобрать из браузера |
| серии | `series build --gap` | |
| виды | `categories build` | |
| очистка превью | `derived clean --kind --min-size --dry-run` | 92 GiB, самая безопасная победа — и её нет в вебе |
| окончательное удаление | `derived purge --older-than` | |
| раскладка по датам | `organize apply --root --gap --skip-uncertain` | предпросмотр есть, выполнения нет |
| откат раскладки | `organize undo --run` | |
| каталоги Lightroom | `catalogs` | |

### 2.3 Чего не хватает интерфейсу как таковому

- **Нет понятия «идёт работа».** Всё синхронно. Индексация 286 GiB — это
  часы, и такой запрос не переживёт ни таймаут, ни перезагрузку вкладки.
- **Нет прогресса.** Ни SSE, ни поллинга, ни ETA, ни текущего файла.
- **Нет ни одного объяснения, что делать дальше.** Пустая база показывает
  нули и не говорит, с чего начать.
- **Списки не виртуализованы.** 50 тысяч строк убьют страницу.
- **Превью по одному запросу на файл**, без ленивой загрузки.
- **Не читается на плотных данных**: мелкий шрифт, нет группировок, числа
  не выровнены, роли не различимы с первого взгляда.
- **Ни одного автотеста на отрисовку.** Показательный случай: правило
  `#lightbox { display: flex }` перебивало атрибут `hidden`, и невидимый
  чёрный оверлей закрывал всю страницу, съедая каждый клик. Баг прожил
  несколько коммитов, потому что страницу никто не открывал в браузере.

## 3. Что требуется сделать

1. Серверная часть: подсистема фоновых задач с прогрессом, отменой и
   восстановлением после перезапуска; эндпоинты для всех операций из §2.2.
2. Фронтенд: новый интерфейс поверх этого API, покрывающий весь путь от
   пустой базы до разложенного архива, без единого захода в терминал.
3. Тесты: смоук-тест реальной отрисовки в браузере, чтобы §2.3 не повторился.

Требование-критерий, которым проверяется всё остальное: **человек, который
никогда не видел командной строки, должен пройти весь конвейер до конца и ни
разу не потерять понимания, что происходит и что будет, если нажать кнопку.**

## 4. Принципы, от которых нельзя отступать

1. **Ничто не двигается без показанного плана.** Любое действие, меняющее
   диск, сначала показывает: сколько файлов, сколько байт, куда именно, что
   при этом откажется и почему.
2. **Подтверждение содержит числа, а не «вы уверены?».** «Перенести в
   карантин 19 332 файла, 214 GiB?» — да. «Точно?» — нет.
3. **Обратимое и необратимое различаются визуально и по трению.** Перенос в
   карантин обратим — обычная кнопка. `purge` уничтожает данные — отдельный
   цвет, ввод слова для подтверждения, напоминание про отсутствие паритета.
4. **Причина отказа всегда видна.** Файл, который инструмент отказался
   трогать, показывается вместе с текстом причины, а не молча исчезает.
5. **Честность про неуверенность.** Дата из `mtime` и дата из EXIF — разные
   вещи, и интерфейс обязан их различать. Никаких «примерно» без указания
   источника.
6. **Ошибка — это текст с путём.** Не «500», не «что-то пошло не так».
7. **Русский язык интерфейса,** ровный и без канцелярита. Термины ролей
   (`ORIGINAL`, `COPY`, `RESIZE`) остаются латиницей — они уже в данных.

## 5. Серверная часть: задачи и прогресс

Это обязательная предпосылка ко всему остальному, и её нужно сделать первой.

### 5.1 Модель задачи

```
POST /api/jobs            {kind, params}  -> {job_id}
GET  /api/jobs?state=     список, новые первыми
GET  /api/jobs/{id}                       текущее состояние
POST /api/jobs/{id}/cancel                кооперативная отмена
GET  /api/jobs/{id}/events                SSE-поток прогресса
```

`kind` — одно из:

| kind | параметры | что делает |
|---|---|---|
| `scan` | `roots[]` | опись производных данных |
| `index` | `roots[]`, `min_size`, `readers_per_disk`, `reindex` | чтение и индекс |
| `families` | `phash_max`, `ssim_min` | сборка семейств |
| `series` | `gap_secs` | серии и лучший кадр |
| `categories` | — | классификация по видам |
| `plan-apply` | `roles[]`, `resize_below`, `allow_lightroom` | перенос дублей в карантин |
| `derived-clean` | `kinds[]`, `min_size` | перенос превью в карантин |
| `derived-purge` | `older_than_secs` | **необратимое** удаление из карантина |
| `organize-apply` | `root`, `gap_secs`, `allow_lightroom`, `skip_uncertain`, `allow_duplicates` | раскладка по датам |
| `organize-undo` | `run_id` | откат прогона раскладки |
| `journal-undo` | `journal_id` | откат одной записи |

Состояния задачи: `queued` → `running` → `done` | `failed` | `cancelled` |
`interrupted`.

### 5.2 Правила выполнения

- **Одновременно выполняется не более одной задачи, меняющей состояние.**
  SQLite держит одного писателя, а два параллельных переноса по одному диску
  только мешают друг другу. Попытка запустить вторую — `409` с указанием,
  какая занята.
- **Предпросмотры остаются синхронными.** `GET /api/plan` и
  `GET /api/organize` считаются быстро и задачами не оформляются.
- **Отмена кооперативная, между файлами.** Переименование атомарно; задача
  завершается на границе файла, уже сделанное остаётся в журнале.
- **Задачи переживают перезапуск сервера.** Таблица `jobs` (id, kind,
  params JSON, state, progress JSON, started_at, finished_at, error,
  run_id). При старте всё, что осталось в `running`, помечается
  `interrupted`, и интерфейс показывает это на видном месте вместе с
  незавершёнными записями журнала (`journal.status = 'pending'`).

### 5.3 Поток прогресса

SSE, событие не реже раза в секунду и не чаще десяти раз в секунду:

```json
{
  "phase": "чтение файлов",
  "done": 18422, "total": 50398,
  "bytes_done": 41231234567, "bytes_total": 307223456789,
  "current": "/mnt/disk3/data/media/foto/2019/DSC01234.ARW",
  "per_disk": [{"disk": "disk2", "done": 9100, "total": 21000}],
  "eta_secs": 2280,
  "note": "RAW читаются через встроенное превью"
}
```

Требования к клиенту: переподключение с возрастающей паузой, продолжение с
текущего состояния через `GET /api/jobs/{id}` при разрыве, корректная работа
при уходе вкладки в фон.

### 5.4 Недостающие эндпоинты помимо задач

```
GET  /api/fs?path=/mnt/disk3           листинг каталогов сервера для выбора
                                        корней: только каталоги, только чтение,
                                        без содержимого файлов
GET  /api/catalogs                     каталоги Lightroom, их состояние
GET  /api/journal?run=&op=&status=     журнал операций
GET  /api/runs                         прогоны, что сделал каждый
POST /api/families/{id}/split          {file_id} — разъединить ложное семейство
POST /api/series/{id}/best             {file_id} — назначить лучший кадр вручную
POST /api/files/{id}/category          {category} — ручная правка вида
POST /api/files/{id}/date              {taken_at} — ручная дата, source=manual
GET  /api/settings | PUT /api/settings пороги по умолчанию, путь карантина
```

Ручная правка даты и вида уже поддержана в схеме БД (`file_categories.manual`),
и правка человека не должна перезатираться следующим прогоном.

## 6. Экраны

### 6.1 Первый запуск

Пустая база — это не «ноль файлов», это «мы ещё не начинали». Экран ведёт:

1. **Выбор корней.** Через `GET /api/fs`, с подсказкой: указывать
   `/mnt/diskN/...`, а не `/mnt/user/...` — FUSE-слой Unraid скрывает, на
   каком диске лежит файл, и ломает и шардинг чтения, и карантин. Подсказка
   показывается рядом с полем, а не в документации.
2. **Опись** (`scan`) — секунды, сразу показывает найденные превью Lightroom
   и системный мусор.
3. **Индексация** (`index`) — часы. Экран прогресса с ETA, разбивкой по
   дискам, текущим файлом и возможностью закрыть вкладку без последствий.
4. Дальше — семейства, серии, виды: три задачи, которые можно запустить
   одной кнопкой «построить всё» и увидеть как цепочку.

### 6.2 Обзор

Не набор карточек с числами, а состояние конвейера.

- **Цепочка стадий**: опись → индекс → семейства → серии → виды → план →
  раскладка. У каждой: сделано / не сделано / устарело (индекс новее, чем
  сборка семейств) / идёт сейчас. Клик ведёт на стадию.
- **Что это даёт**: возвращаемое место, разбитое по источникам — превью
  Lightroom, точные копии, уменьшенные производные. Отдельно: сколько уже
  лежит в карантине и ждёт `purge`.
- **Предупреждения сверху**: прерванные записи журнала, открытый каталог
  Lightroom (превью удалять нельзя), отсутствие паритета массива, задачи в
  состоянии `interrupted`.
- **Следующий шаг** — одна фраза и одна кнопка.

### 6.3 Семейства

Главный экран разбора. Единица показа — один спуск затвора, а не файл.

Дерево, где отступ показывает происхождение:

```
DSC01234 · 14.07.2019 18:32 · A7 III                        6 файлов · 61 MiB
├── ORIGINAL    DSC01234.ARW      24.1 MiB  6000×4000  ★★★★☆  LR: Main library
│   └── sidecar DSC01234.xmp
├── CAMERA JPG  DSC01234.JPG       8.2 MiB  6000×4000
├── CONVERTED   DSC01234.dng      22.8 MiB  6000×4000
└── EXPORT      DSC01234-Edit.jpg  4.1 MiB  6000×4000
    ├── COPY    DSC01234-Edit.jpg  4.1 MiB  идентичен      /Backup/foto/2019/
    └── RESIZE  DSC01234-Edit.jpg   380 KiB 1200×800       /Web/
```

Требования:

- превью у каждого узла, ленивая загрузка, заметный признак «хранимого»
  файла (keeper) — не только цветом;
- смена keeper одним действием, оптимистично, с откатом при ошибке;
- «разъединить» для ложного объединения (`POST /api/families/{id}/split`);
- сравнение двух кадров: рядом и наложением, зум 1:1 с синхронным панорамированием
  — иначе про две версии одного кадра нельзя принять решение;
- фильтры: только с несколькими файлами, по роли, по диску, по объёму, «где
  провенанс не определился» (роль `?`) — именно это разбирается руками;
- сортировка по возвращаемому объёму, по дате, по числу файлов;
- виртуализованный список: 50 тысяч семейств должны листаться плавно;
- клавиатура: `J`/`K` — навигация, `Space` — сменить лучший, `Enter` — крупно,
  `/` — фокус в поиск. Подсказка по `?`, а не постоянной строкой в шапке.

### 6.4 Серии

Группы кадров одного момента: очередь, брекетинг, pixel-shift. Серии — **не**
дубликаты, и интерфейс обязан это проговаривать: ничего из серии не
предлагается к удалению само по себе.

- кадры в порядке ранга, с разбором оценки (резкость, клиппинг, детализация)
  — оценка показывается как складываемые части, а не одно число;
- назначение лучшего вручную;
- pixel-shift помечен как защищённый, действия прореживания недоступны.

### 6.5 Виды

Документы, скриншоты, пустые кадры, монохром, фотографии. Плитка с превью,
счётчики, фильтр. Исправление вида вручную — и отметка, что вердикт
пользователя не перезаписывается следующим прогоном.

Отдельная честная строка: смысловые виды («фото счётчика», «чек») здесь не
определяются — это вопрос о смысле картинки, а не о её пикселях, и он ждёт
модели (pc-embed, вне объёма).

### 6.6 Политика и план

- переключатели ролей с живым пересчётом: «→ 19 332 файла, 214 GiB»;
- порог для `RESIZE` в мегапикселях;
- защита файлов из живых каталогов Lightroom — включена по умолчанию,
  снимается только явно и с предупреждением;
- список кандидатов: что уходит, **ради чего** остаётся (keeper, с превью
  рядом), какова причина;
- отказы отдельным списком, сгруппированные по причине, с раскрытием;
- применение — задача с прогрессом, потому что каждый файл перечитывается и
  сверяется по пикселям перед переносом;
- карантин: что лежит, сколько места, откат по записи, `purge` с двойным
  подтверждением и напоминанием, что это навсегда.

### 6.7 Раскладка по датам

Сейчас в вебе только предпросмотр; нужно полноценно.

- **выбор корня нового дерева** через тот же `GET /api/fs`, с проверкой на
  сервере, что корень на том же диске, что и файлы: перенос — `rename(2)`,
  и чужой диск превратил бы его в копирование 286 GiB;
- разрыв между съёмками (по умолчанию 6 часов) — ползунок с живым
  пересчётом числа событий;
- **дерево предпросмотра**: год → событие → файлы, с обложкой события
  (лучший кадр из уже посчитанных серий) и числом кадров;
- **источник даты виден у каждого файла**: съёмка (EXIF), имя файла, путь,
  `mtime`. Ненадёжные выделены, есть фильтр «показать только их»;
- **ручная правка даты** для таких файлов, по одному и пакетно для события;
- события с датой до месяца или года показываются отдельно и не
  притворяются конкретным днём;
- переименования из-за коллизий имён (`DSC01234_2.ARW`) помечены с
  объяснением, что имя было занято;
- запрет на раскладку до разбора дубликатов объясняется текстом и ссылкой на
  экран плана, а не сухой ошибкой;
- применение и откат прогона целиком — из интерфейса.

### 6.8 Производные данные

Превью Lightroom и кэши: 92 GiB, которые возвращаются без всякого риска —
это самый первый выигрыш, и он должен быть самым заметным.

- группировка по видам, объёмы, что заблокировано и почему (открытый
  каталог, потерянные мастера, невосстановимый вид);
- очистка и `purge` как задачи;
- явное различие между «удаление запрещено видом данных» и «заблокировано
  сейчас по обстоятельствам».

### 6.9 Журнал и прогоны

Всё, что инструмент сделал с диском: операция, откуда, куда, размер, время,
статус. Фильтры по прогону, типу, статусу. Откат записи или всего прогона.
Прерванные записи — сверху и с объяснением, что проверить.

### 6.10 Настройки

Пути (база, кэш превью, карантин), пороги по умолчанию (`phash_max`,
`ssim_min`, `min_size`, разрыв серий и событий), тема, плотность.

## 7. Визуальный язык

Это инструмент, за которым сидят часами и принимают решения по чужим
фотографиям. Он должен быть спокойным и плотным, а не нарядным.

- **Тема**: тёмная и светлая, обе полноценные, переключение и следование
  системной. Фон явный, не наследуемый.
- **Шрифт**: системный стек, без загрузки с CDN — у NAS может не быть
  интернета. Числа — моноширинные цифры (`font-variant-numeric: tabular-nums`),
  колонки размеров и дат выравниваются по разряду.
- **Сетка**: 8 px, две плотности — свободная и компактная.
- **Цвет несёт смысл, но никогда не один**: keeper, кандидат на перенос,
  защищённый, отказ — различаются меткой или иконкой вдобавок к цвету.
  Контраст текста ≥ 4.5:1, границ ≥ 3:1.
- **Превью**: фиксированное соотношение под контейнер, без прыжков вёрстки,
  скелетон вместо пустоты, полный кадр — только по запросу.
- **Пусто / загрузка / ошибка** — три разных состояния у каждого списка, с
  текстом, который говорит, что делать.
- **Клавиатура**: фокус виден всегда, ловушек фокуса нет, модальное окно
  закрывается `Esc` и возвращает фокус туда, откуда открылось.
- **Ширина**: рабочий минимум — планшет в альбомной ориентации (1024).
  Телефон не целевой, но страница не должна разъезжаться.

## 8. Технические рамки

- **Поставка**: статика вшивается в бинарь (`include_bytes!` или `rust-embed`)
  и отдаётся из `crates/pc-api/web/dist`. Никаких внешних запросов в рантайме:
  ни шрифтов, ни CDN, ни телеметрии.
- **Стек фронтенда на выбор** (Svelte, Solid, React, Vue) при условиях:
  TypeScript, сборка через Vite, бандл ≤ 400 KB gzip, собранный `dist`
  коммитится, сборка воспроизводима без сети после `npm ci`.
- **Сервер**: Rust, axum 0.8, SQLite через rusqlite. Один писатель.
- **Браузеры**: Safari и Chrome, две последние версии.
- **Производительность**: первый осмысленный экран < 1.5 с в локальной сети;
  списки виртуализованы от 200 строк; превью грузятся по мере появления в
  области видимости; SSE переподключается сам.
- **Язык интерфейса** — русский. Строки собраны в одном месте, чтобы перевод
  был возможен, но многоязычность в объём не входит.

## 9. Безопасность и границы

1. **Сервер слушает по умолчанию `127.0.0.1`.** Открытие наружу — явный
   флаг, и интерфейс показывает, что он доступен по сети.
2. **`GET /api/fs` — только листинг каталогов**, без чтения файлов, без
   выхода за пределы существующих точек монтирования, с отказом на
   символические ссылки наружу.
3. **Ничего не удаляется без карантина.** Единственная необратимая операция —
   `purge`, и она требует ввести слово, а не нажать «ОК».
4. **Про отсутствие паритета говорится прямо** на экране `purge`: массив без
   избыточности, восстановить из него нечего.
5. **Файлы живых каталогов Lightroom защищены** и от удаления, и от переноса.
   Снятие защиты — осознанное действие с предупреждением, что ссылки в
   каталоге ведут по абсолютному пути и переезда не переживут.

## 10. Тестирование

- **Смоук-тест отрисовки** (Playwright): страница открывается, ни один
  элемент не перекрывает содержимое, каждая вкладка переключается кликом,
  у корневого контейнера непустая высота. Это прямое следствие бага с
  невидимым оверлеем — такой тест поймал бы его сразу.
- **Тесты состояний**: пустая база, идущая задача, прерванная задача, ошибка
  сервера, пустой результат фильтра.
- **Тест долгой задачи**: прогресс идёт, вкладка перезагружается, прогресс
  продолжается с того же места, отмена останавливает на границе файла.
- **Контрактные тесты API** на стороне Rust — форма ответов фиксируется.
- **Доступность**: проверка контраста и прохода по всем действиям с
  клавиатуры.

## 11. Критерии приёмки

1. Весь путь — корни, опись, индекс, семейства, серии, виды, план, перенос,
   карантин, откат, раскладка, `purge` — проходится из браузера. Терминал не
   нужен ни на одном шаге.
2. Любая длинная операция показывает прогресс, переживает перезагрузку
   вкладки и останавливается по кнопке.
3. Ни одно действие, меняющее диск, не выполняется без показанного плана с
   числами и списком отказов.
4. Каждый отказ объяснён текстом, каждая ошибка показана с путём.
5. Источник даты виден у каждого файла в раскладке; ненадёжные выделены и
   фильтруются.
6. Список из 50 000 семейств листается без подвисаний.
7. Тёмная и светлая темы обе читаемы; весь интерфейс проходится с
   клавиатуры; контраст соответствует §7.
8. Смоук-тест отрисовки в CI зелёный.

## 12. Вне объёма

- Смысловые категории и поиск по смыслу — ждут pc-embed (ONNX, эмбеддинги).
- Видео (755 GiB) — отдельная фаза.
- Инкрементальный режим и приём новых карточек — отдельная фаза.
- Многопользовательский доступ, учётные записи, права.
- Мобильная вёрстка как отдельный сценарий.
